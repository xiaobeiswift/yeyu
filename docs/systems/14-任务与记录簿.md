# 《雾州侠行》任务与记录簿系统工程规格

> 状态：实施中；离线切片已落地：QuestCatalog、目标事实投影、接取/推进/放弃、`READY_TO_TURN_IN` 交付校验、`DELIVER_ITEM`/`OWN_ITEM` 背包快照刷新（可回退）、完成 saga（先预检 → 扣交付物 → 经济发奖 → COMPLETED → `QuestCompleted`；失败保持 READY；幂等 command/receipt 重放；`reward_receipt_id` 落槽 2）、`prerequisite_quest_id` + `accept_policy=AUTO_EVENT` 连锁自动接取（仍走 `AcceptQuest`，绑定 `QuestCompleted.event_id`；`chain_bindings` 可覆盖派生 ID）、`EvaluateQuestAvailability`/`list_availability`/`reveal_hidden_quest`（HIDDEN/LOCKED/AVAILABLE 与入口匹配）、`TrackQuest`（追踪位 1–3；完成/放弃清追踪；Journal 追踪优先排序）、主线接取默认自动占第 1 追踪位（`auto_track_main`，仍走 `TrackQuest`；位 1 已占用不抢占；可关闭）、`QuestSaveBridge` 经 `SaveCoordinator` 合并写槽 2 任务 sections（需 `player_save_scope`；与 world 等同槽 section 合并不整槽覆盖；集成验证 quest→world→quest 重写不互盖，并可 `import_save_bundle` 从槽 2 水合后继续查询）、`QuestCompletionSaveBridge` 完成路径一次检查点写槽 2/4/5（owner 先 `skip_save` 内存提交，再同 `checkpoint_id` 落盘；尚非 ADR-0002 全量子收据 PREPARED/恢复）、SaveCodec（含 `revealed_hidden_quests`/`tracked_quest_runs`）与 section 注册。完整条件集合、PREPARED 子收据前向恢复、PENDING 待领 UI 与 Y3 表现尚未开始。

## 1. 目标与非目标

### 1.1 目标

- 统一承载主线、支线、隐藏事件、教学任务、悬赏/委托等可重复任务的可接取、阶段、目标、分支、交付、奖励和终态。
- 以已提交领域事件推进目标，明确“累计获得”“当前拥有”“交付消耗”“击败”“到达”“对话选择”等不同语义，防止双计数和误计数。
- 任务定义和运行实例绑定版本、稳定 ID 与可验证图；活动任务升级有显式迁移，不因热更静默重置玩家进度。
- 所有接取、阶段推进、交付、奖励和分支选择使用收据与修订；断线/重复回调不重复奖励、不重复消耗。
- 提供记录簿、追踪、地图指引、隐藏信息、完成反馈和只读恢复的明确 ViewModel 契约。
- 首章支持 1 条主线、6 条支线、2 种重复任务以及完整新手引导衔接，且无现实时间/体力对主线阻断。

### 1.2 非目标

- 不在任务配置中编写任意 Lua、改变战斗公式、直接生成随机掉落或直接操作 Y3 单位。
- 不拥有对话图、世界对象、背包、奖励、伙伴、门派或战斗状态；只查询或调用其稳定端口。
- 不实现多人共享任务、公会任务、玩家发布任务、开放式脚本 Mod、现实 GPS、自动寻路跨区或任务编辑器 UI。
- V1 主线不允许永久不可逆失败；分支可改变对白、奖励或局部状态，但不能无恢复路径地锁死首章。
- 记录簿筛选、展开、滚动位置等纯展示偏好不作为任务规则或奖励条件。

| 类型 | 合法语义 | 权威事实/查询 | 计数规则 |
|---|---|---|---|
| `TALK` | ONCE_FACT | `DialogueCompleted` 指定 dialogue/NPC | 命中一次置 1 |
| `CHOOSE_DIALOGUE` | ONCE_FACT | `DialogueChoiceCommitted` | 指定 choice/memory |
| `DEFEAT_ENEMY` | ACCUMULATE | `EncounterCompleted` 的规范化 defeated entries 与 settlement_receipt_id | 按敌人 ID/tag 和数量累计；仅配置允许的已结算结果 |
| `COMPLETE_ENCOUNTER` | ONCE_FACT/ACCUMULATE | `EncounterCompleted` encounter_id/result | 每个唯一 encounter settlement 最多一次 |
| `ACQUIRE_ITEM` | ACCUMULATE | `ItemGranted` | 接取后实际获得量，消耗后不回退 |
| `OWN_ITEM` | CURRENT_SNAPSHOT | 背包查询及物品变化事件触发重算 | `min(current,required)`，可回退 |

| `SEARCH_POINT` | ONCE_FACT | `SearchPointResolved` | 指定 interactable/result |
| `GATHER_NODE` | ACCUMULATE | `GatherNodeHarvested` | 按节点/tag/周期配置累计 |

| `ENHANCE_EQUIPMENT` | ACCUMULATE/ONCE | `EquipmentEnhanced` | 按实际提升级数或次数，配置明确 |
| `LEARN_MARTIAL` | ONCE_FACT | `MartialLearned` | 指定武学/类别 |

### 4.6 `ObjectiveState`

字段：`run_id`、`objective_id`、`progress`、`status`（IN_PROGRESS/COMPLETE）、`last_fact_event_id?`、`state_revision`。不保存 required_count 或描述；从绑定定义读取。CURRENT/DELIVER 目标在查询/相关事件时重算，存的 progress 是最近确认镜像而非外部物品权威。

### 5.4 任务动作白名单

允许：设置当前 run 分支、请求世界 flag、请求对话/Encounter、请求 reward、请求好感或功能解锁、自动接下一任务。动作按阶段 `ON_ACCEPT/ON_STAGE_ENTER/ON_STAGE_COMPLETE/ON_COMPLETE` 分批。外部效果必须调用其唯一所有者并携带由 transaction_id 派生的 child receipt；任务系统不得直接改角色、伙伴、背包、货币或世界表。

`DialogueChoiceCommitted` 只提交“玩家选择了什么”这一事实。好感、招募、任务分支、奖励和世界 flag 分别由其所有者消费并执行一次；对话配置不得再复制同一效果，任务动作也不能与 13 的对话动作双重执行。

动作失败默认阻止阶段提交；启动对话/Encounter 这类外部流程只保存“请求事实/检查点”，其结果通过事件回流，不跨长会话保持数据库事务。

## 6. 运行时状态与不变量

### 6.1 任务会话

- `QuestSession`：活动/终态索引、槽2修订、定义版本缓存、周期可用性。
- `QuestFactInbox`：待处理 DomainEvent，按事件 ID 去重并按稳定到达序列处理。
- `QuestMutation`：接取/事实/交付命令、外部资源事务、槽2/5提交状态。
- `JournalProjection`：可丢弃缓存，按 quest/run revision 重建。

### 6.2 强制不变量

1. 每个非重复 quest 最多一个非终态 run；非 BOARD 重复任务每 period 的 run 数不超过自身上限；BOARD run 必须拥有唯一 source_offer_id，配额由 17 判定。
2. 当前 stage 属于绑定定义，ObjectiveState 恰对应当前阶段目标；历史阶段可只保留摘要。
3. 累计目标 progress 单调且限制为 `0..required_count`；超过需求只夹取“显示/状态计数”，原事件数量仍可在诊断摘要记录。
4. CURRENT/DELIVER 目标可以回退，READY 状态必须随其变化回 `ACTIVE`。
5. 同一 event ID 对同一 run/objective 最多应用一次；同一 combat/reward source occurrence 也不能换 event ID 重复计。
6. 完成奖励只由 completion receipt 发放一次；`COMPLETED` 必须能指向明确收据结果或 `reward_policy=NO_REWARD`。
7. FAILED/ABANDONED/EXPIRED/COMPLETED 为终态，不接收普通进度事件。
8. 主线运行不存在由现实时间或服务器日过期导致的失败。
9. 记录簿追踪、已读和折叠不修改目标进度。
10. 同一 source_offer_id 最多创建一个 QuestRun；BOARD 任务若无 17 的有效 transaction_id 必须拒绝。

### 6.3 活动任务上限

领域硬上限为同时 100 个非终态 run，UI 建议上限不作为拒绝依据。达到硬上限时禁止接取可选任务并返回 `QUEST_ACTIVE_LIMIT_REACHED`；主线自动接续需在生成阶段证明旧主线先终态，或保留专用主线容量 1。V1 追踪上限 3，不限制接取。

## 7. 状态机与详细规则

### 7.1 可接取派生状态

无 run 时依次判断：定义/版本/功能开关 → 是否 deprecated → 可重复周期和次数 → 互斥组历史/活动状态 → 前置条件 → reveal 条件。结果：

- `HIDDEN`：UI 不显示，NPC 也不显示任务标识。
- `LOCKED`：可按配置显示模糊提示，但不能接。
- `AVAILABLE`：可手动/自动接取。
- `PERIOD_UNAVAILABLE`：可信时间不可用，仅冻结重复任务；主线/普通支线继续。

### 7.2 Run 状态机

`AVAILABLE → ACTIVE ↔ READY_TO_TURN_IN → COMPLETING → COMPLETED`。

分支终态：`ACTIVE/READY → FAILED`（仅显式配置）、`ACTIVE/READY → ABANDONED`（策略允许）、周期改变 `ACTIVE/READY → EXPIRED`（repeat policy）。`COMPLETING` 写入未知则 `RECOVERY_REQUIRED`；恢复后只能落回原状态或 `COMPLETED`，不得创建第二奖励。

`AUTO_ON_COMPLETE` 在最后阶段满足后直接进入 COMPLETING；`TURN_IN_NPC` 进入 READY，交付用例再次验证 CURRENT/DELIVER 目标和 NPC。`NO_REWARD` 仍写 completion receipt，保证接续任务/事件只触发一次。

### 7.3 接取

1. 从服务端/世界事实重算可接取，不信任 NPC 图标；BOARD 任务只接受 17 冻结 Offer，普通 `AcceptQuest` 必须拒绝。
2. 创建 run ID、当前阶段和全部初始 ObjectiveState。
3. CURRENT_SNAPSHOT 目标立即读取外部事实；ACCUMULATE 不补算接取前历史。
4. 槽 2 单槽提交 run、初始目标、ON_ACCEPT/首阶段 ON_ENTER 本槽动作和创建子收据；跨所有者动作写入 Saga/outbox 并由子收据前向恢复，不承诺跨槽整体回滚。
5. 发布 `QuestAccepted`，再由 Journal/应用层选择是否自动追踪（主线默认 `auto_track_main=true`：首次接取通过 `TrackQuest` 占用第 1 追踪位；位 1 已占用不抢占；玩家可关闭后不再自动）。

### 7.4 事实消费

1. 验证事件信封/schema，拒绝未知版本。
2. 找出订阅该 event type 的活动当前目标，按 `quest_id/run_id/objective_id` 排序。
3. 对每个过滤器使用事件 payload 白名单字段求值；不得调用会产生副作用的外部服务。
4. 计算增量或触发快照重算，生成候选 ObjectiveState。
5. 同一事件涉及多个任务时，可在一次槽2事务更新；某任务配置错误不得污染其他任务，错误任务进入诊断隔离，事件仍留可重放。
6. 写进度和 event receipt 后才发布 `QuestObjectiveProgressed/Completed`。

任务事件消费必须至少一次传递、业务去重；不能依赖进程内“已经处理”集合。

### 7.5 阶段完成

- 忽略 `optional=true` 后按 ALL/ANY/COUNT 判定。
- CURRENT/DELIVER 目标在判定前重新查询，避免缓存过期。
- 阶段首次满足后，执行 ON_STAGE_COMPLETE，按 branch route 选择后继；若无后继则进入最终完成流程。
- 有后继：槽 2 单槽提交历史阶段摘要、新 stage、新目标、本槽 ON_STAGE_ENTER 动作与收据，修订加 1。
- 同一事实可以完成旧阶段，但默认不得自动用于新阶段累计，避免一个击杀跨两阶段计数；只有目标显式 `allow_carry_fact=true` 且生成器标记为安全时可复用，V1 默认全部 false。

### 7.6 目标语义细则

- `ACQUIRE_ITEM`：只计成功 `ItemGranted`，不计购买预览、待领未领取或迁移镜像；若奖励进入待领，领取后才计。
- `OWN_ITEM`：接取时可立即完成；数量减少可回退。只读取可用所有权，是否包含事务预留由配置固定为 false。
- `DELIVER_ITEM`：达到数量显示完成/READY，但交付时才扣；玩家使用后任务回 ACTIVE。扣除 purpose 为 `QUEST_DELIVERY`，不得由普通 ItemConsumed 误计。
- `DEFEAT_ENEMY`：只读战斗结算中的敌人定义/标签和数量，不从模型死亡事件计数；召唤物是否计数由 enemy 配置 `quest_countable`。
- `REACH_LOCATION`：一次性探索通常用 LocationDiscovered；要求“返回某地”时用经去抖 AreaEntered 且过滤 run 开始后序号。
- `TRAVERSE_LINK`：只计 26 在安全落点验证完成后发布的 `TraversalLanded`。事件必须携带按实际前进顺序规范化的 `traversed_link_ids[]`；若 ObjectiveDefinition.target_id 出现在列表中，则以 `traversal_session_id + target_id` 去重后推进一次。列表重复、同一会话事件重放或一条路径同时包含其他 Link 都不得额外计数；`RequestTraversal` 的接受结果、跳跃动画、迟到 Y3 回调和恢复到岸边均不计。
- `ENTER_WATER_ZONE`：只计具备 WATER_WALK 能力且正常进入目标水面区后发布的 `WaterWalkEntered`；迁移或异常恢复不得伪造完成。
- `GATHER_NODE`：计成功采收，不计仅交互或奖励提交未知；同一 harvest receipt 一次。
- `EQUIP/FORMATION` 教学：只计玩家发起且成功的命令，存档迁移/自动修复事件标为非玩家来源。

### 7.7 分支与互斥

- branch value 只能通过 `ChooseQuestBranch` 写一次，除非定义 `mutable_until_stage_id`；V1 关键选择一经提交不可修改。
- 同互斥组接取一个任务后，其他项可为 `LOCKED_BY_CHOICE`；是否永久锁定由组策略配置。
- 分支路由找不到命中 fallback 是 P0 配置错误，run 停在当前检查点并可恢复，不任意选第一后继。

### 7.8 交付与奖励

交付由 SaveCoordinator 按 ADR-0002 编排：重算目标/验证 NPC 与阶段 → 规范化 DELIVERY 成本和奖励 owner entries → 槽 5 写 PREPARED 意图 → 各所有者按固定顺序预留并提交 child receipt → 槽 2 写 run COMPLETED 与 completion child receipt → 写 COMMITTED/outbox → 发布事件。任一步结果未知均进入 RECOVERY_REQUIRED，并从已存在的子收据前向收敛；Y3 多个云槽之间不承诺 ACID 回滚。

离线最小切片：`QuestCompletionSaveBridge` 在 owner 内存提交（`skip_save`）后，以**一次** `SaveCheckpoint` 合并写槽 2（quest）+ 槽 4（economy balances + inventory stacks）+ 槽 5（economy receipts）。覆盖：纯货币完成、`DELIVER_ITEM` 扣物 + 货币/物品发奖（inventory 亦 `skip_save`）。尚未实现 PREPARED 子收据索引、未知结果 RECOVERY_REQUIRED 前向收敛与 outbox。

- 背包满且奖励允许 PENDING：交付物可扣，任务完成，奖励完整进入待领；UI 必须明确。
- 若奖励策略 REJECT：保持 READY，不扣交付物。
- 写入未知：run/事务显示 RECOVERY_REQUIRED，NPC 不再次显示普通交付按钮，只显示核对；恢复完成后映射到 READY 或 COMPLETED。
- 重复同一 command/receipt 返回原 reward/pending 结果。

### 7.9 放弃、失败与过期

- 放弃不退还已消耗物品、不回滚世界 flag/对话选择/已领奖励；确认页必须列明。
- `ALLOW_RESET_RUN` 再接取时创建新 run ID，累计目标从 0 开始；一次性世界对象若已消耗，生成器必须证明任务仍可完成。
- 主线 `DENY`；支线若存在不可再获得关键物，必须 DENY 或提供恢复来源。
- 周期过期只由 TrustedPeriodPort 的新 period 驱动；时间不可用时保持原 run，不擅自过期。
- FAILED 必须来自明确、已提交事实与配置规则，并提供 UI 说明/替代路线；V1 主线无 FAILED。

## 10. 存档 DTO、槽位与迁移

### 10.1 槽 2 `QuestSaveDTO`

为满足三层限制使用平行表：

| 字段 | 形态 | 说明 |
|---|---|---|
| `quest_runs` | `run_id -> 扁平记录` | quest/version/status/stage/period/revision/receipt |
| `quest_objectives` | `run_id\|objective_id -> 扁平状态` | progress/status/revision/last fact摘要 |
| `quest_branches` | `run_id\|branch_key -> 类型化标量编码` | 不任意嵌套 |
| `quest_stage_history` | `run_id -> 版本化有序 stage 摘要编码` | UI/迁移；设置条目上限 |
| `quest_completion_history` | `quest_id或run_id -> 终态摘要` | 条件/日志，不复制奖励内容 |
| `revealed_hidden_quests` | 稳定 ID 集合编码 | 仅 reveal 事实 |
| `tracked_quest_runs` | tracking_position 1–3 的扁平映射 | 最多三个记录簿追踪位；这里的 1–3 不是云存档槽号 |
| `quest_event_receipts` | event/source occurrence 去重表或压缩高水位 | 与目标进度同槽提交，避免进度已写但去重收据未写 |
| `quest_command_receipts` | 接取、阶段、分支和终态本槽收据 | 输入哈希与结果摘要 |

### 10.2 槽 5

只保存跨槽 `QuestTransaction` 的 PREPARED/RECOVERY_REQUIRED/COMMITTED 状态、owner child receipt 索引和恢复游标。周期权威留在 17，BoardOffer 留在 17，目标事件收据留在槽 2；槽 5 不复制任务进度或重复任务次数。

活动 run 的槽 2 事件收据不能在其终态前删除；终态后可压缩为 run 的最终 `event_projection_hash` 和来源结算收据。一次性奖励/交付的组合收据必须在所有 owner 子收据仍可查询的窗口内永久可判定。

### 10.3 事件去重与容量

- 优先使用来源系统唯一 `event_id`；同时记录 `source_occurrence_id` 防同一事实换事件 ID 重放。
- 单个活动 run 默认最多保留 5000 个事实收据；达到上限进入诊断并压缩连续可证明的事件流，不丢弃未知/未提交事件。
- 对有单调 sequence 的事件流可保存最高连续 sequence 加间隙 ID 集合；压缩算法必须版本化并有属性测试。

### 10.4 迁移

- 活动 run 绑定旧 definition_version；发布包至少保留上一版读取/执行路径，或提供 run migration。
- 增加新目标：默认只影响新 run；若迁移活动 run，必须定义初值（0/当前快照/自动完成）并说明公平性。
- 降低 required count 可完成已有目标；提高 count 不得让已完成历史阶段回退，活动当前阶段需 ADR 和玩家补偿策略。
- 拆分/合并/删除目标使用 `old objective -> new objectives/progress transform` 显式函数和永久迁移收据。
- stage/branch ID 变化提供图节点映射；无法映射时停在最近阶段检查点并进入只读恢复，不直接标完成。
- 重复任务 period 规则变化不重开当前 run；从下一可信周期使用新规则。

## 11. Y3 适配与记录簿 UI

### 11.1 Y3 适配

- Y3 单位死亡、进入区域、点击 NPC 等底层事件不能直接推进任务；对应系统先产生权威领域事件，任务消费者再处理。
- NPC 头顶标识通过 Quest availability/readiness 投影更新；表现延迟不影响接取/交付校验。
- 地图指引只从 `guide_ref_id` 经 WorldGuidePort 转换为当前可见标记；领域存档不保存 Y3 区域/点 Key。
- 任务更新提示从领域事件队列生成，可合并动画但不能合并/丢失权威进度。
- SaveCoordinator 统一编排槽2任务、各 owner 成本/奖励子收据与槽5恢复索引；Y3 回调超时进入核对。

### 11.2 记录簿结构

必须支持 `LOADING/EMPTY/READY/BUSY/READ_ONLY/ERROR/RECOVERY_REQUIRED/PERIOD_UNAVAILABLE`。

- 分类：主线、支线、隐藏（已揭示）、悬赏/委托、已完成；教学可归入当前相关分类或帮助页。
- 默认排序：可交付 → 追踪 → 主线 → 分类 sort order → 接取序号 → quest ID。
- 详情显示阶段描述、目标、进度、交付 NPC、奖励预览、放弃影响、来源/期限和分支已知结果。
- `hidden_until_progress` 目标在未揭示时显示“继续调查”或完全隐藏，不能从地图标记泄露目标。
- CURRENT/DELIVER 目标用不同图标/文本说明“需保持拥有/交付时将扣除”；数量回退即时提示。
- 可重复任务显示可信周期与本周期次数；服务器时间不可用时显示暂停而非倒计时猜测。
- 追踪最多 3 条，HUD 每条最多显示当前阶段 3 个非隐藏目标；更多目标进入详情。
- 提交/放弃按钮防双击；未知提交显示核对页；只读可查看但不能接取/交付/放弃/改追踪。

### 11.3 地图与 NPC 标识

- NPC 标识优先级：主线可交付 > 主线可接 > 支线可交付 > 支线可接 > 重复可交付/可接 > 普通功能。
- 同 NPC 多任务聚合成一个标识，交互时由 13 入口优先级展示。
- 地图标记只显示当前追踪、已发现区域和可公开 guide；跨区显示地区级提示，未发现隐藏点不显示精确位置。
- 自动寻路仅调用世界 `RequestMove/Travel` 的已有能力，不穿越未解锁路线，不传送玩家到目标。

## 12. 边界、失败与恢复

| 场景 | 必须行为 |
|---|---|
| 同事件重复/乱序 | 按 event/source receipt 去重；累计不重复，CURRENT重算最终事实 |
| 活动任务配置/目标未知 | 单 run 隔离为恢复态，其他任务继续；不自动完成或删除 |
| 交付物在 READY 后被用掉 | 目标回退、状态 ACTIVE；交付返回明确缺口 |
| 奖励背包满 | 配置允许则完整待领并完成；否则不扣交付、不完成 |
| 完成写入结果未知 | run RECOVERY_REQUIRED，NPC 显示核对，不允许再次交付 |
| TrustedPeriod 不可用 | BOARD 接取、周期领取和过期判断冻结；主线支线正常 |
| NPC/地点暂时不可用 | 任务保留；指引显示当前不可达原因，不能传送绕过 |
| 玩家放弃含一次性世界物任务 | 生成阶段必须有重获路径；否则该任务禁止放弃 |
| 事件 schema 新旧不兼容 | 保留事件待升级消费者，不丢弃、不按默认 payload 计数 |
| 达到活动/收据上限 | 阻止新可选任务并引导清理/诊断；不删除活动进度 |
| 热更发生于活动阶段 | 继续绑定旧版本或显式迁移；不混读新目标列表 |

## 13. 数据生成与校验

### 13.1 结构与引用

必须拒绝：重复/错误前缀 ID、quest-stage-objective 归属断链、stage 图有环、无终点、分支无 fallback、不可达 stage、同 objective 被多 stage 拥有、event filter payload 字段不在 schema。

### 13.2 可达性与可完成性

生成器必须建立条件/产出/消耗图并检查：

- 主线从新档初始事实到首章完成存在至少一条可达路径。
- 任务所需物品、NPC、地点、Encounter、伙伴、门派条件在相应阶段可获得/可到达。
- 主线要求的 TraversalLink/WaterSurfaceZone 必须在此前保证可获得并装备满足条件的轻功；不能靠可错过支线、随机掉落或付费独占能力解锁唯一主线路径。
- 任务不要求自己的最终奖励作为前置，不产生 quest/flag/item 循环死锁。
- `DELIVER_ITEM` 所需总量有保底来源；允许放弃重接时一次性来源仍可恢复。
- 夜间/昼夜目标有休息/时间推进路径；主线不依赖服务器周期或重复任务刷新。
- 互斥和分支每条允许路径都有首章终点，不把唯一主线锁死。
- TURN_IN NPC 在任务 READY 时存在至少一个可达 interactable/对话入口。

### 13.3 经济、事件与 UI 校验

- reward/cost ID 有效，关键奖励有 PENDING 策略，completion occurrence key 可生成。
- objective 类型、语义、event type/filter/required count 组合合法；CURRENT 不用累计事件，DELIVER 有合法物品。
- `include_pre_accept` 只用于 CURRENT；可重复任务有 period 规则和上限。
- hidden 目标不配置泄露精确地图 guide；所有文本/提示/失败原因本地化 Key 存在。
- 首章所有任务目标事件都有至少一个真实生产者；禁止配置不存在的自定义事件。

生成报告输出：任务依赖 DAG、每条主线/分支可达证明、物品来源/消耗、事件订阅表、NPC入口冲突、隐藏泄露、最长目标数、奖励容量包络、重复周期和版本差异。

## 14. 测试矩阵

| 层级 | 覆盖 | 断言 |

## 15. 验收标准

- 主线、6 支线和 2 种重复任务可从真实 NPC/世界入口完整闭环，不需开发命令且不存在现实时间/体力阻断。
- 每种首章目标有权威事实源；重复/乱序事件、保存重进和断线不会重复或丢失进度。
- ACCUMULATE、CURRENT、DELIVER 三类数量语义对玩家清晰且规则准确，READY 可正确回退。
- 任务交付、物品扣除、奖励/待领、完成状态和收据在故障注入下保持幂等，并能依靠 owner 子收据前向恢复到一致终态。
- 活动任务绑定版本；新增/删除/拆分目标和阶段迁移不会静默清零、误完成或锁档。
- 隐藏任务/目标不会被记录簿、NPC 标识或地图指引提前泄露。
- 服务器时间不可用仅暂停重复刷新，不影响主线/支线和已有非周期进度。
- 配置可达性、资源来源、事件生产者、分支、NPC/地点和奖励校验全部通过。
- 特殊通行任务只由成功落地/正常踏水进入事实推进，主线能力来源可达且不会因换装、断线或落点阻塞形成永久卡关。
- 无引擎、Fake 契约、故障、存档、Y3 冒烟、性能和首章全流程测试通过，P0/P1 为零。
