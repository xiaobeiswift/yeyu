# 《雾州侠行》装备、强化与淬炼系统工程规格

> 状态：实施中；离线切片已落地：实例/穿戴/强化/贡献纯规则、`EquipmentSaveCodec`（槽 4 扁平 instances/affixes/loadouts + 空 tombstones）、section 注册、FakeEquipmentStore、`EquipmentSaveBridge` 合并写槽 4、`EquipmentService` create/equip/unequip + 可选存档，以及 `HydrateGameRuntime` 导入。强化/淬炼扣费事务、槽 5 收据与墓碑销毁路径尚未开始。

## 1. 目标与非目标

### 1.1 目标

- 定义可唯一追踪的装备实例、穿戴槽、武器路线、基础属性、随机词条、强化和淬炼规则。
- 保证预览、扣费、随机结果、实例修改和存档提交位于同一业务事务；重试不得重复扣费或重投词条。
- 为角色属性、战斗快照、背包、奖励、商店、制作和擂台公开快照提供稳定、最小且可校验的接口。
- 首章支持拳套、剑、刀、枪棍四条武器路线，以及头部、衣甲、饰品三个防具槽；24 件装备只复用配置，不复用实例身份。
- 所有派生属性都由合法配置和实例原始数据重算，不在存档或擂台快照中信任最终攻击、防御等派生值。

### 1.2 非目标

- 不定义角色基础属性和最终战斗属性公式；由 `01-角色与属性` 负责组合。
- 不定义物品容积、堆叠、发放和销毁的一般规则；由 `09-背包与物品` 负责。
- 不定义掉落抽取、奖励收据和货币账本；由 `10-经济奖励与掉落` 负责。
- 不定义锻造配方、商店库存、交易、玩家间交易、耐久度、装备损坏、宝石镶嵌、套装随机洗炼或强化失败。
- V1 不提供强化降级、装备继承、付费锁词条、自动批量淬炼和跨角色一键换装；这些能力只有在本文修订后才能加入。

| 10 经济奖励与掉落 | 货币余额、奖励生成的实例原型、词条种子与业务收据 | 槽 4 协调事务中的扣费/创建步骤、拆解产物请求 |

### 2.2 明确的系统端口

本系统对外只暴露以下语义接口；接口名是未来契约名，不限定文件语言实现方式。

| 接口 | 调用方 | 契约 |
|---|---|---|
| `EquipmentQuery.get_instance(instance_id)` | 背包、UI、存档 | 返回不可变实例副本；不存在返回 `EQUIPMENT_NOT_FOUND` |
| `EquipmentQuery.get_character_loadout(character_id)` | 属性、战斗、擂台 | 返回四个槽的实例 ID 与装备修订号 |
| `EquipmentQuery.calculate_contribution(character_id)` | 属性、快照 | 直接返回 01 定义的 canonical `StatContribution[]`，不返回第二套 DTO 或 Y3 Key |
| `EquipmentCreationPort.prepare_instance(source_spec,seed_context)` | 10 奖励、16 制作/商店 | 纯确定性计算并返回 `EquipmentInstanceDraft`；不分配所有权、不扣成本、不写存档、不发布事件 |
| `EquipmentCommand.equip` / `unequip` | UI、任务/引导 | 只能经应用用例调用，成功后统一提交槽 4 |

| `EquipmentValidator.validate_public_instance(dto)` | 擂台 | 白名单、范围、词条来源和强化等级校验后重建 |
| `InventoryEquipmentPort` | 本系统 | 查询所有权、锁定/收藏、消耗材料和槽 4 变更草案；不得绕过背包所有权索引 |
| `Slot4TransactionCoordinator` | 装备、背包、经济 | 在一个槽 4 change set 中提交实例、所有权索引、货币/材料和事务收据；写入未知时按 18 的可恢复事务查询 |
| `EconomyTransactionPort` | 本系统 | 计算并预留货币变化，交由 `Slot4TransactionCoordinator` 提交；不得宣称跨云槽 ACID 回滚 |

跨系统事件仅用于通知已发生事实。角色属性缓存收到 `EquipmentEquipped` 后可以失效，但不得通过事件反向执行穿戴命令。

### 4.3.1 `EquipmentInstanceDraft`（跨系统创建草案）

`EquipmentCreationPort.prepare_instance(source_spec,seed_context)` 的唯一输出。字段固定为：`draft_hash`、`equipment_id`、`enhancement_level=0`、规范化 `affixes[]`、`origin_type`、`origin_ref`、`creation_ordinal`、`config_version`、`rules_version`、`roll_seed_hash`。它不包含 `instance_id`、背包所有权、角色穿戴关系、货币/材料变化或已提交收据。

- `source_spec` 只允许 `equipment_id/origin_type/origin_ref/creation_ordinal/config_version` 和已注册创建策略，禁止调用方传入最终词条值。
- `seed_context` 必须由来源系统根种子按 `equipment:create:<source_occurrence_id>:<creation_ordinal>` 命名空间派生；端口禁止读取本地时间、`math.random`、Y3 句柄或实时背包。
- 相同规范输入必须得到相同 `draft_hash/affixes/roll_seed_hash`；配置断链、词条池不可满足或版本不兼容时整份草案拒绝。
- `instance_id` 在最终槽 4 事务中由 `created_receipt_id + creation_ordinal` 稳定分配。只有 `Slot4TransactionCoordinator` 能把草案变为 08 实例行，同时写入 09 所有权索引、成本/货币变化和经济收据。

### 4.5 属性贡献值

装备属性生产者只输出 00/01 冻结的 canonical `StatContribution`：`source_type`、`source_id`、`target_stat`、`operation`、`value`、`priority`、`condition_tags`、`stable_order_key`。固定映射如下：

- `source_type=EQUIPMENT`；`source_id` 由 `instance_id + ":base"/":enhance"/":affix:"+slot_index` 规范派生。
- 固定值使用 `ADD_FLAT`，相加倍率使用 `ADD_BP`，独立乘区只有配置显式声明时使用 `MULTIPLY_BP`；禁止同时填 `flat_value/rate_basis_points` 这类第二套字段。
- `target_stat` 使用 01 属性白名单；`priority` 来自冻结的装备贡献优先级表，`condition_tags` 是排序去重后的战前上下文标签列表，无条件时为空列表。
- `stable_order_key` 规范为 `equipment:<loadout_slot_order>:<instance_id>:<component_order>:<affix_slot_or_0>:<target_stat>:<operation>:<local_contribution_id>`，任何本地化、UI 顺序或 Y3 Key 都不得参与。
- `stable_order_key` 在完整构筑内必须唯一；输出严格按 01 的 `(priority,stable_order_key)` 排序，同键整份构筑拒绝，保证私有/公开重建和战斗快照一致。

若 UI 需要“基础/强化/词条”分组，可从 `source_id` 生成只读 `EquipmentContributionView`；它不是领域 DTO，不进入存档、公共快照、属性计算或事件。

## 6. 运行时状态与不变量

### 6.1 会话状态

- `EquipmentSession`：加载的槽 4 修订号、实例只读索引、角色 Loadout 索引、未提交命令集合。
- `EquipmentMutation`：`command_id`、期望修订、费用预留、材料预留、变更前/后实例、状态。
- `TemperPreview`：实例 ID、实例修订、目标槽、费用、候选池摘要；仅展示，不预抽结果，不写存档。
- `AttributeCache`：按 `character_id + loadout_revision + instance_revisions` 缓存，任一修订变化立即失效。

### 6.2 强制不变量

1. 一个装备实例最多属于一个角色的一个槽。
2. Loadout 指向的实例必须存在于同一玩家槽 4，且 `owner_character_id` 与角色一致。
3. 装备槽、武器路线、角色等级和角色标签必须全部兼容。
4. 战斗会话锁定后不得修改参战角色装备；命令返回 `EQUIPMENT_COMBAT_LOCKED`。
5. 实例词条必须来自其定义允许的词条池，槽号连续，互斥组不重复。
6. 已发布但被 `deprecated` 的装备可继续加载和穿戴；不得再从新奖励生成。
7. 所有成本、属性和数量计算使用整数；基点除法一律向下取整。
8. 任何失败路径都不得留下“已扣费、未改实例”或“已改实例、未保存费用”的半状态。

## 7. 规则、公式与状态机

### 7.1 属性计算顺序

对每件装备、每个属性按以下固定顺序计算：

1. 读取该属性基础平值 `B`。
2. 读取强化轨道当前等级的额外倍率 `E_bp`，强化后基础值 `B_enhanced = floor(B × (10000 + E_bp) / 10000)`。
3. 汇总该实例所有 `FLAT` 词条为 `A_flat`，按词条槽序相加。
4. 汇总所有 `RATE_BP` 词条为 `A_bp`；本系统不在实例内乘算，作为独立基点贡献交给角色属性系统。
5. 输出平值 `B_enhanced + A_flat` 与倍率 `A_bp`。最终角色属性的乘区顺序由 01 文档定义。

任何中间值超过有符号 32 位整数时立即返回 `EQUIPMENT_STAT_OVERFLOW`，配置生成阶段也必须用最坏组合预检。

### 7.2 强化状态机

`IDLE → VALIDATING → RESERVED → APPLIED → COMMITTED`。

- 校验或预留失败：回到 `IDLE`，无状态变更。
- `RESERVED` 后实例应用失败：释放全部预留并返回失败。
- 存档提交结果未知：进入 `COMMIT_UNKNOWN`，禁用同实例操作，通过幂等键查询或重试；不得直接再次扣费。
- 成功后等级恰好加 1，不支持跳级；批量强化由应用层逐级计算总成本后作为一个槽 4 change set 提交，任一级不满足则在写入前整批拒绝。

### 7.3 强化费用与上限

- 单级费用完全取自目标等级行，不从显示公式反推。
- 批量 `L0 → L1` 的总铜钱和材料是所有目标等级行之和，任意求和溢出则拒绝。
- 达到轨道末级返回 `EQUIPMENT_ENHANCE_MAX_LEVEL`。
- 角色未达到装备穿戴等级不妨碍在背包内强化；章节门槛不满足时禁止强化。

### 7.4 淬炼抽取

1. 调用方提交实例、目标词条槽、幂等键和期望实例修订。
2. 领域层按装备槽、路线、品级、互斥组过滤合法池，再按 `entry_order` 排序。
3. 使用命令事务注入的显式 PRNG；在 `[1,total_weight]` 上取整数并选择首个累计权重覆盖值的条目。
4. 数值可选格数为 `floor((max-min)/step)+1`，用同一 PRNG 的下一次输出等概率选择格位。
5. 若新 `affix_id+tier+value` 与旧值完全相同且池中存在其他合法结果，最多重新抽取 8 次；仍相同时通过“按排序取下一合法候选”确定回退，不额外扣费。
6. 替换目标槽，`roll_ordinal + 1`，实例修订加 1；其他槽不变。

淬炼费用：`cost = floor(base × (10000 + growth_bp × min(old_ordinal, cap)) / 10000)`，最终限制在 0–2,000,000,000。材料数量 V1 不随次数增长。

### 7.5 穿戴与换装

- 穿戴目标槽已有装备时，在同一槽 4 change set 中执行交换：旧装备回背包、新装备设为已穿戴；背包容量按交换后的净占用校验。
- 从角色 A 直接给角色 B 穿戴同一实例时，必须在同一命令显式设置 `allow_transfer=true`；否则返回 `EQUIPMENT_OWNED_BY_OTHER_CHARACTER`。
- 拳套的装备形态为 `FIST_WEAPON`，其 canonical `weapon_route` 必须为 `UNARMED`；空手不是装备实例。`FIST_WEAPON` 不得映射为独立第五路线，角色倾向和武学兼容均只比较 `UNARMED/SWORD/BLADE/STAFF`。
- 卸下若造成背包容量不足则失败；任务强制卸装也必须走相同规则，不能丢到地面。

### 8.2 预览签名

强化/淬炼页面返回 `preview_token`，绑定：玩家、实例 ID、实例修订、槽 4 修订、目标操作、成本配置版本。提交时任一字段变化返回 `PREVIEW_STALE` 并刷新，不允许 UI 传入价格作为权威值。

### 8.3 事务提交顺序

应用层必须按“加载并校验修订 → 计算 → 预留货币/材料 → 生成包含实例、所有权、货币/材料和收据的槽 4 change set → 由唯一协调器写入并回读 → 确认提交 → 发布事件”执行。创建装备时，实例行、09 的所有权索引和经济收据缺一不可；事件不负责补写任何一项。若还影响其他云槽，则引用 18 的 `PendingTransaction` 可恢复 Saga，按子收据前向恢复，不宣称云端 ACID 回滚。发布事件失败不回滚已提交业务状态，由事件发件箱重放；存档写入未知则转 `COMMIT_UNKNOWN` 查询同一收据。

## 10. 存档 DTO、槽位与迁移

### 10.1 槽位

- 槽 `4` 是装备实例和 Loadout 的唯一私人权威持久化位置；不要在槽 3 复制整件装备。
- 槽 `3` 只保存角色对装备实例 ID 的可选镜像时，必须由槽 4 重建且不作为权威；推荐完全不保存镜像。
- 槽 `100` 仅存擂台最小公开装备 DTO，不含实例来源、库存锁定/收藏、费用、收据或随机种子。
- 槽 `5` 保存强化/淬炼命令收据索引，业务结果摘要可引用槽 4 新修订。

### 10.2 扁平化 `EquipmentSaveDTO`

为满足三层嵌套，槽 4 使用平行表：

| 字段 | 形态 | 说明 |
|---|---|---|
| `schema_version/revision` | 整数 | 槽信封 |
| `equipment_instances` | `instance_id -> 扁平实例记录` | 词条不内嵌多层对象 |
| `equipment_affixes` | `instance_id -> 有序紧凑字符串/扁平数组` | 解码后逐字段校验；格式带版本 |
| `character_loadouts` | `character_id -> 四槽扁平记录` | 只含实例 ID 和修订 |
| `equipment_tombstones` | `instance_id -> destroyed_revision` | 防旧档/延迟命令复活；压缩须保留永久收据 |

紧凑词条编码必须是版本化、无歧义、可逆的字段序列，不得执行动态代码。实例数、单实例词条数和字符串长度在读取时设硬上限。

### 10.3 公共 `EquipmentPublicDTO`

仅允许 `equipment_id`、`enhancement_level`、按槽排序的 `affix_id/tier/rolled_value`。实例 ID 可替换为快照内局部序号。读取后依据当前支持的规则版本重算；任何未知、重复、越界、禁用词条使整份擂台快照拒绝，不能静默修正为更弱或更强版本。

### 10.4 迁移

- V0→V1：缺失实例修订补 0；缺失来源标为 `ADMIN_MIGRATION`，生成稳定迁移收据。
- 词条范围收紧时不得夹取旧值后继续用于擂台；私人 PVE 可按明确迁移表转换，无法转换则转为等价补偿奖励并保留墓碑。
- 迁移先验证引用，再构建新 DTO，最后一次替换；重复执行结果一致。
- 槽 4 读取失败或与 Loadout 不一致时进入只读恢复，不自动删除“孤儿实例”。

## 11. Y3 适配与 UI

### 11.1 Y3 适配

- `appearance_id` 在 `adapters/y3/mappings` 映射模型/附件数字 Key；领域和存档不持有句柄。
- 穿戴成功事件驱动模型附件更新；附件失败只记表现错误并可重试，不回滚权威穿戴。
- 战斗开始时表现层从不可变 `CombatSnapshot` 创建单位外观；战斗中背包 UI 被禁用。
- 音效、强化闪光、词条滚动动画不得决定成功或随机结果。
- Y3 云档写入由 SaveStore 适配器处理修订冲突与未知结果，本系统不直接调用云 API。

### 11.2 UI 页面状态

装备页必须支持：`LOADING/EMPTY/READY/BUSY/READ_ONLY/ERROR/COMMIT_UNKNOWN`。

- 左侧角色与四槽，右侧背包候选；候选按兼容优先、品级、定义 ID、实例 ID稳定排序。
- 比较面板分别显示“基础+强化”“词条”“装备后角色最终差值”；最终差值来自属性查询接口。
- 不满足条件的按钮不只置灰，还提供本地化原因。
- 强化页显示当前/目标等级、逐项总消耗、强化必成说明；提交期间锁定目标实例。
- 淬炼页明确只替换哪一槽，确认前不展示伪随机候选；结果由服务返回后再播放动画。
- `COMMIT_UNKNOWN` 显示“正在核对”，只允许查询/安全重试和离开页面，不允许再次购买。
- 所有关键操作提供鼠标与键盘等价路径；拆解/覆盖高品级装备需要二次确认，实际拆解规范见背包/经济文档。

## 12. 边界、失败与恢复

| 场景 | 必须行为 |
|---|---|
| 配置 ID 未知 | 私人旧档进入兼容恢复；公共快照直接拒绝 |
| Loadout 与实例归属不一致 | 不猜测正确方，进入只读诊断并提供修复工具输入报告 |
| 金额/属性溢出 | 命令失败，日志记录配置与实例脱敏信息，不截断 |
| 双击强化/淬炼 | 同幂等键返回同结果；不同键但旧修订返回冲突 |
| 扣费预留后写档失败 | 释放预留或进入未知查询，绝不直接再扣 |
| 词条池过滤后为空 | 返回 `AFFIX_POOL_EMPTY`，不消耗资源 |
| 背包满且需要卸装 | 穿戴交换按净容量判断；纯卸装失败 |
| 已下线装备 | 可读取/穿戴/卸下；禁止新生成；是否允许强化由配置兼容策略明确，默认允许至原上限 |
| 战斗中打开页面 | 只读展示战前快照，所有修改命令失败 |
| 展现附件失败 | 权威状态保留，适配器可重建；不得补发装备 |

## 13. 数据生成与校验

生成阶段必须拒绝：

- 重复/错误前缀 ID，装备引用非装备物品，槽与武器路线不匹配；`FIST_WEAPON` 未映射 `UNARMED` 或出现 canonical `FIST` 路线。
- 强化目标等级不连续、倍率倒退（除非显式允许并有决策记录）、负费用、无效材料、超过整数上限。
- 词条最小值大于最大值、步长不能整除范围、互斥组内仍可重复、权重非正或总权重溢出。
- 装备所需词条数量大于过滤后可形成的合法互斥组合数。
- `deprecated` 内容仍被新掉落、商店或配方引用。
- 基础属性、最大强化和最高词条组合导致任一中间值溢出。
- 外观映射缺失、公共快照允许词条引用未登记属性、配置版本未写入生成清单。
- 任一装备属性无法无损转换为 00/01 canonical `StatContribution`，缺少 `stable_order_key`，仍使用 `stat_key/condition_tag`，或输出了自定义贡献字段/非冻结优先级。

生成报告至少输出：每件装备可用词条数、最小/最大属性包络、强化总成本、所有来源反向引用、下线内容残余引用。

## 15. 验收标准

- 任意合法装备实例可在无 Y3 环境中创建、穿戴、强化、淬炼、序列化、反序列化并得到同一属性贡献哈希。
- 穿戴、卸下、跨角色交换不会产生双重归属，背包满时行为符合净容量规则。
- 强化必成且成本准确；淬炼固定种子、固定配置必得相同结果，重试不重投。
- 任意故障注入点都不会产生扣费与装备状态不一致；未知提交可通过收据恢复。
- 保存重进不丢实例、词条、强化或 Loadout；库存锁定/收藏由 09 的所有权索引单独验收，旧档迁移幂等。
- 擂台公开装备可以完全本地重算，非法实例使快照被明确拒绝。
- Y3 附件失败不污染领域状态；页面覆盖通用六类 UI 状态。
- 配置校验、单元/契约/集成/黄金样本全部通过，P0/P1 缺陷为零。
