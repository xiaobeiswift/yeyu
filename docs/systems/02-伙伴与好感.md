# 《雾州侠行》伙伴与好感系统工程规格

> 状态：实施候选稿；仅描述未来实现，不代表代码已经存在。
>
> 上位约束：[00-通用工程约定](./00-通用工程约定.md)。角色属性见 [01-角色与属性](./01-角色与属性.md)，周期唯一派生见 [17-悬赏委托与刷新](./17-悬赏委托与刷新.md)，平台权益唯一对账编排见 [21-卡池商城与权益](./21-卡池商城与权益.md)。

## 1. 目标与非目标

### 1.1 目标

- 管理伙伴从未发现、可招募、已加入到剧情暂离的完整生命周期。
- 统一接入主线/支线、探索、免费活动和平台权益等招募来源，并保证重复回调不重复创建角色或发补偿。
- 提供好感值、好感阶位、礼物偏好、伙伴事件和阶位奖励的可配置、可审计规则。
- 好感推进不使用全局体力；任何每日限制只能作用于可选赠礼效率，不能阻断主线或伙伴核心剧情。
- 对队伍、对话、任务、角色、奖励和擂台提供明确、最小的跨系统查询接口。

### 1.2 非目标

- 不负责角色战斗属性公式、阵容位置、背包扣物、任务状态推进、对话文本播放、卡池随机结果或付费权益真实性验证。
- 不实现玩家之间的伙伴交易、借用、助战或实时联机关系。
- 首章不实现恋爱/婚姻、多角色互斥结局或伙伴永久死亡。
- 好感系统不通过本地时间刷新，也不允许 UI 直接修改好感或招募状态。

## 2. 依赖与跨系统接口

### 2.1 上游依赖

| 系统 | 输入 | 契约 |
|---|---|---|
| 角色系统 | `CreateOwnedCharacter`、角色拥有查询 | 招募成功后以同一业务收据创建角色；已拥有不得重置 |
| 任务系统 | `QuestCompleted`、条件查询 | 任务只提供已完成事实；伙伴系统自行校验招募规则 |
| 对话/世界系统 | `DialogueChoiceCommitted`、地点/昼夜标签 | 必须是已保存事实或世界/周期系统提供的可信标签；伙伴系统不自行换算时间 |
| 背包系统 | 礼物物品查询与消耗事务 | 先验证礼物，再与好感变更组成一致的应用事务 |
| 奖励系统 | 阶位奖励包发放 | 使用好感事件收据，重复处理只返回原奖励 |
| 卡池/权益系统（21） | 内部 `VerifiedCompanionEntitlementGrant` 与逐份子收据 | 21 独占平台计数访问与唯一 `PaidEntitlementCursor`；伙伴系统只落领域招募结果 |
| 17 `TrustedPeriodPort` | `get_period(cycle_def_id, LIVE)` 返回可信 `period_id`、边界与观察修订 | 可选每日赠礼效率与周期窗口的唯一来源；不可用时暂停相关周期写操作 |
| `ClockService.now()` | 可选可信 UTC 秒 | 仅在确需绝对审计/展示时间戳时调用；禁止在伙伴系统内换算日期键或每日周期 |

### 2.2 下游接口

| 消费方 | 输出 |
|---|---|
| 队伍与阵型 | `is_owned`、`is_temporarily_available`、禁用原因 |
| 对话/任务 | 好感值、阶位、招募状态和伙伴标签的只读条件查询 |
| 角色页 | `CompanionSummaryDTO`、下一阶进度、已解锁事件 |
| 擂台 | 只查询是否拥有；不公开好感数值和私人剧情选择 |
| 运营/卡池 | `already_owned` 与重复转化意图；转化规则由卡池系统决定 |

### 2.3 事务边界

招募、赠礼、伙伴事件结算都属于应用层复合事务：相关槽位必须按跨槽 Saga 的固定步骤提交，部分成功通过业务收据向前补齐。领域事件表示已提交结果，不用于绕过事务发奖。若启用每日赠礼效率，槽 3 只提交永久好感，17 返回的可信 `period_id` 与当期额度只提交槽 5；两者和槽 4 扣物共享同一赠礼事务及子收据。

## 4. 领域模型字段

### 4.1 `CompanionRosterEntry`

| 字段 | 类型 | 约束/含义 |
|---|---|---|
| `companion_id` | string | 必须引用 `role=COMPANION` 的 `char_` 定义 |
| `discovery_state` | enum | `HIDDEN/DISCOVERED/RECRUITABLE/RECRUITED`，只允许单向推进 |
| `availability_state` | enum | `AVAILABLE/TEMPORARILY_UNAVAILABLE`；仅已招募有效 |
| `availability_reason_id` | string/null | 剧情暂离规则 ID；为空表示可用 |
| `recruitment_source_type` | enum/null | `STORY/SIDE_QUEST/EXPLORATION/EVENT/ENTITLEMENT/DEVELOPMENT`；正式版禁用最后一项 |
| `recruitment_source_ref` | string/null | 任务、事件或已验证权益收据 ID |
| `recruited_receipt_id` | string/null | 招募业务收据；已招募必须存在 |
| `affection_points` | integer | `0..10000` |
| `affection_rank` | integer | `0..5`，由阈值计算并持久化作一致性检查 |
| `resolved_event_ids` | ordered set<string> | 已完成的伙伴事件 |
| `claimed_rank_rewards` | ordered set<string> | 形如 `companion_id:rank` 的奖励收据键 |
| `revision` | integer | 每次成功变化加一 |

### 4.2 `RecruitmentEvidence`

| 字段 | 类型 | 说明 |
|---|---|---|
| `source_type` | enum | 与名录一致 |
| `source_ref` | string | 已保存事实的稳定引用 |
| `fact_revision` | integer | 上游事实修订 |
| `verified_at` | integer/null | 权益/服务器事件可带可信服务器秒；普通剧情事实可空 |
| `receipt_id` | string | 本次招募幂等键 |

`VerifiedCompanionEntitlementGrant` 是 21 通过内部应用端口调用的不可由 UI 构造的命令，字段固定为 `entitlement_id`、`entitlement_ordinal`、`mapped_companion_id`、`mapping_version`、`child_receipt_id`、`reconciliation_id`。其中 `child_receipt_id` 按 `entitlement_grant:{entitlement_id}:{entitlement_ordinal}` 稳定派生；同一玩家、权益和序号永远得到同一子收据。它不含平台总计数、`last_observed_platform_count`、平台修订或 `delivery_cursor`。

### 4.3 `AffectionDelta`

字段：`companion_id`、`base_delta`、`preference_multiplier_bp`、`context_multiplier_bp`、`final_delta`、`reason_type`、`reason_ref`、`receipt_id`。所有增量先计算后提交，`final_delta` 范围 `-10000..10000`。首章默认没有降低好感的日常行为；负值只为明确剧情选择预留。

### 4.4 好感阶位

首章冻结为六阶：

| 阶位 | 最低好感 | 语义 | 可配置解锁 |
|---:|---:|---|---|
| 0 | 0 | 初识 | 基础档案 |
| 1 | 500 | 相熟 | 营地对白或小传 |
| 2 | 1500 | 信任 | 伙伴事件 1 |
| 3 | 3000 | 同行 | 天赋/被动解锁候选 |
| 4 | 5500 | 知己 | 伙伴事件 2、外观候选 |
| 5 | 8500 | 生死之交 | 最终事件与终阶奖励 |

上限为 10000。阶位名称只用于本地化，权威状态使用整数。

## 5. 配置字段

### 5.1 `CompanionDefinition`

| 字段 | 必填/默认 | 校验 |
|---|---|---|
| `character_id` | 必填 | 角色存在且为伙伴；全表唯一 |
| `schema_version` | 必填 | `>=1` |
| `roster_sort_key` | 必填 | 整数；相同值再按 ID 排序 |
| `initial_discovery_state` | 默认 `HIDDEN` | 不得为 `RECRUITED`，主角不入此表 |
| `recruitment_rule_ids` | 必填非空 | 引用存在，至少一条在目标版本可达 |
| `affection_curve_id` | 必填 | 引用存在 |
| `gift_preference_set_id` | 必填 | 引用存在 |
| `companion_event_ids` | 默认空 | 无重复，引用存在，排序稳定 |
| `rank_reward_bundle_ids` | 长度 6 | 可空位；非空引用奖励包 |
| `temporary_leave_rule_ids` | 默认空 | 规则不得产生永远不可恢复的循环 |
| `tags` | 默认空 | 已注册标签 |
| `deprecated` | 默认 `false` | 已拥有伙伴仍须可加载 |

### 5.2 `RecruitmentRule`

字段包括 `id`、`source_type`、`source_ref`、`required_fact_ids[]`、`forbidden_fact_ids[]`、`minimum_affection`（招募前通常为 0）、`available_area_ids[]`、`availability_period_rule_id`（可空，引用 17 周期规则）、`priority`、`consume_source`、`compensation_policy_id`。条件采用声明式 AND；OR 由多条规则表达。禁止任意脚本表达式和本地日期解析。

### 5.3 `AffectionCurve`

字段包括 `id`、六个严格递增或首项为 0 的 `rank_thresholds`、`max_points=10000`、`negative_delta_allowed`、`rank_drop_allowed`。首章两项均为 `false`，因此任何负增量只能把值钳制在当前阶阈值，不发生降阶。

### 5.4 `GiftPreferenceSet`

| 字段 | 约束 |
|---|---|
| `companion_id` | 唯一对应伙伴 |
| `tag_multipliers` | 礼物标签到倍率基点；`0..30000` |
| `item_overrides` | 特定 `item_` ID 到倍率；优先于标签 |
| `default_multiplier_bp` | 默认 `10000` |
| `disliked_multiplier_bp` | 首章不得低于 `5000`，避免误操作完全无收益 |
| `daily_efficiency_rule_id` | 默认空；若启用必须声明 17 `cycle_def_id`（如日周期）且不阻断剧情 |

礼物物品自身提供 `affection_value`、标签和是否可赠送。伙伴配置不重复定义物品基础值。

### 5.5 `CompanionEventDefinition`

字段：`id`、`companion_id`、`required_rank`、`prerequisite_quest_ids[]`、`forbidden_fact_ids[]`、`dialogue_id`、`quest_id`（可空）、`choice_result_map_id`（可空）、`reward_bundle_id`（可空）、`repeatable=false`、`sort_key`、`deprecated`。

## 6. 运行时状态与状态机

### 6.1 发现/招募状态机

`HIDDEN → DISCOVERED → RECRUITABLE → RECRUITED`

- 上游事实可一次跨越多个中间展示态，但持久状态永不后退。
- `RECRUITED` 后收到另一招募来源不会再次创建角色；返回 `already_recruited`，由来源系统按其规则决定是否产生重复转化。
- `TEMPORARILY_UNAVAILABLE` 只是已招募伙伴的可出战状态：`AVAILABLE ↔ TEMPORARILY_UNAVAILABLE`。恢复条件必须可达，且不能删除角色构筑。

### 6.2 好感状态机

好感事务按“读取旧值 → 计算增量 → 钳制 → 解析跨越阶位 → 生成一次性解锁与奖励意图 → 形成单一业务结果并按跨槽 Saga 提交”执行。一次增量可跨多阶；每个新阶只生成一次 `CompanionAffectionRankReached`。

`affection_points/affection_rank` 是槽 3 的永久伙伴事实。可选每日效率的 `cycle_def_id/period_id/gift_value_used` 是槽 5 的周期操作账本，不属于 `CompanionRosterEntry`，不得复制回槽 3 或用它反推总好感。

### 6.3 会话态

赠礼窗口中的选中物品、数量和预测增量仅为 UI 临时状态。确认前重新读取背包修订、伙伴修订，并向 17 `TrustedPeriodPort` 请求 `LIVE` 周期；预览不得作为事务输入的权威结果。

## 7. 规则与公式

### 7.1 招募

1. 来源系统提交 `RecruitmentEvidence`。
2. 伙伴系统按 `source_type/source_ref` 找到候选规则，并按 `(priority, rule_id)` 排序。
3. 校验全部已保存事实、禁用事实、时间窗、伙伴状态和定义版本。
4. 选择第一条满足规则；多条同优先级同时满足是配置错误。
5. 与角色系统的 `CreateOwnedCharacter` 共用 `receipt_id` 派生的子收据。
6. 角色创建和名录标记全部成功后发布事件；部分成功在恢复时补齐，不回滚已确认平台权益。

### 7.2 赠礼增量

`base_total = item.affection_value × quantity`

`after_preference = floor(base_total × preference_multiplier_bp / 10000)`

`final_delta = floor(after_preference × context_multiplier_bp / 10000)`

- 数量 `1..999`，单次最终增量 `0..10000`；超过上限按当前可增加空间截断，但仍只消耗实际需要数量。应用层必须先计算 `consumed_quantity`，不得多扣。
- 同一物品多个标签命中时取最高倍率，不连乘；特定物品覆盖优先。
- 已满好感时禁止消耗礼物，返回 `COMPANION_AFFECTION_MAX`。
- 若启用每日效率，规则只能降低超额赠礼倍率，不得禁止赠礼；17 无法返回 `LIVE` 周期时返回可重试错误，不使用缓存周期、本地日期或 `ClockService.now()` 自行换算。
- 每日额度计算只读取槽 5 当前 `cycle_def_id/period_id/gift_value_used`。17 返回新 `period_id` 时为新周期建立新行或重置当期用量，旧行仅用于幂等/审计；同一赠礼收据重放不得再次占用额度。

### 7.3 阶位奖励

- 奖励按跨越的阶位从低到高结算，每阶收据为 `affection_rank:{companion_id}:{rank}`。
- 奖励包失败时好感可以已提交，但槽 5 记录 `PENDING_REWARD`，进入游戏/打开伙伴页时继续幂等补发。
- 属性/天赋解锁必须通过角色系统用例执行，不能由 UI 或伙伴对象直接写角色表。

### 7.4 暂离

- 暂离规则只可由已保存剧情事实触发，按优先级选唯一原因。
- 暂离伙伴若正在队伍，队伍系统收到 `CompanionBecameUnavailable` 后执行显式修复用例；事件本身不直接改阵型。
- 开战前再校验一次可用性。当前战斗已开始后发生的世界剧情变化不影响战斗快照。

## 8. 应用用例

### 8.1 `EvaluateCompanionAvailability`

输入伙伴 ID、世界事实快照和来源修订；前置为槽 2/3 已读取。只读计算发现态、可招募态和暂离原因；需要持久推进时提交期望修订。输出 `CompanionAvailabilityDTO`。错误包括 `COMPANION_CONFIG_MISSING`、`COMPANION_FACT_REVISION_CHANGED`。相同事实修订幂等。

### 8.2 `RecruitCompanion`

| 项 | 契约 |
|---|---|
| 输入 | `companion_id`、`RecruitmentEvidence`、`expected_roster_revision` |
| 前置 | 非只读；证据已保存；规则可达；伙伴未招募 |
| 事务 | 校验规则 → 创建角色子事务 → 写名录 → 写收据 → 发布事件 |
| 输出 | 伙伴/角色摘要、使用规则、修订、`already_recruited` |
| 错误 | `COMPANION_NOT_RECRUITABLE`、`COMPANION_SOURCE_UNVERIFIED`、`SAVE_REVISION_CONFLICT`、`SAVE_READ_ONLY` |
| 幂等 | 相同收据返回原结果；同伴已招募但收据不同返回 `already_recruited`，不发替代物 |

### 8.3 `GrantCompanionFromEntitlement`

只接受 21 内部端口提交的 `VerifiedCompanionEntitlementGrant`。前置为 `mapped_companion_id` 与发布的权益映射版本一致、子收据格式与序号匹配且未被不同载荷占用。事务以 `child_receipt_id` 调用招募领域变化及 `CreateOwnedCharacter` 子事务：未拥有时完成唯一招募，已拥有时只返回 `already_owned=true` 和重复转化意图，由 21 决定兑换凭证；伙伴系统不自行发补偿。输出领域发放结果与伙伴/角色修订。错误包括 `ENTITLEMENT_GRANT_UNVERIFIED`、`ENTITLEMENT_MAPPING_MISMATCH`、`IDEMPOTENCY_KEY_REUSED`、`SAVE_READ_ONLY`。本用例不读取槽 `200–299`，不比较平台计数，也不保存任何权益游标；21 仅在全部领域子收据确认后推进唯一 `PaidEntitlementCursor` 并发布 `EntitlementReconciled`。

### 8.4 `GiveGiftToCompanion`

| 项 | 契约 |
|---|---|
| 输入 | 伙伴 ID、物品 ID、请求数量、幂等键、伙伴/背包/每日账本预期修订；应用层从 17 取得 `LIVE period_id`，不接受客户端周期或日期 |
| 前置 | 已招募且当前允许赠礼；礼物合法；背包足够；非只读 |
| 事务 | 读取槽 5 当前 `period_id` 用量并重算实际消耗/增量 → 以子收据扣槽 4 背包 → 更新槽 3 好感/阶位 → 更新槽 5 周期/额度与主收据 → 创建奖励待办；部分成功按同一 Saga 向前恢复 |
| 输出 | 实际消耗、好感前后、当日额度前后、跨越阶位、奖励状态、各槽修订 |
| 错误 | `COMPANION_NOT_RECRUITED`、`COMPANION_GIFT_NOT_ALLOWED`、`INVENTORY_ITEM_INSUFFICIENT`、`TRUSTED_PERIOD_UNAVAILABLE`、`TRUSTED_PERIOD_ROLLBACK`、`SAVE_REVISION_CONFLICT` |
| 幂等 | 同一键返回首次完整结果；超时后按收据查询，不再次扣物 |

### 8.5 `ResolveCompanionEvent`

输入事件 ID、已提交的对话选择/任务完成事实、幂等键。前置为阶位与前置满足、事件未完成。事务记录完成、应用声明式结果、发奖励/天赋解锁并保存。输出事件结局和奖励。错误包括 `COMPANION_EVENT_LOCKED`、`COMPANION_EVENT_ALREADY_RESOLVED`、`COMPANION_CHOICE_UNCOMMITTED`。一次性事件按事件收据幂等。

### 8.6 `SetCompanionTemporaryAvailability`

仅供剧情应用流程调用，输入已保存事实引用和预期修订。不能由 UI、地图触发器或普通脚本直接调用。输出可用性变化；同一事实重放不重复发事件。

| `CompanionBecameRecruitable` | `companion_id`、`rule_id` |

## 10. 存档 DTO、槽位与迁移

### 10.1 槽位

- 槽 `3`：伙伴名录、永久好感总值/阶位、事件完成和暂离状态；禁止保存周期 ID 或每日赠礼额度。
- 槽 `5`：招募、赠礼、阶位奖励、伙伴事件幂等收据、待补奖励，以及可选每日赠礼周期/已用额度。
- 槽 `2`：招募所依赖的任务/对话/世界事实，伙伴系统只读。
- 槽 `200–299`：由 21 独占读写与对账；伙伴系统既不读取也不写入。

### 10.2 扁平 `CompanionSaveDTO`（槽 3 子表）

| 字段 | 行结构 |
|---|---|
| `schema_version/revision` | 槽子表版本与修订 |
| `companion_rows` | `companion_id/discovery_state/availability_state/availability_reason_id/recruitment_source_type/recruitment_source_ref/recruited_receipt_id/affection_points/affection_rank/revision` |
| `event_rows` | `companion_id/event_id/resolved_choice_id/resolved_revision` |
| `rank_reward_rows` | `companion_id/rank/receipt_id/status` |

写出按伙伴 ID、事件 ID、阶位排序；不得嵌套伙伴→事件→奖励超过三层。

### 10.3 扁平 `CompanionOperationDTO`（槽 5 子表）

| 字段 | 行结构 |
|---|---|
| `schema_version/revision` | 伙伴操作账本版本与修订 |
| `daily_gift_rows` | 可选；`cycle_def_id/period_id/period_observation_revision/companion_id/gift_value_used/last_receipt_id/revision` |
| `operation_receipt_rows` | `receipt_id/operation_type/payload_hash/status/result_ref`；含招募、赠礼、事件与领域权益发放 |
| `pending_reward_rows` | `reward_receipt_id/companion_id/source_type/source_rank_or_event/status` |

`daily_gift_rows` 按 `(cycle_def_id, period_id, companion_id)` 唯一且稳定排序。只保留恢复和审计窗口所需周期；裁剪前必须确认关联赠礼收据终态。权益领域发放行只保存子收据和结果引用，不保存平台总计数、`last_observed_platform_count` 或 `delivery_cursor`。

### 10.4 迁移

- 旧阈值变化时以好感点重新解析阶位，但已经领取的奖励不回收、不重复发。
- 移除/弃用伙伴时保留已拥有行和兼容读取；未拥有角色不再新发现。
- 未知伙伴或事件 ID 进入隔离只读，不删除原行。
- 迁移对暂离原因断链只能恢复为 `TEMPORARILY_UNAVAILABLE + UNKNOWN_REASON`，不得擅自设为可用；由兼容规则修复。
- 若旧候选 DTO 曾把 `daily_gift_rows` 放在槽 3，迁移必须先由 17 的兼容映射把旧可信日期键转换为 `(cycle_def_id, period_id)`，再按 `(cycle_def_id, period_id, companion_id)` 幂等复制到槽 5 并写迁移收据；无法证明来源可信时隔离而不重置额度。只有槽 5 回读确认后才能从槽 3 新版本输出中移除。
- 若旧候选 DTO 含伙伴权益游标，只有 21 以迁移收据接管并确认后才可丢弃；伙伴新 Schema 永不保存该字段。

## 11. Y3 适配与 UI

### 11.1 Y3 适配

- 地图 NPC 只携带交互映射 ID；点击后调用可用性查询，不直接招募。
- NPC 显示/隐藏、头顶标识由 `CompanionAvailabilityDTO` 驱动。表现失败不改变发现或招募状态。
- 云存档适配器只做槽 3/5 DTO 转换、修订和错误映射，并保证每日行不会写入槽 3。
- 伙伴模块不提供平台权益适配器。21 通过内部应用端口提交已映射的领域发放命令；Y3 商城对象、平台计数、修订和游标均不能进入伙伴领域层。

### 11.2 UI

- 伙伴名录支持未知剪影、已发现、可招募、已加入和暂离五种视图。
- 详情页显示好感进度、当前阶、下一阶阈值、偏好提示、已解锁/未解锁事件；不泄露隐藏剧情条件全文。
- 赠礼确认展示预计消耗与预计增加，提交后以服务器确认结果校正；按钮忙碌时防重入。
- 已满好感、背包不足、可信周期不可用、只读恢复、奖励待补均有独立提示和安全重试入口。
- 暂离伙伴在队伍页显示明确原因和“前往任务”入口（若配置可导航），不得静默从玩家名录消失。

## 12. 边界、失败与恢复

- 招募与角色创建部分成功：以收据恢复缺失一侧；不得删除已创建角色重做。
- 赠礼扣物成功而保存伙伴失败：收据状态必须允许恢复好感或补回物品，不能简单重试扣物。
- 好感增量跨多阶但奖励服务失败：保存全部待补收据，按阶升序补发。
- 17 报告周期回退、观察修订冲突或非 `LIVE` 状态时暂停每日效率相关赠礼，不影响查看和剧情事件；伙伴系统不得自行比较日期字符串。
- 槽 3 好感已写而槽 5 每日额度未知时，赠礼事务保持 `RECOVERING` 并按原收据及原 `period_id` 补齐槽 5；不得再次扣物、增加好感或使用新周期重算。
- 已暂离伙伴被阵型引用时，队伍系统必须显式修复；战斗启动拒绝含不可用伙伴的快照。
- 重复拥有的付费伙伴不由本系统决定补偿数量，避免不同入口规则冲突。
- 配置把同伴事件互相前置成环时生成失败；运行时不尝试猜测解环。

## 13. 生成与静态校验

必须检查：伙伴/角色一一对应、招募规则来源存在、至少一条可达路径、同优先级歧义、好感阈值严格有序、奖励断链、事件前置环、暂离无法恢复、礼物倍率/基础值范围、事件重复 ID、隐藏内容意外暴露、本地化和资源映射。

生成报告还应列出：每名伙伴最早可招募节点、全部免费/权益来源、达到各阶所需的标准礼物量、一次增量跨阶奖励顺序、所有伙伴事件的可达路径，以及所有依赖 17 `cycle_def_id` 的规则。

## 14. 测试矩阵

| 类别 | 用例 | 通过条件 |
|---|---|---|
| 招募状态机 | 顺序推进、跨态推进、回退、重复来源 | 只单向推进，重复不重置/重发 |
| 招募事务 | 角色成功/名录失败、超时、修订冲突 | 收据可恢复为唯一一致结果 |

## 15. 验收标准

- 五名首章可用角色中的所有伙伴均有至少一条生成器证明可达的招募路径。
- 任一招募证据和收据重放 100 次只创建一次角色、记录一次招募事实。
- 赠礼在偏好、满值、跨阶、背包修订冲突和保存超时下不多扣、不重复加好感。
- 阶位奖励可在故障后幂等补发，且不会因阈值迁移重复领取。
- 暂离/恢复、队伍修复和开战校验契约通过集成测试。
- 本地时间或直接调用 `ClockService.now()` 都不能改变/生成日规则；17 可信周期不可用时安全降级。
- UI 覆盖加载、未知、可招募、已招募、暂离、满好感、错误、只读和待补奖励。

## 16. 实施任务拆分

1. 冻结伙伴、招募来源、好感阶位、事件和错误码枚举。
2. 建立伙伴/招募/曲线/偏好/事件 Schema 和可达性校验器。
3. 实现名录聚合、招募状态机、好感值对象、阶位解析与暂离规则。
4. 定义角色、任务、对话、背包、奖励、21 权益领域发放、17 `TrustedPeriodPort` 和可选绝对时钟端口契约。
5. 实现六个应用用例、复合收据和部分成功恢复流程。
6. 实现槽 3 永久伙伴 DTO、槽 5 每日/收据 DTO、跨槽迁移、隔离读取与 Fake 仓储；不得实现权益游标。
7. 完成状态机、公式、幂等、跨槽故障注入和配置可达性测试。
8. 实现 Y3 NPC 映射、云档适配和伙伴/赠礼 ViewModel。
9. 接入队伍可用性修复、任务/对白条件和阶位奖励消费者。
10. 运行首章全伙伴招募、好感与存读档验收。

## 17. 待决项

- 好感是否提供战斗数值天赋；若提供，阶位 3/5 的增益上限需单独平衡并进入角色贡献契约。
- 是否启用每日赠礼效率递减；当前默认不启用，物品库存本身即成本。
- 付费获得伙伴已拥有时的重复转化比例，由卡池/权益文档决定。
- 伙伴事件是否允许负好感；当前首章不降阶，负结果只可降至当前阶阈值。
- 主线强制暂离时是否允许用“试用镜像”完成指定战斗；当前默认不允许镜像替换真实构筑。
- 主角是否出现在伙伴名录同一 UI；领域模型明确主角不属于 `CompanionRosterEntry`。
