# 《雾州侠行》经济、奖励与掉落系统工程规格

> 状态：工程实施规格候选稿；仅描述未来实现，不代表代码、配置或平台服务已经存在。
>
> 上位约束：[00-通用工程约定](./00-通用工程约定.md)。付费权益和卡池不由本文定义，参见 21 系统。

## 1. 目标与非目标

### 1.1 目标

- 建立单一货币账本、奖励批次、掉落抽取、待领取奖励、一次性奖励和事务收据规范。
- 让任务、战斗、探索、商店、制作、经脉、装备、门派和重复内容共用相同“计算—预检—提交—恢复”链路。
- 所有随机掉落接受显式种子和 PRNG；相同配置版本、上下文和种子必须得到相同规范化奖励结果。
- 对每种货币明确权威来源、合法消耗方、余额上限和溢出策略，禁止 UI 或其他系统直接写余额。
- 保证任何崩溃、重试、断线或存档冲突不会重复发奖励、重复扣款或吞掉已结算奖励。

### 1.2 非目标

- 不定义付费订单、服务器随机卡池、角色/武学权益、概率公示或审计；由 `21-卡池商城与权益` 负责。
- 不定义背包容量、物品使用、装备实例内容、商店库存、制作配方、门派等级或任务状态机。
- 不实现玩家交易、市场浮动价格、离线挂机收益、体力兑换、广告奖励、邮件附件或自动出售。
- 不用客户端统计抽样替代配置正确性；统计测试只负责发现异常。

## 4. 领域模型

### 4.1 `CurrencyDefinition`

| 字段 | 类型/范围 | 说明 |
|---|---|---|
| `currency_id` | `currency_*` | 稳定 ID |
| `category` | `SOFT/PROGRESSION/FACTION/PREMIUM_TEST/PREMIUM_PLATFORM` | 权限边界 |
| `balance_cap` | 整数 1–2,000,000,000 | 单余额硬上限 |
| `overflow_policy` | `REJECT/CLAMP_WITH_COMPENSATION/PENDING` | V1 默认 `REJECT` |
| `display_precision` | V1 固定 0 | 只允许整数 |
| `source_policy_id` | `currpolicy_*` | 合法来源白名单 |
| `sink_policy_id` | `currpolicy_*` | 合法消耗用途白名单 |
| `negative_allowed` | V1 固定 false | 禁止欠款 |
| `icon_id/name_key` | 资源/本地化 Key | 展示 |
| `deprecated` | 布尔 | 旧档兼容 |

首发规划货币：

| ID | 类别 | 主要来源 | 主要消耗 |
|---|---|---|---|
| `currency_copper` | SOFT | 任务、战斗、出售/委托 | 商店、强化、淬炼、制作 |
| `currency_experience` | PROGRESSION | 战斗、任务 | 武学领悟或角色经验转换；不得与角色等级经验重名 |
| `currency_true_qi` | PROGRESSION | 任务、副本、探索 | 经脉激活 |
| `currency_faction_<id>` | FACTION | 门派任务 | 门派商店、门派成长 |
| `currency_test_jade` | PREMIUM_TEST | 开发/封测配置 | 测试币卡池；正式配置必须隐藏 |
| `currency_premium_jade` | PREMIUM_PLATFORM | 仅平台核验权益 | 合法付费消费；本文不直接增发 |

材料是 `item_*`，不作为货币；角色战斗内“聚气”是战斗资源，不是本账本余额。

### 4.2 `CurrencyAccount`

字段：`currency_id`、`balance`、`reserved`（运行时/恢复态）、`account_revision`。可用余额为 `balance-reserved`，必须始终非负。任何修改附带 `delta`、`purpose_type`、`purpose_ref`、`receipt_id`。

### 4.3 `RewardEntry`

| 字段 | 类型 | 说明 |
|---|---|---|
| `entry_type` | `CURRENCY/ITEM/EQUIPMENT/CHARACTER_XP/MARTIAL_XP/AFFINITY/UNLOCK_FLAG` | 白名单 |
| `target_id` | 稳定 ID | 货币、物品、装备定义、角色等 |
| `quantity` | 正整数 | 装备通常为 1 |
| `target_character_id` | 可空 | 角色/武学类奖励必填或由上下文解析 |
| `metadata` | 扁平白名单字段 | 装备词条池版本等，禁止任意脚本 |
| `entry_order` | 正整数 | 规范化前来源顺序 |

`target_id` 按 `entry_type` 使用闭合前缀映射：`CURRENCY→currency_`、`ITEM→item_`、`EQUIPMENT→equip_`、`CHARACTER_XP→char_`、`MARTIAL_XP→martial_`、`AFFINITY→char_`、`UNLOCK_FLAG→flag_`。它是最长 96 字节的稳定内容 ID，不受运行时原子组件 64 字节上限影响；类型与前缀不匹配时整条奖励拒绝。

规范化后同货币/同物品/同目标成长项合并；装备实例不合并，每件有独立创建序号和种子派生标签。`UNLOCK_FLAG` 的 `metadata.owner_type` 必填并与 flag 注册表一致，禁止由运行时猜测 owner。

`RewardEntry` 只是统一奖励编排语言，不转移字段所有权：

| 条目 | 唯一写入 owner | 提交方式 |
|---|---|---|
| `CURRENCY` | 10 货币账本 | 槽 4 change set |
| `ITEM` | 09 背包 | 槽 4 change set |
| `EQUIPMENT` | 08 实例内容 + 09 所有权索引 | `Slot4TransactionCoordinator` 同时写实例、所有权和经济子收据 |
| `CHARACTER_XP` | 01 角色 | `CharacterRewardPort` + owner 子收据 |
| `MARTIAL_XP` | 04 武学 | `MartialRewardPort` + owner 子收据 |
| `AFFINITY` | 02 伙伴 | `CompanionAffinityRewardPort` + owner 子收据 |
| `UNLOCK_FLAG` | flag 命名空间对应的世界/功能 owner | `UnlockFlagRewardPort` + owner 子收据 |

子收据规范为 `reward:{receipt_id}:{entry_index}:{owner_type}`；`entry_index` 使用规范化后的稳定顺序。经济系统只保存 prepared/result 摘要和子步骤状态，不直接写槽 2/3 的角色、武学、伙伴或世界聚合。

### 4.4 `PreparedReward`

字段：`prepared_id`、`source_type`、`source_ref`、`source_occurrence_id`、`config_version`、`seed_hash`、规范化 `entries`、`content_hash`、`overflow_policy`、`expires_period_id?`。它是可验证计算结果，不等于已经拥有。

### 4.5 `RewardReceipt`

| 字段 | 说明 |
|---|---|
| `receipt_id` | 全局业务幂等键，与命令 ID 可相同 |
| `source_occurrence_id` | 来源唯一实例，如战斗结算 ID、任务周期 ID |
| `request_hash` | 规范化输入哈希；同键不同输入必须报错 |
| `result_hash` | 最终奖励和成本摘要哈希 |
| `status` | `PREPARED/RESERVED/COMMITTED/PENDING/REVERSED/UNKNOWN` |
| `slot4_revision/slot5_revision` | 成功落盘修订 |
| `owner_revision_entries` | 扁平 `owner_type/aggregate_id/revision`；仅保存已确认子步骤证明 |
| `result_summary` | UI 可恢复的最小扁平摘要 |
| `owner_child_receipts` | 扁平 `child_receipt_id/owner_type/status/result_hash`；用于前向恢复 |

### 4.6 `PendingReward`

字段：`pending_id`、`receipt_id`、完整规范化奖励条目、创建来源、创建可信时间或内容序号、状态 `AVAILABLE/CLAIMING/CLAIMED/CANCELLED`、版本。V1 待领奖励不因本地时间过期；运营奖励如需过期必须由可信服务器周期和配置明确规定，过期后也不能静默删除未领取付费权益。

## 6. 运行时状态与不变量

### 6.1 交易状态机

`NEW → VALIDATED → RESERVED → APPLIED → COMMITTING → COMMITTED`。

异常分支：验证失败到 `REJECTED`；预留失败释放到 `REJECTED`；写入结果未知到 `UNKNOWN`；背包容量不足且策略允许则由 `VALIDATED → PENDING → COMMITTED`（提交的是待领记录，不是物品所有权）。

只有 `COMMITTED/REJECTED/REVERSED` 为明确终态；`UNKNOWN` 必须用同一收据查询。V1 普通 PVE 奖励一旦提交不提供任意回滚；退款仅针对尚未消费的明确商业订单并由 21 系统定义。

### 6.2 不变量

1. 所有余额是 `0..balance_cap` 整数，预留不超过余额。
2. 同一 `source_occurrence_id` 对一次性来源最多存在一个 `COMMITTED` 或 `PENDING` 收据。
3. 同一 `receipt_id` 不同 `request_hash` 返回 `RECEIPT_PAYLOAD_MISMATCH`，不得覆盖。
4. 奖励条目不得为 0 或负数；成本由独立 `CostEntry` 表达。
5. 掉落抽取不读取 UI 时间、帧数、Y3 句柄或无序表遍历。
6. `PreparedReward.content_hash` 在提交前必须重算验证，防止 UI 篡改。
7. 货币、背包、装备实例、装备所有权索引和对应经济子收据必须由槽 4 协调器作为一个 change set 提交；`EquipmentCreated/EquipmentOwnershipAdded` 只通知已提交事实，不能补写所有权。
8. 角色经验、武学经验、伙伴好感和解锁 flag 只经其 owner port 写入；跨槽奖励按 18 `PendingTransaction` 和子收据前向恢复，不能以回滚已确认成长冒充云端 ACID。

## 7. 规则、算法与公式

### 7.1 权重抽取

奖励 PRNG 只调用 06 冻结的 `DeriveSeedV1(root_seed, "reward", reward_context_id)`。其中 namespace 必须是字面量 `reward`，不得把来源信息拼进 namespace；`reward_context_id` 固定为 `CanonicalReceiptHashV1(namespace="reward_seed", fields={loot_id,source_occurrence_id})` 生成的派生收据 ID，字段按规范名排序。每个来源与掉落表因此拥有独立 `reward_seed`。它不复用 06 战斗内核 PRNG 状态；奖励侧即使为审计稳定多消耗一次随机输出，也不得改变任何 `CombatEvent`、行动顺序或事件哈希。

对 `WEIGHTED_ONE`：过滤条件后按 `entry_order`、`reward_id` 排序；总权重 `W = no_drop_weight + Σweight`，必须为 1–2,000,000,000。PRNG 取整数 `r∈[1,W]`，从 no-drop 区间开始累计，选首个覆盖 `r` 的条目。每次 roll 都消耗固定次数的 PRNG 输出；即使候选只有一项，也按版本化算法约定是否消耗，V1 规定消耗一次。

### 7.2 独立概率

`INDEPENDENT_EACH` 对每个条目按稳定顺序取 `r∈[1,10000]`，`r<=chance_bp` 成功。`chance_bp=0` 仍消耗一次输出，`10000` 也消耗一次，保证修改概率不改变后续条目 PRNG 位置的审计规则。

### 7.3 随机数量

若 `min<max`，使用下一次 PRNG 输出在包含边界的整数区间等概率选择；然后应用缩放：`scaled = floor(raw × rate_bp / 10000) + flat_bonus`，最终至少 1，超过目标上限则整个准备失败，不截断。

### 7.4 重复唯一项

`REROLL_UNIQUE` 先排除本批已经命中的 `unique_key`，重新计算权重并抽取，最多重复“原配置候选数”次。候选耗尽时转 no-drop；不得无限循环。是否拥有历史唯一项由调用上下文的可信白名单集合提供。

### 7.5 余额变更与溢出

- 成本预检：`available >= cost`，否则整笔失败。
- 奖励预检：`balance + reward <= cap`。默认 `REJECT`；关键奖励可转 `PENDING`。
- `CLAMP_WITH_COMPENSATION` 只有明确配置补偿货币/物品且生成器证明无互相溢出循环时才允许；V1 不启用。
- 多货币按 `currency_id` 排序预留，避免实现层死锁顺序不一致。

### 7.6 奖励规范化顺序

条目排序键：`entry_type_order → target_id → target_character_id → equipment_creation_ordinal`。合并后计算内容哈希。表现顺序可以按稀有度重排，但不得影响权威哈希和任务事件顺序。

### 7.7 来源唯一键

| 来源 | `source_occurrence_id` 组成 |
|---|---|
| 战斗 | `combat_session_id + settlement_version` |
| 一次性任务 | `quest_id + quest_run_id + reward_stage` |
| 重复任务 | `quest_id + trusted_period_id + cycle_ordinal` |
| 宝箱 | `interactable_id + world_instance_id` |
| 采集 | `node_id + trusted_refresh_period + harvest_ordinal` |

来源系统必须提供该键；本系统不根据当前余额猜测是否已领取。

## 8. 应用用例契约

| 用例 | 输入 | 前置 | 事务/幂等 | 输出 | 主要错误 |
|---|---|---|---|---|---|
| `GetEconomySnapshot` | 货币列表 | 存档已加载 | 只读 | 余额、预留、上限、修订 | `SAVE_NOT_READY` |
| `PrepareReward` | reward/loot ID、上下文、种子、来源 | 配置和来源合法 | 纯计算；相同输入结果相同 | `PreparedReward`、哈希 | `REWARD_CONFIG_INVALID`、`LOOT_CONTEXT_INVALID` |
| `GrantPreparedReward` | prepared、溢出策略、`command_id` | 哈希有效、来源未领 | 槽5父意图 + 槽4 change set + owner 子收据，按18 Saga恢复；命令幂等 | 发放或 pending 结果 | `INVENTORY_FULL`、`CURRENCY_CAP_REACHED`、`RECEIPT_CONFLICT` |
| `SpendResources` | 成本、用途、目标引用、预览 token、`command_id` | 用途白名单、余额/物品足 | 全量预留并提交 | 实际成本、余额、修订 | `CURRENCY_INSUFFICIENT`、`ITEM_INSUFFICIENT` |
| `ExchangeResources` | 成本+奖励、规则 ID、`command_id` | 兑换规则合法 | 成本和产出同一事务 | 新余额/物品 | `EXCHANGE_LIMIT_REACHED`、容量错误 |
| `CreatePendingReward` | prepared、原因、`command_id` | 策略允许 | 槽5提交收据和完整批次 | pending ID | `PENDING_REWARD_LIMIT_REACHED` |
| `ClaimPendingReward` | pending ID、`command_id` | AVAILABLE、容量/上限足 | 复用父奖励的 owner 子收据并按18 Saga推进，全部确认后槽5标记 CLAIMED | 奖励摘要 | `PENDING_REWARD_NOT_FOUND`、`INVENTORY_FULL` |
| `ResolveUnknownReceipt` | receipt ID | 状态 UNKNOWN | 查询槽4/5修订和结果哈希 | COMMITTED/NOT_COMMITTED/仍UNKNOWN | `SAVE_UNAVAILABLE` |
| `ReverseReservation` | reservation ID、原因 | 未提交 | 幂等释放 | 释放摘要 | `TRANSACTION_ALREADY_COMMITTED` |

预览 token 绑定配置版本、成本/奖励哈希、槽4/5修订和用途；过期/不一致返回 `PREVIEW_STALE`。UI 传入的价格、概率或奖励列表只用于回显，服务必须从规则 ID 重算。

| 事件 | payload | 消费者 |
|---|---|---|

| `RewardGranted` | `source_type,source_ref,entries,result_hash,receipt_id,owner_child_receipt_hash` | 任务、结算 UI、统计；只在所有 owner 子步骤确认后发布 |
| `RewardDeferred` | `pending_id,source_ref,reason,receipt_id` | UI、引导 |

## 10. 存档 DTO、槽位与迁移

### 10.1 槽 4：余额权威

`EconomySaveDTO` 与背包/装备共享槽 4：

| 字段 | 形态 | 说明 |
|---|---|---|
| `currency_balances` | `currency_id -> integer` | 不保存显示格式 |
| `currency_account_revisions` | `currency_id -> integer` | 可合并为槽修订下的局部修订 |
| `economy_revision` | integer | 任一余额变化加 1 |

预留不应作为永久余额扣减。崩溃恢复需要的未决预留写槽 5；加载时按收据判定提交/释放。

### 10.2 槽 5：收据与待领

| 字段 | 形态 | 说明 |
|---|---|---|
| `reward_receipts` | `receipt_id -> 扁平摘要` | 关键一次性父收据永久可判定，含 owner 子收据状态摘要 |
| `pending_rewards` | `pending_id -> 版本化紧凑条目` | 完整可重建奖励，限制条目数和总量 |
| `source_occurrences` | `source_occurrence_id -> receipt_id/status` | 防同来源换命令键重复领 |
| `unknown_transactions` | `receipt_id -> 最后状态/修订` | 恢复入口 |

三层限制下，奖励条目使用版本化扁平编码或平行表；解析必须设置最大条目数（单批 V1 100）和字符串长度。待领数量 V1 上限 50 批，达到上限时阻止新的可选奖励来源；关键剧情奖励不得丢失，应阻止结算并要求先清理。

### 10.3 迁移

- 旧货币字段映射到稳定 `currency_id`；不存在明确映射则隔离并只读，不猜测。
- 从物品式铜钱迁移时以一次性迁移收据扣物品、增余额，重复运行不重复转换。
- 收据 Schema 升级保留 request/result hash；无法重建完整 UI 摘要仍必须能判断是否已提交。
- 调整货币上限不能截断旧余额；先支持旧余额只减不增，或提供明确补偿转换 ADR。

## 11. Y3 适配与 UI

### 11.1 Y3 适配

- 普通 PVE 掉落由同步 Lua 权威计算；Y3 特效、掉落动画和飘字只消费 `RewardGranted`。
- 周期来源只接受 17 `TrustedPeriodPort` 已确认的 `period_id`，10 不自行用 `ClockService` 计算日期键；普通掉落完全不依赖时间。只有审计记录确需绝对服务时间时才可调用 `ClockService.now`，且该值不得参与概率、种子或奖励数量。
- 平台高级货币的增加必须来自 21 系统核验端口；普通 `GrantPreparedReward` 遇到 `PREMIUM_PLATFORM` 返回权限错误。
- 云档适配器用统一槽4协调器写背包/装备实例/所有权/货币/槽4子收据；涉及槽2/3成长或槽5父收据时按18可恢复 Saga 提交，不宣称跨云槽原子回滚。
- 世界实体掉落在提交成功后才销毁；若采用自动拾取，动画开始不代表已获得。

### 11.2 UI

- HUD 余额订阅修订事件；变化动画显示实际 `delta`，不可自行推算。
- 战斗/任务结算显示“已领取”或“待领取”，待领取必须说明背包/上限原因和处理入口。
- 奖励预览标注固定、概率、首通、条件和可能数量范围；不把权重伪装成精确概率，若需显示概率由生成器精确换算。
- 消费确认显示每项当前→之后余额、物品缺口、配置版本对应价格；提交期间防重复。
- `UNKNOWN` 显示核对状态，不播放成功/失败结算；恢复后只播放一次可重入表现。
- 只读模式可看余额、来源/用途和待领列表，不能领取或消费。

## 12. 边界、失败与恢复

| 场景 | 必须行为 |
|---|---|
| 掉落表过滤后总权重 0 | 准备失败，战斗结算进入可诊断重试，不默认无掉落 |
| 奖励超过余额/物品上限 | 整批拒绝或完整待领，不截断 |
| 同收据同输入重试 | 返回原结果，不再抽取、不再扣发 |
| 同收据不同输入 | 安全错误并记录，禁止覆盖 |
| 槽4成功槽5响应超时 | 通过结果哈希和修订核对；不得再提交 |
| 槽5先记录 RESERVED 后崩溃 | 加载恢复，确认槽4未变再释放 |
| 配置热更发生在预览后 | 预览失效，重新展示；已 Prepared 且开始结算的战斗绑定原版本 |
| pending 满 50 | 阻止可选领取/新结算；不删除最旧关键奖励 |
| 客户端要求增付费货币 | `ECONOMY_SOURCE_NOT_AUTHORIZED` |
| PRNG 或种子缺失 | 随机奖励准备失败，不回退 `math.random` |

## 13. 数据生成与校验

必须拒绝：

- 货币重复、余额上限非法、来源/消耗白名单空缺、正式配置仍开放测试币来源。
- 奖励数量非正、随机范围倒置、目标 ID 断链、奖励包循环、嵌套超过允许层。
- 成长/解锁条目无法唯一路由到 01/04/02/世界 owner port，或缺少稳定 `entry_index`/子收据派生信息。
- `EQUIPMENT` 奖励不能在同一槽4 change set 中同时生成实例行、09所有权索引与经济子收据。
- 权重/总权重溢出、模式与 `weight/chance_bp` 字段混用、概率超 10000、唯一重抽无 `unique_key`。
- 缩放区间重叠或空洞、最坏数量溢出、补偿溢出互相循环。
- 一次性宝箱/任务没有可生成来源唯一键；关键奖励使用 `REJECT` 且可能被背包容量阻塞但无待领方案。
- 付费平台货币被普通任务、掉落、测试命令或可编辑源表直接产出。

生成报告必须输出：

- 每种货币的所有来源、所有消耗点、首章理论最小/最大净流量和无来源/无消耗警告。
- 每个掉落表的精确概率（可解析模式）、最小/最大价值包络、空掉落概率、固定种子快照。
- 一次性奖励的来源键策略、可能占用格数、待领策略和反向引用。
- 测试币/付费币权限扫描与正式发布阻断结果。

## 14. 测试矩阵

| 层级 | 用例 | 断言 |
|---|---|---|
| 单元 | 余额 0/恰好/不足/上限/溢出 | 整数边界无截断 |
| 单元 | 权重 1、no-drop、概率 0/10000、随机数量 | 固定种子结果精确 |

| 统计 | 大样本概率 | 仅检测偏差，不替代精确配置校验 |
| 契约 | 背包/装备/角色/武学/伙伴 Fake 成功与失败 | 槽4无半状态；跨 owner 子收据可恢复且只应用一次 |

## 15. 验收标准

- 同一掉落配置、上下文和种子产生完全一致的规范化奖励与哈希，不依赖表遍历或帧时间。
- 每个首章奖励来源拥有唯一 occurrence ID，重复结算、重进、断线均不会重复领取。
- 多货币、物品和装备创建在槽4不产生半状态；成长奖励通过唯一 owner port 与子收据可恢复提交，任一故障点重进后只得到一个最终业务结果。
- 背包满/余额满时关键奖励完整进入待领，保存重进后内容和来源不变。
- 所有货币拥有来源/消耗白名单，普通 Lua 路径无法增发平台高级货币。
- 未知事务能够凭收据、修订和结果哈希恢复为明确状态，UI 只展示一次结果。
- 配置概率、范围、引用、循环、包络和正式币权限校验全部通过。
- 无引擎、Fake 契约、故障注入、Y3 集成和首章经济闭环测试通过，P0/P1 为零。
