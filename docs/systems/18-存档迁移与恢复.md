# 《雾州侠行》存档、迁移与恢复系统规格

> 状态：系统规划冻结候选稿；Foundation V1 的 SaveEnvelope、Manifest/section 注册与 SaveStore 端口契约已落地，系统 01 的角色存档 Codec、仓储端口与 Fake 仅完成离线边界
>
> SaveCoordinator、迁移流程及真实 Y3 云存档适配尚未实现和验证；离线 Fake 通过只证明目标端口契约，不代表真实平台故障分类或能力可用，也不得据此启用生产存档。

## 1. 目标与非目标

### 1.1 目标

- 为槽 1–5、公开槽 100、排行槽 101 和平台整数槽建立统一加载、校验、迁移、写入、冲突与恢复流程。
- 任何下载失败、结果未知、版本不兼容或修订冲突都不得用默认新档覆盖已有云档。
- 迁移必须按版本逐级、纯函数化、幂等并在内存校验通过后才覆盖云端。
- 对关键奖励、交易、擂台积分和权益建立业务收据及恢复日志，避免只依赖一次云写成功。
- 将“确认为新玩家”和“暂时读不到旧档”严格区分。
- 以槽 1 Manifest 作为私人检查点唯一提交标记，并在加载时识别未被 Manifest 引用的孤儿槽写入。
- 以 SectionOwnerRegistry 约束每段持久化数据只有一个写入 owner；业务系统只提交 section 变更，不直接覆盖整槽。

### 1.2 非目标

- 不自建外部云存储、跨平台账号合并、玩家自行编辑存档或任意版本降级。
- 校验和仅用于发现损坏，不提供密码学防篡改保证。
- 首版不承诺自动合并两个设备的分叉进度；无法安全判断时进入冲突恢复。
- 本系统不重算具体战斗、任务、背包或权益规则，只调用各系统验证器和迁移器。

## 4. 领域模型

### 4.1 SaveEnvelope

| 字段 | 类型 | 约束 |
|---|---|---|
| schema_version | integer | 槽 DTO 结构版本，至少 1 |
| revision | integer | 每次成功权威写入递增 1 |
| checkpoint_id | string | 产生该版本的私人检查点 ID；公开派生槽使用独立发布 ID |
| content_version | string | 写入时内容兼容版本 |
| owner_fingerprint | string | `owner_v1_` + SHA-256 小写十六进制；输入为认证存档作用域，不保存原始 AID |
| payload_checksum | string | 规范序列化后的损坏检测值 |
| written_at | integer? | 可信服务器时间；不可用时为空 |
| payload | table | 满足三层嵌套限制的槽 DTO |

owner_fingerprint 用于防止误串档，不作为安全签名。校验和不包含 written_at，算法和版本必须显式记录或由 schema_version 固定。

### 4.2 SaveManifest（槽 1 `payload.manifest` section）

槽 1 的 payload 是 section 容器，固定包含 `manifest`、`player_profile`、`settings_profile`；SaveManifest 只指其中的 `manifest`。路径均相对 payload，三个 section 由 SaveCoordinator 合并，任何 owner 不得整槽覆盖。

`manifest` 与 `player_profile` 的唯一 owner 是 18，`settings_profile` 的唯一 owner 是 24。`player_profile` 仅含建档内部作用域和创建元数据，不得吸收角色、任务、世界、周期或平台身份原值。

槽根 `SaveEnvelope` 不计入平台三层限制：`payload → section → 行表/标量集合` 已经用完三层，因此行表和最内集合只能包含标量。所有系统的 SaveCodec 必须先规范化到该形状；需要更深结构时拆成同 section 下的独立行并用稳定 ID 关联，禁止把任意领域对象原样塞入存档。

| 字段 | 类型 | 说明 |
|---|---|---|
| save_format_version | integer | 全局兼容版本 |
| created_revision | integer | 新档创建修订 |
| slot_revision_entries | flat map | 槽 2–5 固定使用 `slot_<id>_schema_version/revision/checkpoint_id/payload_checksum`；禁止数组再嵌行表 |
| checkpoint_id | string | 最近完整私人检查点 ID，也是槽 1 最后提交的唯一 commit marker |
| last_save_server_time | integer? | 最近一次保存观察到的服务器时间，仅用于诊断与冲突摘要；不得用于日刷新、赛季或运营条件 |
| save_seed | integer | `1..2147483646`；确定性系统根种子，与 06 `DeriveSeedV1.root_seed` 同型 |
| feature_flag_snapshot | list | 影响存档读取的已启用功能 |
| recovery_epoch | integer | 每次人工/自动恢复递增 |

### 4.3 PendingTransaction

| 字段 | 类型 | 说明 |
|---|---|---|
| transaction_id | string | SaveCoordinator 向业务仓储提供的外部原子事务 RuntimeId component；`1..64` 字节，首字符必须是 ASCII 字母或数字，其余字符才可为 ASCII 字母、数字、`_`、`.`、`-`，不得包含 `:` |
| transaction_type | string | REWARD、CRAFT、ARENA_SCORE、ENTITLEMENT 等 |
| state | enum | 正常 PREPARING→PREPARED→APPLYING→COMMITTED；异常 RECOVERY_REQUIRED、COMPENSATED、FAILED_BEFORE_APPLY |
| ordered_steps | list | 确定顺序的 step_id、owner section、affected_slot、expected_revision 和目标结果摘要 |
| completed_step_ids | list | 已确认完成的有序 step_id；只追加、不回退 |
| result_hashes | list | 每个已完成 step_id 的规范结果哈希，用于重放对账 |
| target_checkpoint_id | string? | 涉及私人多槽变更时固定的目标检查点 ID |
| outcome_digest | string | 全部 ordered_steps 预期最终结果摘要，不含完整敏感数据 |
| retry_count | integer | 非负 |
| created_at、updated_at | integer? | 可信时间 |

`transaction_id`、业务 `receipt_id` 与传输 `context.idempotency_key` 是三个不同命名空间的身份，禁止直接复用字段值。业务收据标识一次业务事实；`transaction_id` 标识 SaveCoordinator 编排的原子恢复单元；传输幂等键只绑定一次端口请求。系统 01 只能接收并校验 SaveCoordinator 提供的 `transaction_id`，不得从 `receipt_id`、命令摘要、预期结果摘要或传输幂等键派生它，也拒绝把这些值原样复用为 `transaction_id`。传输幂等键可以对业务事实作确定性绑定，但必须使用独立命名空间，并继续满足 RequestContext 的长度和字符约束。

系统 01 的所有业务/创建/奖励收据与上述两种技术身份，还必须和命令、结果、奖励计划及奖励结果的摘要原值分离。此规则既适用于当前请求 tuple，也适用于 Fake 和后续 SaveCoordinator 的已接纳历史；NOT_FOUND 查询本身不取得任何新身份所有权。

`SaveCriticalTransaction` 的调用方必须把 SaveCoordinator 为该原子单元提供并冻结的 `transaction_id` 随 change set 原样提交；系统 18/SaveCoordinator 负责校验该组件并拥有复合 `step_id` 的构造与排序权。任何 owning system 都不得另造同义事务 ID 或自行拼接恢复步骤身份。

### 4.4 LoadReport

记录每槽 fetch_status、schema_version、revision、checksum_status、migration_path、validation_errors 和 recovery_action。该报告仅在会话和诊断日志存在，不包含完整存档内容。

## 5. 配置字段

### 5.1 SlotDefinition

| 字段 | 说明 |
|---|---|
| slot_id | 平台槽编号 |
| owner_system | 权威系统 |
| required_for_start | 是否必须加载后才能游玩 |
| current_schema_version | 当前版本 |
| min_readable_version | 最低可读版本 |
| max_payload_budget | 验证后的安全容量 |
| write_policy | CHECKPOINT、CRITICAL、DERIVED |
| public | 是否公开档案 |
| validator_id、codec_id | 对应实现契约 |

### 5.2 SectionOwnerDefinition

| 字段 | 说明 |
|---|---|
| section_key | 全局稳定键，例如 arena_private、tutorial_progress |
| slot_id | section 所在槽位 |
| owner_system | 唯一允许生成该 section 变更集的系统 |
| schema_version | section 自身结构版本 |
| write_policy | CHECKPOINT、CRITICAL、DERIVED |
| validator_id、codec_id | section 合并前后的验证与编码契约 |

同一 section_key 和同一 DTO 路径都只能有一个 owner。业务系统不得读取整槽后回写他人 section；SaveCoordinator 依据 registry 合并各 section，并负责整槽 revision、checksum 与 checkpoint_id。

轻功落地固定注册为：槽 2 `world_position` 的 owner 是 12，包含 `last_landing_receipt_id`；槽 5 `save_recovery_transactions` 的 owner 是 18，只保存检查点意图/结果并引用该 ID。`landing_receipt_id` 本身不是 section，也不是 18 新建的第二份业务收据；它由 12 对 canonical tuple `{player_save_scope, traversal_session_id, active_segment_command_id, segment_sequence, target_cell_id, rules_version}` 做规范化哈希生成，26 只提供输入，18 只引用结果，三者均禁止改写 tuple 或另造同义 ID。

### 5.3 MigrationDefinition

包含 slot_id、from_version、to_version、migration_id、输入校验器、输出校验器、是否需要跨槽上下文和兼容内容版本范围。只允许相邻版本迁移；跨版本必须串联。

## 6. 运行时状态

### 6.1 SaveSession

- state：UNINITIALIZED、LOADING、MIGRATING、RECONCILING、READY、SAVING、READ_ONLY、RECOVERY_REQUIRED、CONFLICT。
- loaded_envelopes：槽 ID 到已验证信封。
- base_revisions：本会话加载时的云端修订。
- dirty_sections：section_key、owner_system、变更摘要和原因。
- target_checkpoint_id：本轮冻结后不可变的目标检查点 ID。
- committed_manifest_checkpoint：槽 1 已确认的唯一完整检查点 ID。
- pending_transactions：待确认事务。
- write_queue：按优先级和槽 ID 稳定排序。
- last_load_report：诊断摘要。
- session_instance_id：本次进程唯一 ID。
- exit_flush_requested：退出前是否请求写入。

同一玩家同一进程只允许一个 SaveCoordinator。所有表型槽与公开槽写入必须经它串行化；UI 和业务系统不得直接调用 SaveStore，也不得绕过 SectionOwnerRegistry。

## 7. 加载、迁移与写入状态机

### 7.1 加载

顺序：

1. FETCH_PROFILE：读取槽 1 并明确区分 FOUND、CONFIRMED_ABSENT、TEMPORARY_FAILURE、PERMISSION_ERROR。
2. CONFIRM_NEW：仅槽 1 被平台明确确认为不存在，且新档创建锁成功时可建新档。
3. FETCH_REQUIRED：按 manifest 和 SlotDefinition 读取槽 2–5及所需整数权益。
4. VERIFY：校验 owner、版本、校验和、修订、结构，并逐项比对槽 1 的 slot_revision_entries。
5. MIGRATE_IN_MEMORY：逐级迁移副本，原云档尚未覆盖。
6. CROSS_VALIDATE：检查角色、物品、任务、权益等跨槽引用。
7. DETECT_ORPHAN_WRITES：若槽 2–5 的 revision、checkpoint_id 或 checksum 未被当前 Manifest 向量引用，标记 ORPHAN_SLOT_WRITE；不得自动采用或覆盖。
8. RECONCILE：按 pending transaction 的 target_checkpoint_id 与目标 revision 向量前向恢复，并处理权益差异。
9. NORMALIZE_TRANSIENT_WORLD：不得从存档恢复 `TraversalSession`、候选格、movement token、空中轨迹或水上剩余距离。`RequestTraversal` 的接受与表现阶段只在内存存在，进程中断后直接作废；只有 12 已生成并进入安全落点提交的 `landing_receipt_id`，才可用槽 2 `world_position.last_landing_receipt_id` 与槽 5 `save_recovery_transactions` 的引用证据前向恢复。证据不足时由 26 编排、12 解析并回到 `last_safe_marker_id`，禁止采用 Y3 单位残留坐标。
10. READY：全部必要槽可用；或 READ_ONLY：数据可读但无法安全写。

任何 TEMPORARY_FAILURE 都不能进入 CONFIRM_NEW。

### 7.2 迁移

- 每个迁移器接收旧 DTO 和显式迁移上下文，输出新 DTO 与 MigrationReport。
- 重复执行同一迁移必须产生相同规范化结果。
- 迁移不调用 Y3、系统时间、随机数、UI 或网络。
- 迁移完成后运行新版本单槽和跨槽验证。
- 只有全部必要槽迁移成功才进入保存候选；任何失败保留原云档并进入 RECOVERY_REQUIRED。
- 当前版本至少保留上一已发布 schema 的读取与迁移路径。
- 旧槽 1 若含 last_trusted_server_time，仅原值迁移为 last_save_server_time 并标记诊断用途；不得把它注入 17 的 TrustedPeriod/Cycle 状态。

### 7.3 写入

写入流程：

DIRTY_SECTIONS → PREPARING_CHECKPOINT → VERIFY_BASE_REVISION → WRITING_DATA_SLOTS → VERIFY_DATA_SLOTS → WRITING_MANIFEST_LAST → VERIFY_MANIFEST → CLEAN。

1. 冻结 section 变更集、完整目标 revision 向量和唯一 target checkpoint_id；此后重试不得换 ID。
2. SaveCoordinator 按 SectionOwnerRegistry 将变更合并到槽 DTO，验证非 owner 路径没有变化。
3. 先写并回读验证所有脏的私人数据槽 2–5；每个新信封写入同一 checkpoint_id、目标 revision 和 checksum。
4. 只有所有必需数据槽都确认成功后，才最后写槽 1 Manifest。Manifest 的 checkpoint_id 与完整 slot_revision_entries 是私人检查点唯一 commit marker。
5. 回读槽 1 并确认 revision、checkpoint_id 与向量后才能发布 SaveCheckpointCommitted 和清理脏 section。

- 目标 revision = 基础 revision + 1；未变化槽沿用已提交 revision/checkpoint/checksum 并进入 Manifest 完整向量。
- 若平台支持条件写入，必须以 expected revision 提交；若不支持，写前重新读取修订，无法排除并发覆盖时进入冲突恢复，不声称强一致。
- 写入返回超时或未知时不得立即换 revision 或 checkpoint_id 重写；先查询远端 revision、checkpoint_id 与 checksum。
- 槽 1 写入前崩溃会留下未被旧 Manifest 引用的孤儿候选槽。加载时只可依据已保存意图和完全匹配的目标向量继续前向提交；证据不足则进入 RECOVERY_REQUIRED/READ_ONLY，绝不自动采用孤儿数据。
- 跨槽写入不是 ACID 事务，不承诺原子回滚。恢复策略是幂等查询、收据对账和前向完成；不得声称“失败后回滚全部槽”。
- 关键事务先保存可恢复意图，再提交权威 section/checkpoint，再将事务标记 COMMITTED。
- 公共擂台槽 100 和排行榜 101 是派生发布，不参与私人进度完整检查点，也不受槽 1 commit marker 覆盖。
- 轻功选点、起跳、空中和水上移动过程不触发保存裸坐标；只有 `TraversalLanded` 或 `WaterWalkExited` 对应的安全地面提交完成后，12 才登记 `world_position` 为脏，18 登记引用同一 receipt 的恢复事务并请求关键检查点。若进程在表现途中退出，重进只能从最近已提交安全 marker 开始。

### 7.4 SaveStore V1 写入绑定

SaveCoordinator 调用 22 的 SaveStore 时必须遵守以下冻结契约；这些约束是恢复证据的一部分，不是适配器可选元数据：

- `stage_slot` 输入固定为 `player_ref、slot_id、expected_revision、checkpoint_id、payload_checksum、dto`。`dto` 必须通过 SaveEnvelope 校验，且 `dto.revision = expected_revision + 1`，其 `checkpoint_id/payload_checksum` 必须与顶层字段完全相等。
- `stage_slot` 接纳后只接受 `{player_ref, slot_id, revision, checkpoint_id, payload_checksum, request_key}` 成功结果；前五项必须回显请求及信封内容，`request_key` 必须等于本次 `context.idempotency_key`。
- `commit` 输入的 `commit_entries` 必须按 `slot_id` 严格升序且唯一；每行固定为 `{slot_id, target_revision, checkpoint_id, payload_checksum}`。任何重试沿用原清单和业务幂等键。
- `commit` 成功结果固定为 `{player_ref, status, slot_results, request_key}`。CONFIRMED 行必须逐项回显目标 revision/checkpoint/checksum；无法确定的行只能是 `UNKNOWN + PLATFORM_RESULT_UNKNOWN`，不得把 `PLATFORM_UNAVAILABLE` 或 `PLATFORM_RATE_LIMITED` 藏在一个“已完成”的失败行里。
- `load_slot` 的 `{player_ref, slot_id, dto, revision, checkpoint_id, payload_checksum}` 必须内部一致；回读不一致按非法平台结果处理，不能进入 Manifest 比对。
- `upload` 与整数 CAS 的已确认写结果同样必须带与 `context.idempotency_key` 相等的 `request_key`。结果缺失、错绑、超预算或 malformed 时统一进入 `PLATFORM_RESULT_UNKNOWN`，恢复动作为 `QUERY_OR_RECONCILE`，禁止盲重写。
- `query_integer_request` 必须同时携带 `player_ref、slot_id、original_idempotency_key`，所有返回分支都回显这三项；CONFIRMED 分支才额外携带 value/revision。

端口同步 admission 失败代表“未接纳”，保证不触发 completion；只有精确的 `{ok=true,value={accepted=true}}` 才进入异步等待。接纳后的 completion 必须非内联、最多一次。该区别决定恢复流程能否安全修正请求后重试，禁止把 admission error 与结果未知混写。

## 8. 应用用例

| 用例 | 输入 | 前置 | 事务/输出 | 主要错误 | 幂等 |
|---|---|---|---|---|---|
| LoadGameSave | player_context | 无活动会话 | 返回 SaveLoadResult 与模式 | SAVE_DOWNLOAD_FAILED、SAVE_CORRUPT | session_instance_id |
| CreateNewSave | command_id | 槽 1 CONFIRMED_ABSENT | 创建槽 1–5 初始信封 | SAVE_EXISTENCE_UNKNOWN | command_id |
| SaveCheckpoint | command_id、reason、dirty_sections | READY | 返回 checkpoint_id、完整 revision/checksum 向量；槽 1 最后提交 | SAVE_REVISION_CONFLICT、SAVE_RESULT_UNKNOWN、ORPHAN_SLOT_WRITE | command_id |
| SaveCriticalTransaction | 外部原子 transaction_id、change_set | READY 且可写 | SaveCoordinator 校验事务组件、构造有序 step_id，再执行意图、应用、校验、提交 | TRANSACTION_RECOVERY_REQUIRED | transaction_id |
| QueryCommandOutcome | owning system 冻结的原请求证明 tuple；系统 01 的完整字段见下文 | 已加载收据且调用方持有原请求证明 | 按 owning system 的端口契约校验并返回状态；不得仅凭事务 ID 采信结果 | RECEIPT_UNAVAILABLE、PLATFORM_RESULT_UNKNOWN | 只读 |
| RetryLoad | retry_token | READ_ONLY 或加载失败 | 重新取失败槽，不清空内存 | SAVE_RETRY_EXHAUSTED | retry_token |
| RecoverPendingTransactions | recovery_id | RECONCILING | 对账并提交或补偿 | RECOVERY_AMBIGUOUS | transaction_id |
| ResolveSaveConflict | command_id、chosen_revision | CONFLICT、玩家确认或确定策略 | 保留选定分支并递增 recovery_epoch | CONFLICT_CHOICE_STALE | command_id |
| FlushBeforeExit | command_id、deadline | READY 且有脏槽 | 尽力保存并报告未确认项 | SAVE_FLUSH_TIMEOUT | command_id |

删除或重置进度必须是独立高风险用例，要求明确二次确认和平台存在性复核；任何恢复流程不得自动触发。

当前已冻结该强证明查询契约的范围是系统 01 `query_character_transaction`，不得把它未经版本化设计直接扩写成“所有事务查询”的统一字段契约。该请求的完整 tuple 为 `player_save_scope`、`original_request_key`、`receipt_id`、`transaction_id`、`operation_type`、`command_digest`、`expected_result_digest`、`expected_character_save_revision`、原始 `command`；端口必须重新校验命令摘要及全部身份。非 COMMITTED 状态只能回显基础身份/证明字段，不得夹带结果或修订；COMMITTED 才能增加角色/收据修订、`result_digest` 和类型化结果，且已存结果摘要必须同时匹配 `expected_result_digest` 与规范结果摘要。其他 owning system 必须各自冻结并版本化自己的查询证明，不得默认照搬或弱化这一 tuple。

## 10. 存档 DTO 与槽位所有权

| 槽 | 权威内容 | 备注 |
|---:|---|---|
| 1 | Manifest、玩家档案、save_seed、兼容功能标记 | 加载入口；私人检查点最后写入的 commit marker |
| 2 | 世界、任务、门派、对话、一次性探索状态 | 表型信封；只保存已提交 marker 与 `last_safe_marker_id`，不保存轻功选点/空中/水上临时态 |
| 3 | 角色、伙伴、武学、经脉、阵型 | 表型信封 |
| 4 | 背包、装备、非付费货币、制作和 NPC 商店收据 | 表型信封 |
| 5 | 引导、周期内容、恢复日志、幂等收据、擂台私人状态 | 表型信封 |
| 100 | 公开擂台快照 | 不可信输入、可重建派生数据 |
| 101 | 排行榜编码整数 | 由槽 5 赛季积分派生 |
| 200–299 | 平台付费角色/武学权益单调整数 | 平台权威；私人槽 5 仅由 21 保存 last_observed count 与唯一 delivery_cursor，不保存第二个权威计数 |
| 300–319 | 平台抽取凭证、抽数、最高稀有度序号、兑换 earned/spent 等单调 totals | 是否足以承载状态须在卡池门禁验证；不保存可递减余额 |

逻辑模型超过三层时必须拆成扁平 entry 列表，例如角色、武学、装备关系分别保存 owner_id 与 content_id，不按多层对象嵌套。表中“权威内容”描述数据归属，不授予系统整槽写权；精确写权以 SectionOwnerRegistry 为准。

## 11. Y3 适配与恢复 UI

### 11.1 SaveStore 适配契约

必须将平台结果映射为：

- FOUND
- CONFIRMED_ABSENT
- TEMPORARY_FAILURE
- PERMISSION_DENIED
- QUOTA_EXCEEDED
- RATE_LIMITED
- RESULT_UNKNOWN
- UNSUPPORTED

不得把空表、超时或解析失败映射成 CONFIRMED_ABSENT。

SaveStore 的平台错误到本系统状态采用固定映射：

| 端口结果 | 本系统状态/错误 | 说明 |
|---|---|---|
| 明确 SAVE_NOT_FOUND | CONFIRMED_ABSENT | 仅平台明确证明该槽从未存在时成立 |
| PLATFORM_UNAVAILABLE | TEMPORARY_FAILURE / SAVE_DOWNLOAD_FAILED | 可重试，绝不创建新档 |
| PLATFORM_RESULT_UNKNOWN | RESULT_UNKNOWN / SAVE_RESULT_UNKNOWN | 写后先按目标 revision 与 checksum 查询 |
| SAVE_REVISION_CONFLICT | CONFLICT / SAVE_REVISION_CONFLICT | 重新读取并进入冲突流程 |
| PLATFORM_PERMISSION_DENIED | PERMISSION_DENIED | 禁止继续写入 |
| PLATFORM_QUOTA_EXCEEDED | QUOTA_EXCEEDED | 不截断权威内容 |

上表是生产适配器必须达到的目标归一化契约，不表示这些错误名、接纳时点或返回字段已经在真实 Y3 平台观察到。真实 Y3 的槽不存在证明、超时、频控、配额、权限、条件修订以及“写已执行但响应丢失”路径都必须逐项故障注入并形成验证报告；完成前只能使用 Fake，生产 SaveStore 适配保持关闭。

槽 1 的 last_save_server_time 不进入 ClockService 的可信时间缓存，也不能被周期系统读取。日刷新权威时间只归 17 的 TrustedPeriod/Cycle 服务。

### 11.2 UI

- 首次加载显示必要槽进度，不显示内部敏感值。
- READ_ONLY 页面允许继续查看已有进度、重试和退出；所有会改变进度的入口禁用。
- RECOVERY_REQUIRED 显示错误编号、可导出的诊断摘要和安全选项，不展示“开始新游戏”捷径。
- CONFLICT 页面展示服务器时间、章节、等级、修订等摘要；选择前再次读取远端。
- 保存中、成功、延迟、结果未知和失败使用不同提示。
- 退出前保存超时须明确告知仍有未确认数据，不能伪报成功。

## 12. 边界与失败

- 槽 1 成功而必要槽缺失：若 manifest 声明该槽存在，则视为损坏或部分档，不自动补默认。
- 校验和失败：保留原始下载副本于内存诊断范围，进入 RECOVERY_REQUIRED。
- 内容 ID 下线：由 owning system 的兼容映射处理；不存在映射时不得静默删除有价值内容。
- 云端 revision 高于本会话 base revision：停止写入并进入冲突。
- 写成功响应丢失：查询 revision 与 checksum；一致则确认成功，不一致则保持 UNKNOWN。
- 多槽事务部分成功：旧 Manifest 仍是提交边界；根据 PendingTransaction 的 target_checkpoint_id、ordered_steps、completed_step_ids、result_hashes 与目标 revision/checksum 向量前向对账。无法证明结果时禁止补发、禁止自动采用孤儿槽，也不承诺跨槽回滚。
- 容量超限：先拒绝写入并进入可诊断状态，禁止截断角色、物品或权益；仅允许按已冻结策略裁剪过期日志。
- 玩家身份不匹配：立即停止加载，不能提供覆盖选项。

## 13. 生成与静态校验

- 每个表型槽恰有一个 current_schema_version 和连续迁移链。
- MigrationDefinition 不得有分叉、缺口或循环。
- 所有 DTO 生成样本满足三层嵌套和容量预算。
- 跨槽引用拥有明确 owner；同一权威字段不得在两槽各存一份可写值。
- 每个持久化 section 必须注册且恰有一个 owner；同槽路径不得重叠，非 owner 生成写入在构建期失败。
- 收据裁剪策略不得移除仍可能重试或审计期内的事务。
- 默认新档通过全部当前验证器。
- 上一发布版本黄金档均存在并能迁移。
- 公开槽和平台整数槽不得被私人存档迁移器覆盖。

## 14. 测试矩阵

| 类别 | 必测场景 |
|---|---|
| 加载 | 全新账号、完整旧档、单槽超时、权限失败、明确不存在 |
| 迁移 | 每个相邻版本、重复迁移、跨槽引用、迁移中断 |

| 写入 | 正常、限流、配额、响应丢失、远端 revision 冲突、Manifest 最后提交 |

| 事务 | 多槽部分成功、奖励已发未记收据、恢复重复执行、禁止假设跨槽回滚 |
| 所有权 | section 未注册、重复 owner、路径重叠、非 owner 写入被拒绝 |

FakeSaveStore 必须支持逐调用故障注入、延迟、结果未知、陈旧读和修订冲突。

## 15. 验收标准

- 网络失败、解析失败或超时永远不会触发新档覆盖。
- 当前版本及上一发布版本档案均可加载；迁移重复执行结果一致。
- 关键事务在任一保存失败点重进后只会得到一次最终结果。
- 所有写入均有目标修订、校验和与结构化日志。
- 只有槽 1 最后写入并回读确认后检查点才完成；任一孤儿槽都能被检测且不会被静默采用。
- 所有持久化写入均能追溯到唯一 section owner，并由 SaveCoordinator 合并整槽。
- 只读模式阻止奖励、交易、阵容变化、擂台计分和卡池操作。
- 槽 100、101 写入失败不会损坏槽 1–5 的私人进度。
- 任意轻功通行阶段退出重进后，角色只能位于已提交目标安全 marker 或此前 `last_safe_marker_id`；不会停在空中/水面、复制探索进度或永久锁住输入。
- 最大压力样本不超过经 Y3 实测确认的安全容量。

## 17. 待决项

- Y3 SaveStore 是否提供明确“槽不存在”、条件修订写和写后读取能力。
- 各槽实测容量、频率限制、表嵌套计数方式及最大整数范围。
- 多设备冲突是否提供平台会话锁；没有时允许玩家选择的最小安全摘要。
- 收据的安全保留数量与裁剪规则。
- 是否具备平台版本历史或恢复快照；当前规格不假设存在。
- 退出事件是否保证足够时间完成云写；关键节点仍必须提前保存。
