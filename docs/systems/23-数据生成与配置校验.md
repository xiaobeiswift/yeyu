# 数据生成与配置校验系统工程规格

> 状态：待评审
>
> 遵循：[通用工程约定](./00-通用工程约定.md)

## 1. 目标与非目标

本系统建立“Excel 源表 → Schema 校验 → 跨表校验 → 只读 Lua 配置/Y3 物编映射 → 测试 → 发布清单”的确定性内容管线。

目标：策划可批量维护内容；所有配置错误在进入游戏前暴露；同一输入生成字节级稳定产物；生成物可追溯到源表版本；任务可达性、掉落概率、武学引用、轻功通行可达性和存档兼容可自动检查。

非目标：不在运行时解析 Excel；不允许手改生成 Lua；不通过生成器改变玩家存档；不让数字物编 Key 成为领域 ID。

## 2. 依赖与消费者

所有系统配置都依赖本管线。输入来自 `design/data-source`，输出到 `wzx/config/generated` 与 `wzx/adapters/y3/mappings`。测试系统消费生成报告、内容清单和快照指纹。

## 4. 配置领域模型与通用字段类型

| 类型 | 规则 |
|---|---|
| `StableId` | ASCII 小写、前缀合法、全局或类型内唯一 |
| `LocalizedKey` | 必须存在中文条目，不直接放长文本 |
| `Int` | 声明最小/最大值和是否允许 0 |
| `Fixed` | 声明精度与取整；权威数值应尽量转整数 |
| `Enum` | 只接受 Schema 枚举，不接受自由拼写 |
| `Ref<T>` | 指向指定表且目标不能 deprecated |
| `RefList<T>` | 有序列表，生成时保持明确顺序 |
| `ProbabilityWeight` | 非负整数权重；池总权重大于 0 |
| `ConditionExpr` | 只允许白名单操作符与已注册变量 |
| `RewardList` | 引用合法奖励项，数量为正整数 |
| `VersionRange` | 明确首次引入、弃用和规则版本 |

空单元格、空字符串、0 和 false 必须有不同语义；每个字段声明默认值，禁止读取器自行猜测。

### 4.1 轻功通行跨系统生成 Schema

23 负责统一生成和校验，不因此取得领域所有权。下表字段直接复用 04/12/26 的 canonical 模型；Y3 区域句柄、运行时坐标对象和物编数字 Key 只能进入适配映射：

| Schema | Owner | 主键与 canonical 字段 | 生成约束 |
|---|---:|---|---|
| `LightnessTraversalProfileDefinition` | 04 | `profile_id,source_martial_id,rules_version,level_row_ids,default_presentation_profile_id,deprecated` | `profile_id` 使用 `traversal_profile_`；轻功反向引用唯一；恰有 1–10 重 |
| `LightnessTraversalLevelRow` | 04 | `profile_id,level,capability_specs,range_query_radius_cells,presentation_profile_override_id?` | capability spec 字段完全使用 04/26 契约；能力固定顺序且不无说明倒退 |
| `TraversalGrid` | 12 | `grid_id,area_id,cell_size_cm,origin_mapping_id,layer_ids,bake_version,spatial_revision` | 格坐标转换确定；地图源变化提升 bake_version、重新烘焙并生成新空间修订 |
| `TraversalCell` | 12 | `cell_id,grid_id,area_id,location_id?,grid_x,grid_y,layer_id,world_anchor_cm,height_level,surface_type,base_walkable,blocking_flags,clearance_class,landing_safety,safe_landing_marker_id?,region_ids,reveal_policy,region_revision` | `surface_type=GROUND/WATER/HAZARD/VOID`；阻挡只放 flags；SAFE_GROUND 必有安全 marker |
| `TraversalLink` | 12 | `link_id,from_cell_id,to_cell_id,direction,link_type,horizontal_cost_cells,rise_levels,drop_levels,required_clearance,condition_set_id?,landing_marker_id?,source_type,link_revision` | 普通/跳跃边可烘焙，特殊边可手工覆盖；authoring 的 ADD/REPLACE/BLOCK 必须规范化成唯一发布边或屏蔽记录 |
| `TraversalRuleDefinition` | 26 | `rule_id,applies_to_link_types,required_capability_any,required_capability_all,allowed_from_surfaces,allowed_to_surfaces,distance_budget_policy,height_policy,landing_policy,condition_policy` | `distance_budget_policy` 仅 `JUMP_DUAL_LIMIT/WATER_SESSION_COST`；规则 ID 使用 `traversal_rule_`；能力只取统一四枚举；不能复制地图坐标 |
| `WaterSurfaceZone` | 26 | `water_zone_id,grid_id,region_id,cell_ids,entry_link_ids,exit_link_ids,safe_shore_marker_ids,rule_id,availability_condition_id?,route_role` | 所含格均为 WATER；一入一出；每个可停留水格在配置预算内可达安全岸点 |

辅助注册表只保留 19/Y3 拥有的 `TraversalPresentationProfile` 与 `LightnessTargetOverlayDefinition`，前缀分别为 `traversal_presentation_`、`traversal_overlay_`；不另造与 Link 路径重复的 `TraversalPathProfile`。所有地理 ID 删除时保留墓碑，不能复用旧 ID 表示不同位置。

烘焙器依据格坐标、表面、高度级、净空和阻挡生成普通 `GROUND_ADJACENT`，并在项目最大轻功半径内生成安全的 `JUMP_DIRECT` 格对；策划表只对跨沟、高差、单向、特殊水路和剧情边做 ADD/REPLACE/BLOCK 覆盖。输出同时包含规范化格表、普通邻接/直跃表、手工覆盖表和按 Profile 档位生成的静态可达索引。运行时动态阻挡、昼夜/任务条件和角色当前能力仍由 26 在打开选点及确认时重校验，预烘焙结果不是最终授权。

运行时候选快照必须携带来源向量 `{spatial_revision, world_revision, source_loadout_revision, source_progress_revision, profile_hash, rules_version}`：前两项来自 12，后四项原样来自 04 的当前 LightnessTraversalProfile。23 校验生成 DTO 与 RequestTraversal Schema 含完整向量；任一分量变化都使旧候选过期，不能把地图 `bake_version` 混同为玩家世界状态修订，也不能把两个 Profile 来源修订折叠成未定义的单一 revision。

## 5. 源表规范

- 第一行为机器字段名，第二行为类型，第三行为策划说明，数据从固定行开始。
- 合并单元格只允许用于纯说明页，数据页禁止。
- 列删除属于破坏性 Schema 变更，必须提升 Schema 版本并提供迁移说明。
- 稳定 ID 单元格禁止公式；数值公式若允许，生成时保存求值结果并报告公式来源。
- 列表使用独立子表或明确分隔规范，不在单元格内嵌 Lua/JSON 代码。
- 文本内容使用本地化 Key；对话正文可有专用文本表，但仍需稳定行 ID。
- 每张表声明 owner、schema_version、primary_key 和排序键。

## 6. 生成流水线状态机

`discovered → parsed → normalized → schema_validated → references_validated → semantics_validated → emitted → tested → publishable`。

任一 error 立即阻止生成产物进入发布目录。warning 可以生成但必须列入报告；发布候选不允许存在未豁免 warning。豁免包含规则 ID、理由、责任系统和失效条件，不能用全局“忽略全部”。

为避免失败时留下半套产物，所有输出先写入临时生成目录，全部校验与测试通过后再以清单为单位替换发布目录。

## 7. 校验层级

### 7.1 结构校验

- 工作表、列、字段类型和主键存在。
- 数字、布尔、枚举、列表可正确解析。
- 必填值、范围、字符串长度和默认值合法。

### 7.2 引用校验

- 所有 `Ref` 目标存在且类型正确。
- 武学招式引用的效果、动画标签和消耗存在。
- 装备词条、掉落项、商店商品和奖励项存在。
- 任务前置、目标、对话、地区和遭遇引用存在。
- Profile Definition/LevelRow 引用的轻功、能力枚举和表现 profile 存在；TraversalGrid 的地区/bake_version 存在；TraversalCell 的网格、安全 marker、region 和揭示策略存在；TraversalLink 的端点、marker 及条件引用存在；TraversalRule 与 WaterSurfaceZone 的规则、格、入/出 Link 和安全岸点存在。
- Y3 映射覆盖所有需要表现的领域 ID。

### 7.3 语义校验

- 概率池无负权重、空池或非法保底目标。
- 任务前置图无意外环；从新档起点可达所有必做主线终点。
- 对话选择不存在无出口节点；跳转不会形成未声明无限循环。
- 装备等级、武学重数、敌人等级与章节范围一致。
- 同一互斥组内效果定义不冲突。
- Encounter 至少有一个敌方单位，阵位合法，首领阶段阈值严格递减。
- 商店价格为正，货币存在，测试商品和正式商品环境隔离。
- 公开快照允许的内容均标记为 `arena_legal`。
- TraversalGrid 内 `(grid_x, grid_y,layer_id)` 唯一，ID 与格坐标规范映射一致；普通邻接边双向性按表面规则成立，不得跨层、穿越带阻断 flag 的格或越过 clearance 限制。
- TraversalCell 的 `landing_safety=SAFE_GROUND` 必须同时 `base_walkable=true`、净空充分且具有有效 `safe_landing_marker_id`；隐藏 reveal policy 不得被静态候选索引泄漏。
- TraversalRule 的距离、高差和能力要求不超出至少一个合法 Profile 等级行；若同时要求多个能力，必须存在同一当前装备轻功能满足的组合。
- 需要安全落地的 TraversalLink 终点必须为 SAFE_GROUND，不能是 WATER/HAZARD/VOID、未加载分区或另一个单向连接的瞬时触发体。
- 同一普通边上的 ADD/REPLACE/BLOCK 手工覆盖不能互相冲突；REPLACE/BLOCK 必须指出被覆盖边，孤立覆盖视为错误。
- WaterSurfaceZone 至少有一个合法入口 Link、出口 Link 和 SAFE_GROUND 岸点；格集合连通，不越出所属 TraversalGrid，也不与 GROUND 格错误重叠。
- 每个允许停留的水格必须证明 `入口及此前累计 cost + 到该格 cost + 到任一可用出口 cost <= 对应 WATER_WALK.water_range_cells`；入口、水格和出口 Link 使用同一规范整数 cost。`WATER_WALK.max_route_cost` 必须为 0 且不得进入证明；否则静态生成失败，该格不得进入合法候选。
- 入水 Link 必须终止于 Zone 的 WATER 格；离水 Link 必须从 Zone 水格连接到其声明的安全岸格。
- `route_role=MAIN_REQUIRED` 的连接和水域不得依赖随机掉落、付费独占、可永久错过支线或该连接之后才可取得的能力。

### 7.4 可玩性静态检查

- 首章四条武器路线均能取得至少一套合法套路、武器和内功/轻功组合。
- 主线关键战前存在可获得的最低装备与恢复来源。
- 必做任务不依赖随机掉落的唯一结果。
- 不允许因背包满而永久失去主线关键物品；关键物品必须有保底投递策略。
- 将 TraversalCell 普通烘焙边、TraversalLink 手工覆盖和 WaterSurfaceZone 内部/入口/出口边统一构造成有向世界图；分别以新档能力集和每个主线检查点保证获得的能力集运行可达性检查。
- 每个主线强制目的地必须从对应章节入口可达；路径需要 `JUMP_BASIC/JUMP_LONG/JUMP_HIGH/WATER_WALK` 时，生成器必须证明此前存在不可错过且不依赖付费/随机的 LightnessTraversalProfile 来源。
- 能力来源证明至少给出 `source_type`、`source_id`、最早可获得主线节点、前置闭包和授予的 profile/能力；仅在可选角色身上、仅临时演出或仅 UI 教程标记均不算保证来源。
- 首章必须至少存在一个可达的必经基础跳、两个可选高级跳和一个可选踏水片段；未取得非必需高级轻功或 WATER_WALK 时仍可沿普通路径完成主线。

## 8. 确定性输出

- 输入文件按规范化路径排序，工作表按固定顺序，记录按主键排序。
- 浮点值规范化到声明精度；换行、编码和转义固定为 UTF-8/LF 规则。
- 输出表字段按 Schema 顺序，不依赖哈希表遍历。
- 相同源表、Schema 和生成器版本必须产生相同 manifest 哈希。
- 时间戳不进入内容哈希；诊断时间只能写在独立报告元数据中。

## 9. ContentManifest

Manifest 至少包含：`content_version`、`rules_version`、`foundation_contract_version`、`schema_versions`、`generator_version`、每张源表哈希、每类记录数量、每个生成文件哈希、所有稳定 ID 到所属系统的索引、Y3 映射版本、世界图/轻功通行图哈希、EventSchemaRegistry 哈希、SectionOwnerRegistry 哈希、允许读取的最低存档内容版本。

运行时启动只校验 manifest 与配置模块一致，不重新做完整 Excel 校验。存档和擂台快照记录 `content_version` 与 `rules_version`，未知版本拒绝进入权威结算。

### 9.1 EventSchemaRegistry

所有跨系统领域事件和应用事件必须进入生成后的 EventSchemaRegistry。每条注册记录至少包含：

| 字段 | 规则 |
|---|---|
| event_type | 全局唯一完成时事实名，发布后不复用 |
| producer_system | 唯一权威生产者；多生产者必须使用完全相同契约并显式批准 |
| schema_version | 正整数；升级保留上一发布版读取路径 |
| envelope_kind | DOMAIN_EVENT 或 COMBAT_EVENT；应用层已发生事实仍归 DOMAIN_EVENT，纯表现信号进入 PresentationSignalRegistry |
| required_payload_fields | 字段名、类型、范围、是否敏感 |
| optional_payload_fields | 字段名、类型和默认语义 |
| consumer_systems | 已知消费者及其最低可读版本 |
| persistence_policy | TRANSIENT、RECEIPT_REQUIRED 或 AUDIT_REQUIRED |
| deprecated | 下线后保留历史解析 |

COMBAT_EVENT 是通用 DomainEvent 信封的确定性专化：event_id 由 combat_id 与 sequence 规范派生，aggregate_id=combat_id，revision=sequence，occurred_at 必须为空；专有字段为 combat_id、sequence、action_index、causation_id 和 payload。所有表现与测试文档统一使用 combat_id，不得另建 battle_id 别名。

生成器必须执行：

- 消费者引用的 event_type 必须存在，名称大小写完全一致；DialogueCompleted、EquipmentEquipped、CraftCompleted 等不得使用未注册别名。
- 消费者声明的 payload/filter 字段必须存在于该版本 Schema，类型兼容。
- 同一 event_type 不得出现不同 payload 定义或不同权威生产者。
- UIAnchorAvailable、ScreenOpened、ToastShown 等 presentation 内部信号必须登记在独立 PresentationSignalRegistry，不能冒充领域事件或推进奖励。
- EventSchemaRegistry 本身进入 content manifest 哈希；事件契约变化必须被差异报告标为兼容升级或禁止发布。

### 9.2 SectionOwnerRegistry

所有持久化表型 section、公开派生 section、排行整数和平台整数映射必须进入生成后的 SectionOwnerRegistry。每条记录至少包含：

| 字段 | 规则 |
|---|---|
| section_key | 全局唯一稳定键，发布后不复用 |
| storage_kind | TABLE_SECTION、PUBLIC_SECTION、RANK_INTEGER 或 PLATFORM_INTEGER |
| slot_id | Y3 槽号；整数范围展开后不得冲突 |
| section_path | 表型槽内的规范路径；整数槽使用固定映射键；代码与 ADR 不接受 `dto_path` 别名 |
| owner_system | 唯一允许提交该 section 变更/整数事务的系统 |
| schema_version | 正整数；升级需兼容或迁移路径 |
| write_policy | CHECKPOINT、CRITICAL、DERIVED 或 PLATFORM_CAS |
| validator_id、codec_id | 写前验证与合并编码契约 |
| sensitive/public | 隐私与公开档案约束 |

生成器必须执行：

- 每个 section_key 恰有一个 owner_system；同一 slot_id 下 section_path 不得相同、互为祖先或以其他方式重叠。
- 所有 Save DTO 字段都必须被一个 section 覆盖；未注册 section、未覆盖路径或同一路径多 owner 均阻止发布。
- 系统声明的持久化写集合只能包含自己拥有的 section；非 owner 直接写整槽、他人 section 或平台整数槽在生成阶段失败。
- 槽 1 manifest/player_profile 的 owner 固定为 18，settings_profile 的 owner 固定为 24；Manifest 的 commit marker 只由 SaveCoordinator 生成。槽 100 arena_public_snapshot 与槽 101 arena_rank_value 必须显式注册给竞技系统，并仍由 SaveCoordinator/对应端口执行写入。
- 槽 5 的 tutorial_progress、arena_private、paid_transactions、paid_entitlement_cursor 等必须分别注册，任何系统都不能因共享一个槽而获得整槽所有权。
- 槽 200–319 的单调整数映射由 21 的 EntitlementStore/CounterStore 门面拥有，写策略固定 PLATFORM_CAS；不得注册可递减 balance 字段。
- SectionOwnerRegistry 本身进入 ContentManifest 哈希；owner、路径、槽位或 write_policy 变化按存档兼容变更处理。

## 10. Y3 开发助手插件边界

Excel 读取和物编生成可通过 Y3 开发助手插件实现，但业务 Schema、引用校验和语义校验属于项目代码，不绑定插件 UI。插件操作必须可无交互重复执行，并输出机器可读结果。

Y3 数字 Key 分配由独立注册表管理：已有映射不可因行顺序变化而重排；删除内容保留墓碑；新 Key 冲突立即失败。领域生成配置只引用稳定字符串 ID，数字映射单独输出给适配层。

## 11. 应用用例与事件

| 用例 | 输入 | 输出与失败语义 |
|---|---|---|
| `ValidateContent` | 源表集合、Schema 版本 | 完整问题报告；存在 error 时不生成发布产物 |
| `GenerateContent` | 已验证规范化数据、生成器版本 | 临时目录、manifest 和哈希；失败不污染旧产物 |
| `PublishGeneratedContent` | 已测试临时目录、预期旧 manifest | 原子替换后的新 manifest；旧版本不匹配则拒绝 |
| `DiffContentManifest` | 两份 manifest | 按安全、黄金变化、需迁移、禁止发布分类的差异 |

工具链事件包括 `ContentValidationFailed`、`ContentGenerated`、`ContentPublishRejected` 和 `ContentPublished`。事件载荷保存 manifest/报告引用与哈希，不嵌入整份 Excel 内容；它们只服务构建与审计，不写入玩家存档。

## 12. 错误报告

每条问题包含：严重度、规则 ID、源文件、工作表、行、列、记录 ID、实际值、期望、关联目标和建议修复。跨表问题同时指出源记录与目标记录。

典型错误码：`CFG_DUPLICATE_ID`、`CFG_REF_MISSING`、`CFG_PROBABILITY_INVALID`、`CFG_QUEST_UNREACHABLE`、`CFG_DIALOGUE_DEAD_END`、`CFG_Y3_MAPPING_MISSING`、`CFG_SAVE_BREAKING_CHANGE`、`CFG_EVENT_UNKNOWN`、`CFG_EVENT_SCHEMA_CONFLICT`、`CFG_EVENT_FIELD_MISSING`、`CFG_SAVE_SECTION_OWNER_CONFLICT`、`CFG_SAVE_SECTION_UNREGISTERED`、`CFG_SAVE_SECTION_PATH_OVERLAP`、`CFG_TRAVERSAL_PROFILE_INVALID`、`CFG_TRAVERSAL_GRID_COORD_DUPLICATE`、`CFG_TRAVERSAL_BAKE_STALE`、`CFG_TRAVERSAL_CELL_INVALID`、`CFG_TRAVERSAL_REVEAL_LEAK`、`CFG_TRAVERSAL_LINK_UNSATISFIABLE`、`CFG_TRAVERSAL_OVERRIDE_CONFLICT`、`CFG_TRAVERSAL_LANDING_UNSAFE`、`CFG_WATER_ZONE_INVALID`、`CFG_MAIN_ROUTE_ABILITY_SOURCE_MISSING`、`CFG_WORLD_ROUTE_UNREACHABLE`。

## 13. 配置变更与兼容

变更分为：

- 安全：新增可选字段、新内容、纯展示文本修正。
- 需黄金更新：数值、AI、掉落、战斗效果修改。
- 需迁移：删除/替换存档会引用的 ID、改变等级上限或词条结构。
- 禁止直接发布：复用旧 ID、改变 ID 语义、删除主线所需内容、降低可读存档版本但无迁移。

发布清单必须指出变更类别。需迁移变更在存档迁移实现和夹具通过前不可标记 publishable。

## 15. 验收标准

- 任意已知断链、重复 ID 和非法概率都能在启动游戏前失败。
- 相同输入产生相同产物和哈希。
- 生成失败不会污染上一份可发布配置。
- 首章主线、四路线和关键物品通过静态可达检查。
- 首章世界图在每个能力获取检查点可达；必经基础跳能追溯到此前保证获得的合法 LightnessTraversalProfile，可选高级跳/踏水支路的能力不足不会封死主线；TraversalGrid/Cell、落点和恢复点全部通过安全校验。
- 相同地图、`bake_version`、配置和 profile 生成相同格 ID、普通边、手工覆盖、静态候选索引与世界图哈希；未揭示格不会进入玩家可见候选索引。
- 领域配置不存在 Y3 数字 Key。
- 所有跨系统事件消费者均能解析到唯一 EventSchema，未注册别名在生成阶段失败。
- 每个持久化字段都解析到唯一 section owner；共享槽不会授予整槽写权，槽 100/101 与 200–319 均有显式 owner 和写策略。
- 每个发布配置可追溯到源表、Schema 和生成器版本。
