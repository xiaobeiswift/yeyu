# 《雾州侠行》异步擂台与赛季系统规格

> 状态：规划冻结候选稿
>
> 本文只定义未来实现契约，不代表代码已经存在。公开档案、排行榜和平台身份能力未通过风险验证前，正式擂台保持关闭。

## 1. 目标与非目标

### 1.1 目标

- 使用公开离线阵容快照实现四人队伍全自动异步挑战，不要求双方同时在线。
- 进攻方本地使用确定性战斗内核重建战斗；相同双方快照、规则版本与种子产生相同事件哈希。
- 采用 28 天赛季的进攻积分制，防守者离线不扣分。
- 同一对手同一服务器日只有首次胜利增加积分，练习模式不限次数且不计分。
- 公开快照始终按不可信输入处理：只接受白名单 ID 和合法原始成长字段，所有派生属性本地重算。
- 排行榜发布失败不损坏私人擂台积分，并可通过派生发布队列恢复。
- 排位挑战必须先持久化不可变挑战意图；退出、崩溃或断线不能绕过已武装的失败结算。
- 竞技使用冻结 ArenaRuleBundle，待恢复挑战不会因在线配置或内容版本变化而改写结果。

### 1.2 非目标

- 不实现实时 PVP、观战、玩家聊天、下注、匹配体力、挑战券或防守复仇扣分。
- 首版不提供严格电子竞技级反作弊保证；若 Y3 无法认证公开档案写入者和权威结果，擂台只能作为轻竞技玩法。
- 不从公开快照读取或信任攻击、防御、战力、最终生命等派生属性。
- 不允许客户端 UI 直接提交胜负、积分差值、对手排名或随机种子。

## 4. 领域模型

### 4.1 ArenaSnapshot

| 字段 | 类型 | 约束 |
|---|---|---|
| schema_version | integer | 当前及上一发布版可读 |
| rules_version | integer | 正整数；决定战斗规则，与 CombatSnapshot、ContentManifest 使用同一字段名和数值语义 |
| content_version | string | 内容兼容版本 |
| owner_fingerprint | string | 与被查询 AID 的脱敏摘要一致 |
| source_revision_vector | list | 槽 3 修订、槽 4 修订、平台权益游标证明收据的修订/摘要、rules_version、content_version 的规范向量 |
| arena_rules_id | string | 可恢复的冻结 ArenaRuleBundle ID |
| bundle_hash | string | 规则束规范摘要 |
| formation_id | string | 合法 3×3 阵型 |
| member_entries | list | 1 至 4 名，位置唯一 |
| published_at | integer | 可信服务器时间 |
| snapshot_hash | string | 规范字段摘要；不是安全签名 |

### 4.2 ArenaMemberEntry

ArenaMemberEntry 必须复用 01 角色系统生成的 CharacterBuildSnapshot 公共子集，不能另造角色成长字段。只包含：

- character_id、definition_version、level、awakening_rank、character_revision。
- formation_slot。
- 排序后的 talent_entries。
- 武学系统生成的 MartialLoadoutSnapshot 公共子集。
- 装备系统生成的 EquipmentPublicDTO：装备模板 ID、强化等级、合法词条 ID 与原始词条值。
- 经脉系统生成的公开来源 DTO。
- cosmetic_model_id：仅表现，可丢弃。

本类型不包含 attribute_allocations；若以后增加自由属性分配，必须先由 01 定义、保存、校验并加入 CharacterBuildSnapshot 新版本。

禁止字段：最终攻击、最终防御、最终生命、战力、伤害倍率、付费金额、平台凭证和 Y3 物编 Key。

source_revision_vector 必须覆盖构建该快照所用的全部权威来源：槽 3 的角色/武学/经脉/阵型、槽 4 的已装备物与词条、21 唯一维护的平台权益交付游标的证明收据，以及规则和内容版本。竞技系统不读取原游标；权益向量只接受 21 派生的游标修订与摘要，不公开购买金额、订单或平台计数。

向量字段顺序固定为 slot3_revision、slot4_revision、platform_entitlement_cursor_revision、platform_entitlement_cursor_digest、rules_version、content_version；顶层同名版本必须与向量一致。任一字段缺失、重复或不一致均拒绝快照。

### 4.3 ArenaPrivateState

| 字段 | 类型 | 说明 |
|---|---|---|
| season_no | integer | 当前私人状态赛季 |
| points | integer | 0 至 score_base-1 |
| scored_win_entries | list | day_id、opponent_fingerprint |
| challenge_receipts | list | challenge_id、模式、结果、delta、event_hash |
| challenge_intents | list | 未完成挑战的不可变输入、固定种子、ArenaRuleBundle 和 penalty_armed |
| rank_publish_state | enum | CLEAN、DIRTY、PUBLISHING、UNKNOWN、ERROR |
| last_published_rank_value | integer? | 最近确认值 |
| published_snapshot_hash | string? | 最近确认公开快照 |
| snapshot_publication_state | enum | CLEAN、DIRTY、PUBLISHING、UNKNOWN、ERROR |
| built_source_revision_vector | list? | 最近构建快照使用的完整来源向量 |
| published_source_revision_vector | list? | 最近确认发布快照使用的完整来源向量 |
| revision | integer | 私人竞技修订 |

### 4.4 ArenaChallenge

包含 challenge_id、intent_revision、combat_id、mode（RANKED/PRACTICE）、season_no、day_id、attacker_fingerprint、defender_fingerprint、双方完整冻结 snapshot/hash、captured ranks、arena_rules_id/bundle_hash、combat_seed、penalty_armed、frozen_recovery_loss_delta、state、outcome、event_hash 和 score_commit_receipt。排位 intent 的 frozen_recovery_loss_delta 由启动时 ArenaRuleBundle 固定为 -6，客户端不可修改。

状态：INTENT_PERSISTING → ARMED → RUNNING → FINISHED → COMMITTED；不可校验结果进入 INVALIDATED。只有挑战意图已经由 SaveCoordinator 确认持久化为 ARMED 后才能启动领域战斗。排位的 penalty_armed 在 ARMED 时固定为 true，后续退出、崩溃或断线不能由客户端清除。

## 5. 配置字段

### 5.1 ArenaSeasonDefinition

| 字段 | 默认规划值 | 规则 |
|---|---:|---|
| epoch_server_day | 待定 | 赛季 0 起始服务器日 |
| season_length_days | 28 | 发布后不得在赛季中修改 |
| daily_reset_offset_seconds | 待定 | 与服务器时区共同定义 day_id |
| score_base | 1,000,000 | 必须大于 points_cap |
| points_cap | 999,999 | 不超过 score_base-1 |
| win_base | 20 | 整数 |
| rank_gap_step | 50 | 每相差多少名修正 1 分 |
| rank_modifier_min/max | -10/+10 | 与蓝图一致 |
| loss_delta | -6 | 超时同样适用 |
| action_limit | 99 | 完整结算第 99 个行动机会后仍无胜负，进攻方失败 |
| max_team_size | 4 | 固定 |

赛季号：

season_no = floor((server_day - epoch_server_day) / 28)

排行榜编码：

rank_value = season_no × score_base + clamp(points, 0, points_cap)

必须先实测 Y3 排行榜整数上限并证明整个运营寿命不会溢出；否则正式擂台不得启用。

### 5.2 ArenaValidationPolicy

定义允许的角色、装备、武学、词条、经脉、天赋 ID，等级范围，队伍规则，上一 rules_version 兼容窗，快照大小上限和拒绝错误码。

### 5.3 ArenaRuleBundle

每个正式启用规则束包含不可变的 arena_rules_id、bundle_hash、rules_version、content_version、战斗公式版本、状态规则版本、AI 版本、快照验证版本、计分版本和超时规则。赛季中不得原地修改；只能发布新 ID。至少保留所有未完成 challenge intent 引用的旧规则束，直到挑战被 COMMITTED 或 INVALIDATED。

## 6. 运行时状态

- feature_state：DISABLED、PRACTICE_ONLY、RANKED_ENABLED、MAINTENANCE。
- season_context：server_time、day_id、season_no、config_version。
- local_snapshot：挑战开始时冻结的进攻方快照。
- opponent_candidates：AID 脱敏引用、排名、读取状态。
- active_challenge：最多一个。
- opponent_archive_cache：只在当前会话使用，按 AID 与 snapshot_hash 索引。
- score_transaction_pending：待提交积分事务。
- rank_outbox：私人积分到槽 101 的派生发布任务。
- snapshot_outbox：完整 source_revision_vector 到槽 100 的派生发布任务。
- unresolved_intent：从槽 5 恢复的唯一未完成挑战；存在时禁止开始新的排位挑战。

缓存和排行榜显示值不是私人积分权威来源。

## 7. 快照新鲜度与不可信输入验证

### 7.1 来源变化与 DIRTY

构建快照前必须同时加载并验证槽 3、槽 4 与 21 提供的平台权益交付游标摘要，并固定 ArenaRuleBundle。以下任一来源发生变化，都必须把 snapshot_publication_state 标记为 DIRTY：阵型/出战成员变化、角色或武学成长、经脉变化、装备穿脱/强化/淬炼、权益子收据应用、规则束变更、rules_version 或 content_version 变更。DIRTY 状态不得被旧发布回调清除；只有回调携带的完整 source_revision_vector 仍等于当前向量时才能置 CLEAN。

排位开始前必须冻结一个与当前 source_revision_vector 完全一致且已验证的进攻方快照。防守公开快照按其自身向量和规则兼容窗校验。任何未覆盖槽 3、槽 4、权益游标或规则/内容版本的旧快照都不可用于新排位。

### 7.2 不可信输入验证

读取公开档案后按以下顺序拒绝或重建：

1. 限制总字节、表层级、成员数和各列表长度，防止资源耗尽。
2. 校验 schema_version、rules_version、content_version、arena_rules_id/bundle_hash 和 source_revision_vector 在兼容窗。
3. 校验 queried AID 的 fingerprint 与 owner_fingerprint 一致。
4. 只解析字段白名单；未知字段忽略或按版本策略拒绝。
5. 校验全部稳定 ID、等级、阵位唯一性、武器倾向和装备部位。
6. 校验词条值处于对应生成规则的合法离散集合或范围。
7. 丢弃任何派生属性并从当前兼容规则重算。
8. 规范序列化并校验 snapshot_hash。
9. 若平台不能证明该公开档案由目标账号的受信游戏逻辑发布，只能证明“结构合法”，不能证明真实拥有；该风险必须进入上线门禁。

不合法快照不修补后进入排位。UI 显示对手不可用并记录拒绝码，不暴露安全细节。

## 8. 匹配、种子与计分规则

### 8.1 对手列表

- RankService 返回当前赛季排名附近 AID 和排名值。
- 过滤赛季编码不等于当前 season_no 的条目、自身 AID、重复 AID 和不可读快照。
- 对手列表不足时可使用合法的系统镜像对手，但系统对手必须明确标记，是否计分由配置固定；首版系统对手仅练习不计分。
- captured_attacker_rank 和 captured_defender_rank 在 Start 时固定，结算不重新查询。

### 8.2 挑战意图与确定性种子

challenge_id 由应用层先生成并持久化，combat_seed 不接受 UI 输入，按以下规范字节串的哈希映射到战斗内核整数范围：

`ARENA_SEED_V1 || challenge_id || attacker_snapshot_hash || defender_snapshot_hash || bundle_hash`

同一 challenge_id、双方快照和 ArenaRuleBundle 必得相同种子；恢复时不得生成新 challenge_id 或换种子。新的合法挑战使用新的 challenge_id，因此不能把练习结果冒充排位结果。

排位开始顺序固定为：冻结双方快照/排名/ArenaRuleBundle → 计算种子 → 通过 SaveCoordinator 将 ARMED intent 写入槽 5 arena_private section 并回读确认 → 启动战斗。未确认 ARMED 前不得创建 CombatSession。

### 8.3 积分

排名差修正：

rank_gap = captured_attacker_rank - captured_defender_rank

rank_modifier = clamp(truncate_toward_zero(rank_gap / rank_gap_step), -10, +10)

胜利且本日尚未对该 opponent_fingerprint 计分：

delta = 20 + rank_modifier

胜利但本日已对该对手计分：delta = 0。

合法失败、完整结算第 99 个行动机会后仍无胜负、主动退出或无法重放的已武装恢复失败：delta = -6，且每个 challenge_id 只提交一次。

快照非法、冻结 ArenaRuleBundle 执行错误、事件哈希不匹配或结果无法证明来自该 challenge 的权威 CombatSession 时，结果标记 INVALIDATED：delta = 0，不写 scored_win_entries，不消耗“每日首次胜利”，也不按失败扣分。

练习模式任何结果 delta = 0。最终：

new_points = clamp(old_points + delta, 0, points_cap)

防守者档案和积分永不由挑战者写入，也不因离线防守结果扣分。

## 11. 存档 DTO 与槽位

### 槽 5：私人权威状态

- season_no、points、revision。
- scored_win_entries：day_id/opponent_fingerprint 扁平列表。
- challenge_receipts：challenge_id、模式、结果、delta、event_hash。
- challenge_intents：不可变双方快照摘要/必要重放数据、ArenaRuleBundle、固定 seed、penalty_armed、状态和 score_commit_receipt。
- rank_outbox：outbox_id、target_value、state、retry_count。
- snapshot_publication_state：built/published source_revision_vector、snapshot_hash、bundle_hash、state。

本系统只拥有槽 5 的 arena_private section、槽 100 的 arena_public_snapshot section 和槽 101 的派生排行发布，不拥有整个槽 5。所有写入由 SaveCoordinator 合并；不得覆盖其他系统 section。

### 槽 100：公开派生快照

保存 ArenaSnapshot，配置为公开读取键。发布只通过 SaveCoordinator/SaveStore 写入并回读确认；OpenArchiveService 仅用于其他账号读取。不得包含昵称以外的敏感身份、完整平台 ID、付费金额、货币、背包或任务数据。

### 槽 101：排行榜值

只保存 rank_value 整数，由槽 5 当前赛季积分派生。冲突恢复以槽 5 为准重新发布，不能反向覆盖私人 points。

## 12. Y3 适配与 UI

### 12.1 Y3 风险验证

- 验证 SaveCoordinator 能否写入并回读确认自己的槽 100；验证 request_open_archive 能否按 AID 跨两个真实测试账号只读指定公开键。
- 分别验证 SaveCoordinator 发布延迟与 OpenArchiveService 跨账号陈旧读取、大小限制、隐私和错误语义。
- 验证排行榜能否返回附近排名对应 AID、值、更新延迟和整数范围。
- 验证公开档案与排行榜的账号身份是否由平台绑定，Lua 是否能伪造 owner。
- 未通过任一身份/完整性关键项时，只开放 PRACTICE_ONLY。

### 12.2 UI

- 擂台页显示赛季剩余时间、积分、排名发布状态、阵容快照状态和规则入口。
- 对手卡展示昵称脱敏信息、排名、队伍公开信息、快照时间和可用状态。
- “排位挑战”和“练习”明确区分；练习结果不显示积分动画。
- 排位 intent 武装后，退出按钮必须明确提示本挑战将恢复原局或按冻结规则判负；关闭表现不能取消结算。
- 战斗强制全自动，隐藏手动绝招入口；允许加速或跳过表现。
- 结算显示基础分、排名差修正、每日首次胜利资格和最终 delta。
- Rank 发布延迟显示“积分已保存，排行榜同步中”，不能回滚分数显示。
- 快照非法、Clock 失败、赛季切换、公开档案过期和排行榜不可用均有独立状态。

## 13. 边界与失败

- 挑战进行中跨赛季：排位结果不提交积分，保存练习结果并返回 SEASON_CHANGED。
- 挑战进行中跨日但不跨赛季：以 Start 时 day_id 判断首次胜利并提交；提交时仍需防重复。
- 对手在列表后更新阵容：expected_hash 不一致则要求重新确认，不能静默换对手。
- 排行榜返回旧赛季值：过滤，不用于当前排名差。
- 未排名玩家的 captured rank 使用已冻结的 unranked_rank_policy；不得由 UI传值。
- 读取超大、深层或未知版本公开档案时尽早拒绝。
- challenge_id 重复但 event_hash 不同：拒绝并记录安全事件。
- 战斗表现崩溃不等于领域失败；只有领域 CombatFinished 可提交。
- 已武装排位 intent 在启动/运行/结算任一点中断：优先用原双方快照、原 ArenaRuleBundle 和原种子确定性重放；依赖缺失或无法安全重放时按 intent 冻结的 recovery_loss_delta 记 -6，且仅一次。
- 快照校验失败、规则执行错误或事件哈希不一致属于 INVALIDATED，不属于战败：delta = 0，且不得写入本日首次胜利记录。
- 私人积分已提交、rank 写未知：对账槽 101；不重复改变积分。
- 同日清理 scored_win_entries 时只删除早于保留窗口的条目，不删除当前日。

## 14. 生成与静态校验

- ArenaValidationPolicy 中所有 ID、范围和装备部位规则引用有效。
- 公开 DTO 最大样本满足槽 100 容量和三层嵌套。
- score_base 大于 points_cap，赛季编码在平台整数边界内。
- 赛季 epoch、长度和日切配置能对边界时间产生唯一 season/day。
- rank_gap_step 大于 0，胜利 delta 最低为 10、最高为 30。
- 所有 rules_version 有明确兼容窗和快照迁移/拒绝策略。
- ArenaRuleBundle 发布后不可变，bundle_hash 与各组件版本一致；仍被 intent 引用的规则束不可裁剪。
- source_revision_vector 必须覆盖槽 3、槽 4、权益游标、rules_version 和 content_version。
- 快照不得包含禁止字段或 Y3 数字 Key。
- 每个可公开角色、武学、装备和词条都有重建器。

## 15. 测试矩阵

| 类别 | 必测场景 |
|---|---|
| 快照 | 合法、未知 ID、越界等级、重复阵位、伪造派生属性、超大输入 |
| 快照新鲜度 | 槽 3/4、装备、权益游标、规则或内容任一变化均标 DIRTY；旧发布回调不能误置 CLEAN |
| 确定性 | 同 challenge_id/双方快照/冻结 ArenaRuleBundle 种子与事件哈希一致；任一输入改变种子改变 |
| 积分 | 强弱排名差、截断、上下限、首次胜利、重复胜利、失败、完整结算第 99 个行动机会、恢复判负仅一次 |
| 赛季 | 起止边界、跨日、跨赛季、旧赛季排行过滤、编码溢出 |
| 幂等 | Commit 重复、同 ID 不同哈希、rank outbox 重放、intent 重放 |
| 中断恢复 | intent 保存前退出不启动；ARMED 后各崩溃点原种子重放或冻结规则 -6，不能通过退出避罚 |
| 无效结果 | 非法快照、规则执行异常、非权威结果、事件 hash 错均 delta 0 且不消费每日首次胜利；已武装 intent 的恢复依赖缺失另按冻结恢复规则判负 |
| 故障 | 公开档案超时/陈旧、排行写未知、Clock 不可用、槽 5/101 部分成功前向恢复 |
| 双账号 | 发布、跨账号读取、附近 AID、更新延迟和身份绑定 |
| UI | 练习/排位区分、同步中、快照非法、赛季切换 |
| 性能 | 两个四人快照重建和 8 单位全自动战斗 |

## 16. 验收标准

- 两个真实测试账号可发布、互读合法公开阵容并完成全自动挑战。
- 相同输入重复挑战产生相同事件哈希和结果。
- 每日同一对手仅首次胜利加分；失败/超时 -6；练习永不改分。
- 已武装排位无法通过退出或崩溃逃避结果；恢复必定重放同一输入，或按冻结规则只记一次 -6。
- 快照/规则/权威性错误只产生 delta 0，且不消耗每日首次胜利资格。
- 快照来源向量完整覆盖槽 3、槽 4、平台权益游标与规则/内容版本，任一变化立即 DIRTY。
- 防守者任何离线结果都不改变其私人积分。
- 非法或未知版本快照被拒绝，派生属性全部由本地规则重算。
- 私人积分与排行榜发布解耦，失败重试不重复计分。
- 赛季编码、平台整数边界和 AID 获取能力均有实机证据。
- 平台不能保证必要身份与完整性时，正式排位开关保持关闭。
