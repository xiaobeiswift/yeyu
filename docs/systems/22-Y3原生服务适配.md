# Y3 原生服务适配系统工程规格

> 状态：V1 端口契约已冻结；Y3 原生 API 映射仍须逐项验证
>
> 遵循：[通用工程约定](./00-通用工程约定.md)

## 1. 目标与非目标

本系统把 Y3 平台能力封装为稳定的应用端口，使领域层与具体 Y3 API、回调对象、句柄和错误码隔离。覆盖云存档、服务器时间、公开离线档案、排行榜、平台商城和服务器随机池。

目标：统一异步调用、超时、重试、幂等、能力探测和日志；向上层提供可测试 DTO；当平台能力缺失时返回明确降级状态；保证付费与权益链路默认关闭且不能因回调歧义被误开启。

非目标：不在适配器中实现战斗、任务、积分、保底或奖励规则；不自建外部后端；不把平台返回内容直接当成可信领域对象；不在这里设计 UI。

## 4. 服务领域模型与通用请求模型

### 4.1 RequestContext

所有端口请求顶层必填 `context`，其闭合字段集如下：

| 字段 | 类型 | 规则 |
|---|---|---|
| `request_id` | RuntimeId component | 单次调用唯一，只用于诊断、只读回调关联和去重；不是业务幂等键 |
| `correlation_id` | RuntimeId component | 贯穿一个应用用例 |
| `idempotency_key` | RuntimeId component? | 所有写操作必填；同一业务意图重试时保持不变 |
| `attempt` | integer | `1..9007199254740991` |
| `started_at_local` | number? | 有限非负数且不大于安全整数上限；只用于诊断耗时 |
| `timeout_ms` | integer? | `1..9007199254740991`；只用于应用编排与诊断 |

RuntimeId component 为 1–64 字节、首字符字母或数字、后续只允许字母、数字、下划线、点和连字符。`request_id` 每次调用变化；`idempotency_key` 是写意图的稳定 `request_key` 来源，二者不得混用。

### 4.2 Result 与两阶段调用

所有方法都采用“同步 admission + 异步 completion”两阶段契约：

1. 调用方法同步返回 `Result`。请求、回调或适配器自身在接纳前失败时返回错误，调用未接纳且不得回调。
2. 接纳回执只能是精确的 `{ ok=true, value={ accepted=true } }`；禁止额外诊断字段、句柄或平台对象。
3. 接纳后回调不得在方法返回前内联执行。首个 completion 经门禁后交付；重复或迟到 completion 在“已完成”分支立即抑制，不再解析其原始载荷。
4. completion 成功信封精确为 `{ ok=true, value=<operation DTO> }`；错误信封精确为 `{ ok=false, error={code,message_key,retryable,details?} }`。错误码必须来自通用或操作级白名单，`message_key` 使用稳定的 `error.*` 键。

`mutating=true` 与 `requires_idempotency=true` 在 V1 必须同时成立，不能只设置其中一个。每个已接纳写操作：

- 成功 DTO 顶层必须返回 `request_key == context.idempotency_key`；
- 错误 completion 必须返回 `error.details.request_key == context.idempotency_key`；
- 同步 admission 错误发生在接纳前，不要求 `request_key`，且绝不回调；
- completion 缺失或错配 `request_key`、DTO 非法、超预算、出现内部 `PORT_*`/`FAKE_*` 错误，或接纳后返回 `PLATFORM_UNAVAILABLE/PLATFORM_RATE_LIMITED` 时，一律向上归一为 `PLATFORM_RESULT_UNKNOWN`、`retryable=false`、`recovery=QUERY_OR_RECONCILE`，并保留有界 `cause_code` 与正确 `request_key`。

### 4.3 载荷预算与快照隔离

预算在操作 validator 之前执行，并适用于 request、completion result 和同步 admission receipt：

| 常量 | 冻结值 |
|---|---:|
| `MAX_SAFE_INTEGER` | `9007199254740991` |
| 直接字段 `MAX_STRING_BYTES` | `1024` |
| `MAX_PAYLOAD_DEPTH` | `8` |
| completion DTO 二次结构校验 `MAX_RESULT_DEPTH` | `8` |
| `MAX_PAYLOAD_NODES` | `4096` |
| `MAX_TOTAL_STRING_BYTES` | `262144` |
| `MAX_KEY_BYTES` | `256` |
| `MAX_VALUE_STRING_BYTES` | `65536` |

遍历必须在首次扫描键时计数并提前停止，不能先收集百万键后才校验。只接受有限数值、布尔、字符串、字符串键 map 或正整数密集数组；禁止空字符串 map key、稀疏/混合键、循环、共享 table alias、函数、userdata、线程和 Y3 句柄。table 只按自身 raw key/value 复制，metatable 被剥离，`__index/__pairs` 不得补出字段或改变扫描结果。

DI 边界实行三向快照隔离：先把调用方 request 复制为私有校验/echo 快照，再给原始适配器另一份独立 request 副本；callback 到达后先复制 result，再做预算与 DTO 校验，application 只收到校验后的副本。调用方、适配器或 application 在返回后修改任一 table，都不能改变另一侧、幂等缓存或 echo 判定。同步 admission receipt 同样复制后校验，原始适配器 table 不得外泄。

### 4.4 只读依赖注入

端口 spec 使用私有 backing；公开 `operations/operation_by_name` 只返回 defensive metadata copy。`AppFactory` 必须以可信 `PortContract` API 包装每个注入实现，捕获原始方法并只暴露操作白名单。`app`、`app.services`、每个 guarded service 和 `app.schemas` 都是空壳只读 facade；不得透传 raw adapter 的 `tick/secret/diagnostics` 或允许替换操作函数。正式平台能力未形成验证报告前，只能注入 Fake 或同步返回 `PLATFORM_UNAVAILABLE` 的不可用适配器。

## 5. 端口契约

V1 只冻结以下 6 个端口、22 个操作。所有 success DTO 都是闭合字段集；表格中的 `?` 才表示可选，未列字段一律拒绝。

### 5.1 SaveStore

所有 `player_ref` 都是 RuntimeId component；所有槽号只允许 `1..319`。表中输入均另含 `context`。

| 操作 | 精确业务输入 | success DTO / union | 关键语义 |
|---|---|---|---|
| `load_slot` | `{player_ref,slot_id}` | `{player_ref,slot_id,dto,revision,checkpoint_id,payload_checksum}` | `dto` 必须是完整 `SaveEnvelope`，且三项 metadata 与顶层完全一致；未找到使用 `SAVE_NOT_FOUND` |
| `stage_slot` | `{player_ref,slot_id,expected_revision,checkpoint_id,payload_checksum,dto}` | `{player_ref,slot_id,revision,checkpoint_id,payload_checksum,request_key}` | `dto` 通过 `SaveEnvelope.validate`；`dto.revision=expected_revision+1`，checkpoint/checksum 与顶层一致；响应逐项 echo |
| `commit` | `{player_ref,commit_entries[]}` | `{player_ref,status,slot_results[],request_key}` | 输入 row 精确为 `{slot_id,target_revision,checkpoint_id,payload_checksum}`，按槽严格升序且唯一 |
| `upload` | `{player_ref}` | `{player_ref,status='CONFIRMED',request_key,upload_ref?}` | 未确认时进入恢复流程 |
| `read_integer` | `{player_ref,slot_id}` | `{player_ref,slot_id,value,revision}` | 只接受非负安全整数 |
| `compare_and_add_integer` | `{player_ref,slot_id,expected_value,expected_revision,delta}` | `{player_ref,slot_id,value,revision,request_key}` | `value=expected_value+delta`、`revision=expected_revision+1`；禁止负增量和溢出 |
| `compare_and_set_integer` | `{player_ref,slot_id,expected_value,expected_revision,target_value}` | `{player_ref,slot_id,value,revision,request_key}` | `target_value>=expected_value`，响应值等于 target 且 revision 只前进一次 |
| `query_integer_request` | `{player_ref,slot_id,original_idempotency_key}` | CONFIRMED：`{status,player_ref,slot_id,original_idempotency_key,value,revision}`；其他：`{status,player_ref,slot_id,original_idempotency_key}` | 其他 status 只允许 `NOT_FOUND/PENDING/UNKNOWN`；所有关联字段 echo，不产生第二次写入 |

`commit.status` 只允许 `CONFIRMED/PARTIAL`。CONFIRMED row 精确为 `{slot_id,status='CONFIRMED',target_revision,checkpoint_id,payload_checksum}` 并完整 echo 对应输入 row；FAILED/UNKNOWN row 精确为 `{slot_id,status,error_code}`。FAILED 的 `error_code` 只允许 `PLATFORM_INVALID_ARGUMENT`、`PLATFORM_PERMISSION_DENIED`、`PLATFORM_QUOTA_EXCEEDED`、`SAVE_REVISION_CONFLICT`；UNKNOWN 只允许 `PLATFORM_RESULT_UNKNOWN`。`PLATFORM_UNAVAILABLE/PLATFORM_RATE_LIMITED` 禁止藏入 FAILED row；无法确定是否写入时必须使用 `UNKNOWN + PLATFORM_RESULT_UNKNOWN`，否则整个 completion 会被门禁提升为未知。

Y3 映射候选：`y3.save_data.load_table/save_*`、玩家上传接口。最终函数名在能力验证报告冻结，业务层不得直接调用这些 API。

21 中的 EntitlementStore 和 CounterStore 不是新增平台端口，而是 SaveStore 整数 CAS 之上的 application 门面：

- EntitlementStore 只允许访问配置映射的槽 200–299，并强制单调权益计数、CAS/原请求查询、幂等键和 ENTITLEMENT_COUNT_REGRESSED 检查。
- CounterStore 只允许访问槽 300–319，保存 credential granted/consumed/refunded、total_draws、last_highest ordinal、token earned/spent 等单调 totals；不得保存可递减余额。
- 两个门面的每次 I/O 都由 SaveCoordinator 串行编排并进入事务/恢复日志，不得由业务 application 旁路直写，也不得把普通表型云档伪装成平台整数权威。

SaveCoordinator 按 18 的 SectionOwnerRegistry 接收 section 变更，再由 SaveStore 写完整槽。私人检查点必须先确认槽 2–5，最后写槽 1 Manifest；SaveStore 的 commit 即使返回“部分成功”也不能被解释为跨槽原子提交。调用方只可按 checkpoint_id、每槽结果和收据前向恢复。

### 5.2 ClockService

| 操作 | 精确业务输入 | success DTO | 规则 |
|---|---|---|---|
| `now` | 无（仅通用 `context`） | `{unix_seconds,trust_level='TRUSTED',response_id}` | `unix_seconds` 为非负安全整数；不可用时返回错误，不回退本地时间领奖 |

ClockService 只取得服务器时间。服务器日、周和通用周期由 17 的 TrustedPeriod/Cycle 服务计算；擂台赛季由 20 的 arena_season 纯领域规则计算；卡池开放窗口由 21 的应用/领域规则计算。适配器不得提供 server_date_key 或 season_id，避免时区与规则版本分叉。

### 5.3 RankService

V1 排行槽固定为 `101`，不接受其他整数槽。

| 操作 | 精确业务输入 | success DTO / union |
|---|---|---|
| `publish_score` | `{slot_id=101,encoded_value}` | `{status='CONFIRMED',slot_id,encoded_value,request_key,rank?}` |
| `get_self_rank` | `{slot_id=101}` | UNRANKED：`{status,slot_id}`；RANKED：`{status,slot_id,rank,encoded_value}` |
| `get_nearby_entries` | `{slot_id=101,center_rank,count}`，`count<=1000` | `{status='AVAILABLE',slot_id,entries[]}` |
| `get_entry_identity` | `{entry={entry_ref,rank,encoded_value,display_name?,aid?}}` | UNAVAILABLE：`{status,entry_ref,rank,encoded_value,aid?}`；AVAILABLE：同结构且 `aid` 必填 |

附近排名 row 精确为 `{entry_ref,rank,encoded_value,display_name?,aid?}`；`rank` 严格升序，`entry_ref` 在响应内唯一。`entry_ref` 是适配器从同一次排行读取取得的平台稳定 opaque token；identity 结果必须 echo `entry_ref/rank/encoded_value`，输入已有 `aid` 时还必须 echo 同一 AID。平台不能提供稳定 token 或原子身份解析时，`rank_identity=unavailable`，不得用“名次+分数”在稍后重新查人，也不得伪造 AID。

### 5.4 OpenArchiveService

| 操作 | 输入 | 输出 |
|---|---|---|
| `read_public_snapshot` | `{opponent_aid,slot_id=100}` | `{status='FOUND',opponent_aid,slot_id,snapshot,revision,payload_checksum}` |

OpenArchiveService 是严格只读端口，不提供 publish/write 操作。响应必须 echo `opponent_aid/slot_id`，checksum 为 64 位小写 SHA-256。槽 100 由本玩家 SaveCoordinator/SaveStore 写入并回读确认，只有读取其他 AID 时使用本端口。

Y3 候选映射：`Player.request_open_archive(aid, callback)`。适配器只解析平台容器，不验证角色、武学和装备合法性；严格校验由擂台系统完成。

### 5.5 PlatformStore

| 操作 | 精确业务输入 | success DTO / union |
|---|---|---|
| `get_goods_info` | `{goods_id}` | `{goods_id,status='AVAILABLE',currency_code,price_minor,metadata,valid_from_unix?,valid_until_unix?}` |
| `purchase` | `{goods_id,quantity}` | `{status='CONFIRMED',order_ref,goods_id,quantity,request_key}` |
| `get_owned_count` | `{platform_item_id}` | `{platform_item_id,count,revision}` |
| `consume_item` | `{platform_item_id,quantity}` | `{status='CONFIRMED',platform_item_id,consumed_quantity,remaining_count,revision,request_key}` |
| `reconcile` | `{known_order_refs?,entitlement_cursor?,cursor_request_hash}` | `{status='CONFIRMED',orders[],request_id,cursor_request_hash,entitlement_cursor?,entitlement_cursor_hash?}` |

`reconcile` 的 known refs 与输入 cursor 至少存在一项。`request_id` 只在这个只读操作中 echo `context.request_id` 以防回调串单，不是业务幂等键；`cursor_request_hash` 必须 echo。输出 `entitlement_cursor/entitlement_cursor_hash` 必须同时出现或同时缺失。订单 row union 为：

- CONFIRMED/REFUNDED：`{order_ref,status,goods_id,quantity}`；
- PENDING/NOT_FOUND/UNKNOWN：`{order_ref,status}`。

响应必须覆盖请求中的每个 `known_order_ref`，且 order_ref 严格升序、唯一。

`CursorRequestHashV1` 由 application 在冻结 reconcile 输入后生成，由适配器在 admission 前从自己的 request 副本重算并验证：

```text
SHA256(
  ASCII "WZX-STORE-RECONCILE-V1\0"
  + one_byte known_refs_present
  + u32be(known_ref_count)
  + each known ref: u32be(utf8_byte_length) + utf8_bytes
  + one_byte cursor_present
  + CanonicalCursorValueV1(entitlement_cursor, if present)
)
```

`CanonicalCursorValueV1` 只编码本文件 4.3 允许的值：字符串使用 `S+u32be(length)+bytes`，安全整数使用 `I+u32be(decimal_length)+无前导零十进制`，布尔使用 `B0/B1`，数组使用 `A+u32be(count)+顺序元素`，map 使用 `M+u32be(count)+按 UTF-8 字节升序的 key/value`。cursor 根是 map，空根按空 map 编码。摘要输出 64 位小写十六进制。

`entitlement_cursor_hash` 使用同一 canonical cursor 编码，但领域隔离前缀为 `WZX-STORE-CURSOR-V1\0`。application 收到下一 cursor 后先验证该 hash，再据冻结后的 known refs + cursor 计算下一次 `cursor_request_hash`。若真实 Y3 链路无法保留并验证这条 cursor/hash 链，`store_recovery` 不得标记 available，真实付费保持关闭。

若平台不提供唯一订单号或查询/补单能力，真实付费入口保持关闭。

`get_owned_count/consume_item` 仅用于平台明确提供的普通商品道具语义，不得作为 21 真实付费抽取凭证的权威接口。付费抽取凭证必须使用平台单调 credential_granted_total、credential_consumed_total、credential_refunded_total 及 SaveStore CAS/原请求查询；不得维护可递减 balance mirror。

### 5.6 GachaService

| 操作 | 精确业务输入 | success DTO / union |
|---|---|---|
| `request_pool` | `{pool_id,expected_probability_version}` + `context.idempotency_key` | `{status='CONFIRMED',pool_id,request_key,probability_version,result_id,trusted_unix_seconds,platform_code='SUCCESS',rewards[]}` |
| `query_pool_request` | `{original_request_key,expected_pool_id,expected_probability_version}` | CONFIRMED：`{status='CONFIRMED',pool_id,request_key,probability_version,result_id,trusted_unix_seconds,platform_code='SUCCESS',rewards[]}`；其他：`{status,request_key}`，status 只允许 `NOT_FOUND/PENDING/UNKNOWN` |
| `get_pool_capability` | `{pool_id}` | `{status='VERIFIED',pool_id,authoritative,consumption_atomic,result_persistence_atomic,request_query_supported,audit_export_supported}` |

`request_pool.request_key` 固定等于 `context.idempotency_key`；query 响应 `request_key` 固定 echo `original_request_key`。CONFIRMED 的 `pool_id/probability_version` 必须分别匹配请求期待值，`result_id` 是稳定平台结果引用，`trusted_unix_seconds` 是非负安全整数。奖励 row 精确为 `{reward_kind,content_id,quantity}`：kind 只允许 CHARACTER/MARTIAL/VOUCHER，ID 分别使用 `char_`/`martial_`/`item_` 前缀；content_id 严格升序且唯一，最多 100 row。

Y3 候选映射：`player:request_random_pool(id, callback)`。奖励 Key 必须通过白名单映射为 `char_`、`martial_` 或凭证 ID；未知 Key 整单进入隔离对账，不得部分发放。

若 Y3 不能按原 `request_key` 查询，只有在平台书面并实测证明重复 request_pool 使用同一幂等键必定返回原结果时，query_pool_request 才可由适配器安全模拟。两种能力都不存在时，`random_pool_request_query=unavailable`，真实付费卡池强制关闭。任何 CONFIRMED 结果缺少 pool、概率版本、result_id 或受信时间，同样不得授予权益。

### 5.7 操作级错误白名单

平台 completion 的通用稳定码精确为 `PLATFORM_INVALID_ARGUMENT`、`PLATFORM_PERMISSION_DENIED`、`PLATFORM_QUOTA_EXCEEDED`、`PLATFORM_RATE_LIMITED`、`PLATFORM_RESULT_UNKNOWN`、`PLATFORM_UNAVAILABLE`。除此之外，只有下列操作可返回对应业务码：

| 操作 | 附加允许码 |
|---|---|
| `SaveStore.load_slot/read_integer` | `SAVE_NOT_FOUND` |
| `SaveStore.stage_slot/commit` | `SAVE_REVISION_CONFLICT` |
| `SaveStore.compare_and_add_integer/compare_and_set_integer` | `PLATFORM_INTEGER_CONFLICT` |
| `OpenArchiveService.read_public_snapshot` | `OPEN_ARCHIVE_NOT_FOUND` |
| `PlatformStore.get_goods_info/purchase` | `STORE_GOODS_UNAVAILABLE` |
| `GachaService.request_pool` | `GACHA_CREDENTIAL_INSUFFICIENT`、`GACHA_UNKNOWN_REWARD` |
| `GachaService.query_pool_request` | `GACHA_UNKNOWN_REWARD` |

门禁/Fake/admission 内部诊断码的冻结集合为 `PORT_ADAPTER_CALLBACK_INLINE`、`PORT_ADAPTER_FAILED`、`PORT_ADAPTER_RETURN_INVALID`、`PORT_CONTRACT_INVALID`、`PORT_IDEMPOTENCY_REQUIRED`、`PORT_OPERATION_UNKNOWN`、`PORT_REQUEST_CONTEXT_INVALID`、`PORT_REQUEST_INVALID`、`PORT_RESULT_INVALID`、`FAKE_FINGERPRINT_FAILED`、`FAKE_RESULT_SNAPSHOT_FAILED`、`FAKE_SCRIPT_EXHAUSTED`、`FAKE_SCRIPT_HANDLER_FAILED`、`FAKE_SCRIPT_INVALID`、`FAKE_SNAPSHOT_INVALID`、`IDEMPOTENCY_KEY_REUSED`。这些诊断不是平台完成写操作的明确业务结论，尤其不能由已接纳 mutation callback 直接透传给 application。

## 7. 状态机与启动顺序

服务容器状态：`uninitialized → probing → ready/degraded/blocked`。

1. 初始化日志与回调桥。
2. 获取本地玩家与平台身份的脱敏引用。
3. 探测云档读取；成功后交给迁移系统。
4. 探测服务器时间。
5. 非阻塞探测排行/公开档案能力。
6. 商城和随机池只在测试环境或显式验证命令下探测，不自动产生交易。
7. 生成能力快照并装配功能开关。

云档状态为 `blocked` 时，游戏进入只读恢复页，不启动新档业务。排行或商城降级不阻塞离线首章。

## 8. 错误映射与重试

错误分三层：Y3 原始码只存在于适配日志；端口返回 PLATFORM/SAVE/OPEN_ARCHIVE/STORE/GACHA 稳定码；应用层再按用例映射。不得让 UI 解析 Y3 原始码。

| 平台现象 | 端口稳定码 | 应用层结果 | 可否自动重试 |
|---|---|---|---|
| 明确参数非法 | `PLATFORM_INVALID_ARGUMENT` | 对应 SYSTEM_INVALID_ARGUMENT | 否 |
| 服务不可用 | `PLATFORM_UNAVAILABLE` | 存档为 SAVE_DOWNLOAD_FAILED；其他为各系统 UNAVAILABLE | 只读操作可退避重试 |
| 回调超时 | `PLATFORM_RESULT_UNKNOWN` | 存档为 SAVE_RESULT_UNKNOWN；卡池事务进入 RESULT_UNKNOWN | 权益操作按原 `request_key` 查询/对账 |
| 明确无档 | `SAVE_NOT_FOUND` | 仅满足 18 的严格条件时映射 CONFIRMED_ABSENT | 否；未知状态不得建新档 |
| 修订冲突 | `SAVE_REVISION_CONFLICT` | SAVE_REVISION_CONFLICT | 重新读取并走冲突处理 |
| 整数 CAS 冲突 | `PLATFORM_INTEGER_CONFLICT` | COUNTER_REVISION_CONFLICT | 查询最新值与原幂等请求；禁止盲重试增量 |
| 无权限 | `PLATFORM_PERMISSION_DENIED` | PERMISSION_DENIED | 否 |
| 容量超限 | `PLATFORM_QUOTA_EXCEEDED` | QUOTA_EXCEEDED | 清理非权威过期日志后由玩家重试 |
| 频率限制 | `PLATFORM_RATE_LIMITED` | RATE_LIMITED | 只按 Retry-After/端口退避策略 |
| 对手无公开档 | `OPEN_ARCHIVE_NOT_FOUND` | NO_VALID_OPPONENT/换对手 | 只读请求可换目标 |
| 商品关闭 | `STORE_GOODS_UNAVAILABLE` | PRODUCT_UNAVAILABLE | 否 |
| 抽取凭证不足 | `GACHA_CREDENTIAL_INSUFFICIENT` | GACHA_CREDENTIAL_INSUFFICIENT | 否 |
| 随机池未知奖励 | `GACHA_UNKNOWN_REWARD` | MANUAL_REVIEW | 隔离，人工/平台对账 |
| 权益计数低于私人游标 | `ENTITLEMENT_COUNT_REGRESSED` | ENTITLEMENT_COUNT_REGRESSED | 否，禁止反向扣权益 |

自动重试使用有上限的退避并记录 attempt；同一用户动作只能存在一个进行中的写请求。

表中的 `PLATFORM_UNAVAILABLE/PLATFORM_RATE_LIMITED` 自动重试说明只适用于未接纳请求或只读操作。写操作一旦返回 `accepted=true`，随后即使平台 callback 声称 unavailable/rate-limited，也不能证明副作用未发生，端口门禁必须按 4.2 转为 `PLATFORM_RESULT_UNKNOWN`。SaveStore.commit 的 row 也遵守同一原则，不能把歧义码伪装成确定 FAILED。

## 9. 应用事件

适配器不发布会改变领域规则的事件，只发布供应用层编排和诊断消费的事实：

| 事件 | 载荷 | 消费者 |
|---|---|---|
| `PlatformCapabilitiesEvaluated` | 全部能力状态、环境、探测版本 | 启动与功能开关 |
| `SaveLoadCompleted` | 槽号、结果码、平台修订摘要 | 存档恢复系统 |
| `ServerClockUnavailable` | 请求 ID、错误码、最后可信时间摘要 | 刷新与赛季系统 |
| `PlatformRequestTimedOut` | 端口、操作、request_id、是否涉及权益 | 诊断与对账队列 |
| `StoreOrderObserved` | 脱敏订单引用、商品映射、平台状态 | 商城权益系统 |
| `RandomPoolResultReceived` | `request_key`、结果码、奖励 Key 摘要 | 卡池对账系统 |

这些事件遵循通用事件信封。权益相关事件只能触发查询或对账，不能直接发放角色、武学或货币。

## 10. 配置

`platform_services` 配置至少包含：槽号映射、公开档键、排行榜槽、请求超时、只读重试策略、商品 ID 映射、随机池 ID 映射、允许的返回奖励 Key、各功能发布开关和环境标识。运营时区与日切规则属于 17 的 CycleDefinition，擂台 epoch/赛季规则属于 20，不进入平台适配配置。

校验：槽号不可冲突；正式商品不能引用测试池；真实付费开关在构建时默认 false；未知环境强制关闭付费；池的奖励白名单必须全部能映射到权益定义。

## 11. 测试矩阵

- 六个 Fake 端口覆盖全部 22 操作的精确 request/success/error DTO；非法请求同步拒绝且不回调，合法请求只返回 exact accepted receipt，并且至少 tick 一次后才 completion。
- 两阶段门禁测试：内联 callback、adapter throw、非法 admission receipt、恶意额外字段、错误码越权、重复/迟到 callback；重复 callback 必须先抑制，不能再次遍历超大 raw payload。
- 三向快照与只读 DI 测试：调用方/adapter/application 在调用后修改嵌套 table 不互相污染；raw adapter 不可从 app 取得；app/services/schemas/spec 普通赋值不得改变可信 backing。
- payload budget 边界测试：深度、节点数、总字符串字节、key/value 字节恰好上限及上限+1；百万宽表首次扫描早停；cycle/shared alias/sparse/mixed payload 拒绝；metatable 被剥离且 `__index` 不能补出字段。
- 存档无档、坏档、部分成功、修订冲突、上传未知测试。
- 私人检查点数据槽部分成功、槽 1 Manifest 最后提交、checkpoint 回读与孤儿槽识别契约测试。
- ClockService.now 的成功、不可用、异常回退和可信级别测试；跨日/时区/周期边界由 17/20 的纯规则测试。
- 排行 entry_ref 缺失/重复/错配、AID echo、槽非 101、重复项、超范围整数和旧赛季值测试。
- 公开档缺失、陈旧、超大、未知字段测试。
- OpenArchiveService 只读契约测试；槽 100 发布必须走 SaveCoordinator 并回读确认。
- 商城取消、重复回调、延迟成功、断线重连和补单测试；reconcile 必须拒绝错 request_id/cursor_request_hash、cursor/hash 单边出现和请求订单缺行。
- 随机池未知奖励、空结果、重复结果、平台错误和对账测试；同 `request_key` 重试与 query_pool_request 必须返回同一 `result_id`、池、概率版本、受信时间和奖励。
- 整数 CAS 成功/冲突/响应未知/迟到回调测试；query_integer_request 必须返回原结果，paid counter 负增量与无条件 add 必须被拒绝。
- 所有已接纳写操作覆盖 success/error `request_key` 错配、malformed/overbudget completion、内部 `PORT_*/FAKE_*` 错误和 callback `PLATFORM_UNAVAILABLE/RATE_LIMITED`；对外结果必须为带正确 key 的 `PLATFORM_RESULT_UNKNOWN`。
- 两个真实测试账号的跨账号公开档与排行集成验收。

## 12. 验收标准

- 业务模块中不存在六类 Y3 API 的直接调用。
- 同一平台回调只能完成一次应用请求。
- 所有注入实现都经过可信 guard；业务只能看到只读 facade，不能取得或替换 raw adapter/spec/schema backing。
- request、adapter input、echo binding 和 application result 之间不存在可变 table 引用共享；所有载荷在冻结预算内。
- 已接纳写操作的每个终态都能以 `request_key` 关联唯一业务意图；任何无法证明的 completion 都进入 `PLATFORM_RESULT_UNKNOWN`，不得按确定失败重发。
- 任意读取失败都不会触发默认档覆盖。
- 能力不足只关闭依赖功能，不阻塞离线首章。
- 商城/随机池结果未知时不重复消耗或重复发放。
- OpenArchiveService 无写入能力，槽 100 只由 SaveCoordinator 发布。
- 业务系统只能提交已注册 owner 的 section 变更；整槽、平台整数和公开槽写入均由 SaveCoordinator 串行编排。
- SaveStore 不声称跨槽 ACID；槽 1 最后提交和所有部分成功都可被识别并前向恢复。
- ClockService 只有 now；周期和赛季规则不进入 Y3 适配器。
- 未通过原子性和审计验证时，真实付费开关无法被启用。
- PlatformStore.reconcile 的 request/cursor hash 链和 Gacha 完整 audit tuple 未经实测验证时，相关能力不得从 unverified 提升为 available。
