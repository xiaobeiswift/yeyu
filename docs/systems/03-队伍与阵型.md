# 《雾州侠行》队伍与阵型系统工程规格

> 状态：实施中；离线切片已落地：`PartyAggregate` 编队/换位校验、`PartyPreset` 预设 save/apply/delete（每上下文最多 5 套）、`PartySaveCodec` 扁平 `preset_header_rows`/`preset_member_rows` 往返、FakePartyStore 预设集合、`PartyService` 预设 API 与可选 store/save_bridge、section 注册与 `HydrateGameRuntime` 导入。槽 5 编队操作收据（`PartyReceiptCodec` COMMITTED 扁平行 + `commit_formation`/`save_preset`/`apply_preset`/`delete_preset` 幂等）已落地；Y3 表现仍未开始。
>
> 上位约束：[00-通用工程约定](./00-通用工程约定.md)。角色拥有与可用性分别见 [01-角色与属性](./01-角色与属性.md)、[02-伙伴与好感](./02-伙伴与好感.md)。

## 1. 目标与非目标

### 1.1 目标

- 管理最多四名出战角色、3×3 己方阵位、队长、当前阵容和多套阵容预设。
- 对探索、剧情战、副本和擂台提供明确的阵容合法性规则及稳定排序的战斗快照输入。
- 支持拖放、点击换位、键鼠操作和预设切换；任何改动必须通过应用用例并持久化。
- 队员暂离、角色失效、装备/武学变化或关卡限制变化时能检测并显式修复，而非静默替换。
- 阵型系统只保存角色与阵位来源，不保存最终战斗属性。

### 1.2 非目标

- 不负责招募伙伴、修改角色属性、装备武学、执行战斗、发布擂台公开档案或加载 Y3 单位。
- 首章不提供同一角色分身、雇佣助战、玩家共享角色或超过四人的玩家出战队伍。
- 3×3 是逻辑阵位，不等同于地图坐标；世界跟随队列与战斗站位分别由表现适配器计算。
- 不允许 UI 在本地先改存档再补发命令；预览态与权威态严格分离。

## 2. 依赖与跨系统接口

### 2.1 上游依赖

| 系统 | 契约 |
|---|---|
| 角色系统 | 提供 `CharacterBuildView`、拥有状态、角色修订和构筑快照生成接口 |
| 伙伴系统 | 提供 `AVAILABLE/TEMPORARILY_UNAVAILABLE` 及原因 |
| 装备/武学系统 | 提供构筑合法性和修订；阵型不读取内部配置 |
| 关卡系统 | 提供 `PartyConstraintSet`，包括人数、必选/禁用角色、阵位和标签限制 |
| 存档服务 | 槽 3 修订式读写 |

### 2.2 下游接口

| 消费方 | 输出 |
|---|---|
| 战斗系统 | `FormationCombatInput`：稳定排序成员、阵位、队长、阵型加成引用、来源修订 |
| 探索系统 | 当前可见领队与跟随伙伴列表，不包含战斗派生属性 |
| 对话/任务 | 队内角色/队长/人数的只读条件查询 |
| 擂台 | 独立的 `ARENA_DEFENSE` 阵容快照；发布由擂台应用用例完成 |
| UI | 当前阵容、预设、非法原因、变更差异和保存结果 |

### 2.3 跨系统原则

- 队伍只能引用已拥有角色 ID；是否可出战必须在每次写入和开战前重新查询。
- `FormationChanged` 只表达已保存事实。擂台系统收到后可标记公开快照过期，但必须通过显式发布用例更新槽 100。
- 装备/武学变更不改阵型修订；构筑快照哈希包含其各自修订，避免误把阵型保存当作构筑保存。

## 4. 领域模型字段

### 4.1 `PartyAggregate`

| 字段 | 类型 | 约束 |
|---|---|---|
| `party_context` | enum | `PVE_MAIN/PVE_ALT/ARENA_DEFENSE`；首章至少前两者，擂台启用时增加第三项 |
| `leader_character_id` | string | 必须在成员中；普通 PVE 默认主角 |
| `member_rows` | ordered array | `1..4` 名，无重复角色、无重复阵位 |
| `formation_template_id` | string/null | 可空；非空引用已注册阵型模板 |
| `active_preset_id` | string/null | 最近应用的预设；后续手动修改可保留 ID 但标记 dirty |
| `is_dirty_from_preset` | boolean | 当前阵容是否偏离预设保存内容 |
| `revision` | integer | 成功持久变更加一 |

### 4.2 `FormationMember`

| 字段 | 类型 | 说明 |
|---|---|---|
| `character_id` | string | 已拥有且可用 |
| `position_index` | integer | `0..8`，唯一；编码见 4.3 |
| `entry_order` | integer | 首次加入队伍的稳定顺序，仅用于 UI/跟随；不能决定战斗先手 |
| `role_tag_override` | enum/null | 可选 `FRONTLINE/DAMAGE/SUPPORT`，只影响 AI 建议，不改属性 |

### 4.3 九宫格编码

己方视角按“前排到后排、上到下”编码：

| 排 | 上 | 中 | 下 |
|---|---:|---:|---:|
| 前排 | 0 | 1 | 2 |
| 中排 | 3 | 4 | 5 |
| 后排 | 6 | 7 | 8 |

战斗两方都使用己方视角编码；Y3 适配器负责把防守方镜像到世界坐标。领域层永不保存坐标、朝向或单位句柄。

### 4.4 `PartyPreset`

| 字段 | 约束 |
|---|---|
| `preset_id` | `preset_party_` 前缀；单玩家上下文唯一 |
| `display_name` | 0–12 个显示字符；空则使用本地化默认名 |
| `party_context` | 与要应用的聚合一致 |
| `leader_character_id` | 必须在预设成员中 |
| `member_rows` | `1..4`，与阵容相同约束 |
| `formation_template_id` | 可空 |
| `saved_source_revisions` | 角色可用性/配置版本摘要，仅用于提示，不阻止读取 |
| `revision` | 预设自身修订 |

每个上下文最多 5 套预设。预设保存角色和阵位，不复制装备/武学构筑；角色当前构筑在开战时读取。

### 4.5 `PartyConstraintSet`

字段：`constraint_id`、`min_members`、`max_members`、`required_character_ids[]`、`forbidden_character_ids[]`、`required_tags[]`、`forbidden_tags[]`、`allowed_positions[]`、`front_row_minimum`、`protagonist_required`、`leader_rule`、`guest_member_refs[]`（首章默认空）、`failure_message_key`。

### 4.6 `FormationCombatInput`

字段：`party_context`、`formation_revision`、`constraint_id`、`formation_template_id`、`leader_character_id`、按 `position_index, character_id` 排序的 `member_snapshots[]`、`formation_contributions[]`、`source_revision_map`、`rules_version`、`normalized_hash_input`。其中成员快照由角色系统生成，阵型系统不得修改其属性。

## 5. 配置字段

### 5.1 `FormationTemplateDefinition`

| 字段 | 必填/默认 | 校验 |
|---|---|---|
| `id` | 必填 | `formation_` 前缀、唯一 |
| `schema_version` | 必填 | `>=1` |
| `name_key/description_key` | 必填 | 本地化存在 |
| `allowed_positions` | 必填 | `0..8` 唯一整数，至少 4 个可用位或声明特殊用途 |
| `position_contribution_sets` | 默认空 | 阵位到角色系统标准贡献；不得嵌入公式脚本 |
| `adjacency_rule_ids` | 默认空 | 声明式相邻规则，无循环触发 |
| `unlock_rule_id` | 可空 | 引用系统条件配置 |
| `display_asset_id` | 必填 | 原创 UI 资源映射存在 |
| `deprecated` | 默认 `false` | 已保存预设继续可读取 |

首章可只提供“散阵”且不加属性；模块仍按同一契约实现，避免未来阵型加成侵入战斗。

### 5.2 `PartyContextDefinition`

字段包括：`context`、`max_members=4`、`preset_limit=5`、`default_formation_id`、`default_positions[]`、`default_leader_rule`、`protagonist_required`、`allow_temporarily_unavailable=false`、`auto_repair_policy`、`rules_version`。

自动修复策略首章固定为 `REMOVE_INVALID_AND_REQUIRE_CONFIRMATION`：可移除失效成员形成草稿，但不得自动补入其他角色或直接覆盖存档。

## 6. 运行时状态与状态机

### 6.1 编辑会话

`CLOSED → LOADING → EDITING_CLEAN ↔ EDITING_DIRTY → VALIDATING → SAVING → EDITING_CLEAN`

失败从 `LOADING/VALIDATING/SAVING` 进入 `ERROR`；修订冲突进入 `CONFLICT_RELOAD_REQUIRED`。只读模式允许 `EDITING_DIRTY` 预览，但提交按钮禁用且退出时明确丢弃草稿。

### 6.2 草稿与权威状态

- UI 操作只修改 `FormationDraft`：基础修订、成员差异、位置差异、领导差异。
- 保存时完整提交草稿目标状态，不提交“把 A 往右移动”这类依赖旧 UI 状态的隐式命令。
- 成功响应带新修订后替换权威状态；失败保留草稿供修正。

### 6.3 有效性状态

阵容视图可为 `VALID/INCOMPLETE/INVALID_MEMBER/CONSTRAINT_VIOLATION/STALE_SOURCE`。只有 `VALID` 可创建战斗快照。`INCOMPLETE` 可保存为预设，但不能设为当前可开战阵容；当前阵容至少一名成员。

## 7. 规则与状态转换

### 7.1 通用不变量

- 当前 PVE 队伍成员数 `1..4`；战斗限制可要求更多，但不可超过 4。
- 角色 ID 与阵位均唯一。领队必须在队内且可用。
- `PVE_MAIN` 默认要求主角在队且为队长；关卡若允许例外，必须给显式 `PartyConstraintSet`。
- 暂离、未拥有、配置断链或构筑非法的角色不能保存进当前有效阵容。
- 任意数组在哈希、保存和战斗输入前按明确键排序，不依赖添加顺序或 `pairs`。

### 7.2 放置、移动与换位

- 把队外角色放到空阵位：若未满员则加入；满员返回 `PARTY_MEMBER_LIMIT_REACHED`。
- 把队内角色移动到空位：只改其 `position_index`。
- 拖到已占位：默认原子交换两人位置；UI 必须显示交换预览。
- 把队外角色拖到已占位：必须显式选择“替换”；被替换者移出队伍，新角色使用该阵位。无确认不得执行。
- 移除领队时必须同时指定新领队；移除最后成员被拒绝。

### 7.3 阵型贡献

贡献只在构建战斗输入时根据模板和最终位置生成，来源 ID 为 `formation_id:position_index:rule_id`。角色系统按其贡献流水线处理。位置变化令 `FormationCombatInput` 哈希失效，但不改角色永久修订。

### 7.4 预设

- 保存预设是复制当前草稿目标状态；允许保存不满足特定关卡限制但满足通用结构的阵容。
- 应用预设前重新校验拥有/可用状态。若有失效成员，生成修复草稿和原因列表，不直接覆盖当前阵容。
- 删除当前已应用预设不改变当前阵容，只清空 `active_preset_id`。
- 预设重命名只改预设修订，不触发 `FormationChanged`。

### 7.5 暂离修复

收到伙伴暂离事实后，`EvaluatePartyIntegrity` 标记所有引用该伙伴的上下文。探索层可以暂时隐藏跟随单位，但当前阵容持久状态必须由 `RepairParty` 用例在玩家确认或剧情强制流程中修改。强制剧情修复仍使用收据，并禁止自动选择替代角色。

## 8. 应用用例

### 8.1 `GetPartyEditorState`

输入上下文、可选关卡限制 ID。前置为槽 3 及角色/伙伴来源读取成功；只读允许。输出权威阵容、五套预设、角色可用列表、每项禁用原因、当前合法性和基础修订。错误为 `PARTY_SAVE_UNAVAILABLE`、`PARTY_CONFIG_MISSING`。相同修订天然幂等。

### 8.2 `CommitFormation`

| 项 | 契约 |
|---|---|
| 输入 | 上下文、完整目标成员/阵位/队长/模板、可选限制 ID、预期修订、幂等键 |
| 前置 | 非只读；所有角色来源已读取；目标与预期修订对应 |
| 事务 | 规范化排序 → 校验角色/可用性/构筑/限制 → 写槽 3 → 记录收据 → 发布事件 |
| 输出 | 新阵容 DTO、差异、修订、合法性 |
| 错误 | `PARTY_DUPLICATE_MEMBER`、`FORMATION_POSITION_OCCUPIED`、`PARTY_MEMBER_UNAVAILABLE`、`PARTY_CONSTRAINT_VIOLATION`、`SAVE_REVISION_CONFLICT` |
| 幂等 | 相同键返回原结果；键相同而目标哈希不同返回 `IDEMPOTENCY_KEY_REUSED` |

### 8.3 `SavePartyPreset`

输入预设 ID（新建时由应用层生成）、名称、完整草稿、预期预设修订和幂等键。允许结构完整但不满足当前关卡的预设；不允许未知角色、重复位置或超过四人。输出预设和修订。错误包括 `PARTY_PRESET_LIMIT_REACHED`、`PARTY_PRESET_NAME_INVALID`、`PARTY_PRESET_CONFLICT`。

### 8.4 `ApplyPartyPreset`

输入上下文、预设 ID、当前阵容预期修订、幂等键。事务重新校验来源；完全合法则写当前阵容，存在失效成员则只返回 `repair_draft`，不写。错误/结果必须区分“预设不存在”“预设可修复”“当前修订冲突”。

### 8.5 `DeletePartyPreset`

输入预设 ID、预期修订和幂等键；删除预设，不删除当前阵容。默认系统预设若配置为不可删除则返回 `PARTY_PRESET_PROTECTED`。

### 8.6 `RepairPartyAfterAvailabilityChange`

输入上下文、失效事实 ID、目标修复阵容、预期修订、幂等键。前置为确有失效成员；目标仍遵循通用与当前剧情限制。事务显式保存并发布含原因的阵型变化。没有安全修复目标时允许保留不可开战状态，但探索系统必须给玩家编队入口。

### 8.7 `BuildFormationCombatInput`

| 项 | 契约 |
|---|---|
| 输入 | 上下文、`constraint_id`、`rules_version`、战斗种子上下文（不消耗随机）、各来源期望修订 |
| 前置 | 阵容有效；角色/装备/武学/伙伴来源修订一致 |
| 事务 | 全量重新校验 → 按位置生成阵型贡献 → 请求角色构筑快照 → 规范化并哈希；不持久化 |
| 输出 | `FormationCombatInput`、来源修订映射、规范化哈希 |
| 错误 | `PARTY_NOT_READY`、`PARTY_SOURCE_STALE`、`CHARACTER_BUILD_INVALID`、`PARTY_CONSTRAINT_VIOLATION` |
| 幂等 | 相同来源修订和 `rules_version` 输出字节级等价结果 |

## 9. 领域事件

| 事件 | 载荷 |
|---|---|
| `FormationChanged` | 上下文、旧/新规范化哈希、成员/位置/队长差异、原因 |
| `PartyLeaderChanged` | 上下文、旧/新队长；也包含在阵型变更中，供轻量消费者使用 |
| `PartyPresetSaved` | 预设 ID、上下文、内容哈希、是否新建 |
| `PartyPresetDeleted` | 预设 ID、上下文 |
| `PartyIntegrityBecameInvalid` | 上下文、失效成员和原因；应用事件，可重建 |
| `PartyRepaired` | 上下文、触发事实 ID、被移除成员、修复哈希 |

事件不携带最终属性或完整公开擂台档。任务/对话按事件 ID 去重；擂台只把相关阵容标记为待发布。

## 10. 存档 DTO、槽位与迁移

### 10.1 槽位归属

- 槽 `3` 保存当前阵容、阵位和预设。
- 槽 `5` 保存编队写入幂等收据和待处理修复提示。
- 槽 `100` 由擂台系统保存公开阵容副本；本系统不直接写。

### 10.2 扁平 DTO

| 字段 | 行结构 |
|---|---|
| `party_header_rows` | `context/leader_character_id/formation_template_id/active_preset_id/is_dirty/revision` |
| `party_member_rows` | `context/character_id/position_index/entry_order/role_tag_override` |
| `preset_header_rows` | `preset_id/context/display_name/leader_character_id/formation_template_id/revision` |
| `preset_member_rows` | `preset_id/character_id/position_index/entry_order/role_tag_override` |

槽子表自身带 `schema_version/revision`。排序为上下文、预设 ID、阵位、角色 ID。不得保存二维九宫格嵌套表、Y3 坐标、单位句柄或属性快照。

### 10.3 迁移

- 旧阵位编码必须通过显式版本映射转换；未知编码进入只读隔离。
- 从三人上限迁移到四人上限无需改现有成员；反向缩限必须先生成玩家确认的修复草稿，不自动删人。
- 弃用阵型模板时，已有阵容回退到无加成散阵兼容 ID，但须保留原 ID 诊断并只迁移一次。
- 重复/不可用成员不得在迁移中被替换；标记非法并引导修复。

## 11. Y3 适配与 UI

### 11.1 Y3 适配

- `FormationWorldMapper` 将逻辑位置映射为战斗区坐标；防守方镜像只在适配器内完成。
- 探索跟随按 `leader + entry_order` 生成视觉队列，跟随卡住只影响表现，不回写阵位。
- 战前预览创建临时 Y3 单位时必须使用独立生命周期，关闭界面/开战失败后清理；领域层不感知。
- 输入适配器把拖放、点击、快捷键统一转换为草稿操作，再由提交用例落盘。

### 11.2 UI

- 主区为 3×3 网格，清晰标注前/中/后排；候选角色显示拥有、可用、已上阵和禁用原因。
- 拖到占用位展示“交换”；队外角色覆盖时要求“替换”确认。
- 显示当前人数、队长、关卡限制、阵型说明、预设 1–5、未保存标记和来源失效警告。
- 提交态禁用所有写按钮；修订冲突提供“重新载入”和“复制当前草稿摘要”，不得强行覆盖。
- 只读状态可预览和试排，但保存/应用/删除禁用；退出明确告知草稿未保存。
- 低分辨率使用角色列表与网格分栏切换，键盘可遍历九宫格并执行放置/交换/移除。

## 12. 边界、失败与恢复

- 当前阵容槽读取失败时不得用默认主角阵容覆盖；进入只读恢复页。
- 提交保存超时后先按幂等收据或重读修订确认，不重复写入并触发事件。
- 角色在打开编辑器后暂离：提交时返回 `PARTY_MEMBER_UNAVAILABLE` 和最新原因，保留草稿。
- 预设应用与当前阵容发生修订冲突时不自动合并，因为位置交换可能语义冲突。
- 关卡限制在开战前更新时，旧编辑校验结果作废，必须重建 `FormationCombatInput`。
- 四人都位于后排等战术弱阵容只要配置允许即合法；系统不把推荐当硬限制。
- 阵型贡献断链时整个模板非法；禁止忽略缺失加成后继续正式战斗。

## 13. 生成与静态校验

必须检查：阵位范围/重复、模板至少支持上下文最大人数、贡献引用和属性键合法、限制集合自相矛盾、必选与禁用重叠、最少人数大于最大人数、默认阵容不可达、弃用模板兼容映射、预设限制和本地化/资源映射。

生成报告应列出：每个上下文默认阵容可用性、每种关卡限制至少一个满足样例、模板各位置加成、镜像坐标测试向量，以及首章五名角色构成的所有 1–4 人结构合法性统计。

## 15. 验收标准

- 玩家可用鼠标或键盘完成加入、移除、交换、换队长、保存和应用预设。
- 任何合法 1–4 人阵容都能稳定生成唯一规范化哈希；输入行顺序变化不影响结果。
- 不可用/未知/重复角色、重复阵位、关卡限制和构筑断链均在开战前拒绝。
- 五套预设在保存重进后保持一致；失效预设只生成修复草稿，不覆盖当前阵容。
- 阵型变化只保存槽 3，不泄漏最终属性；擂台公开档由独立流程发布。
- 保存失败、超时、只读和修订冲突不丢权威阵容、不重复发事件。
- Y3 镜像和世界跟随表现不会改变领域位置或战斗排序。
