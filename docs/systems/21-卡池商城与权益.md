# 《雾州侠行》卡池、平台商城与付费权益系统规格

> 状态：系统规划冻结候选稿；Foundation V1 的商城/随机池端口与安全门禁已落地
>
> 付费业务状态机与真实 Y3 适配尚未实现。真实付费卡池默认关闭；平台原子性、补偿、概率公示、实名/防沉迷和至少 90 天审计任一门禁未通过时不得开启。

## 1. 目标与非目标

### 1.1 目标

- 以 Y3 平台商城完成真实付费购买，以 Y3 服务器随机池产生付费抽取结果，客户端 Lua 不生成或指定结果。
- 提供角色池与武学池、跨同类型卡池继承的硬保底、重复内容转兑换凭证和确定性定向兑换。
- 付费角色/武学权益与抽取累计状态以平台专用单调整数槽为权威；私人角色/武学档只接收可重放的派生子收据，不保存平台余额镜像。
- 为商城回调、抽取、权益写入和私人档领取建立订单级幂等、结果查询、补偿及人工审计状态。
- 提供完整概率、奖品、保底、兑换、匿名抽取记录和适龄/未成年人限制入口。
- 将测试币卡池与真实付费卡池严格隔离，使未通过门禁时仍可验证玩法。

### 1.2 非目标

- 不接受客户端生成的随机数、抽取结果、订单金额、已付款标志或权益余额。
- 不实现玩家间赠送、权益转移、二级市场、退款套利或外部自建支付。
- 不承诺仅靠私人云存档满足付费审计；审计必须由平台可查询、可导出的受信记录提供。
- 首版不实现动态个性化概率、隐性概率调整、软保底或未公示的权重变化。
- 不把 NPC 商店、高级货币显示余额或 UI 动画作为付费权益权威。
- 不保存或消费可递减的“抽取凭证余额/兑换 token 余额”镜像；可用量一律由平台单调累计量之差派生。

## 4. 领域模型

### 4.1 BannerDefinition

| 字段 | 类型 | 约束 |
|---|---|---|
| banner_id | string | 唯一 banner_ ID |
| banner_type | enum | CHARACTER、MARTIAL |
| pity_group_id | string | 同组跨卡池继承 |
| probability_version | string | 每次发布不可变 |
| reward_pool_id | string | Y3 服务器随机池 ID |
| open_at、close_at | integer | 可信服务器时间 |
| draw_cost_product_id | string | 平台凭证/商品映射 |
| single_draw_cost | integer | 正整数 |
| multi_draw_count | integer | 默认 10，按序逐抽 |
| rarity_weights_ppm | list | 总和 1,000,000 |
| highest_rarity | string | 触发保底的稀有度 |
| hard_pity_count | integer | 角色 80，武学 60 |
| exchange_token_per_draw | integer | 每抽固定累计凭证 |
| duplicate_token_by_rarity | list | 重复额外转化 |
| exchange_catalog_id | string | 同类型定向兑换 |
| paid_only | boolean | 真实付费池标记 |
| audit_policy_id | string | 审计与展示策略 |

角色池最高稀有度基础概率固定为 2% 即 20,000 ppm，80 抽硬保底；武学池为 3% 即 30,000 ppm，60 抽硬保底。除硬保底抽外不改变基础概率；首版无软保底。

### 4.2 PityState（平台单调累计视图）

| 字段 | 类型 | 说明 |
|---|---|---|
| pity_group_id | string | CHARACTER 或 MARTIAL 对应组 |
| total_draws | integer | 平台单调累计的已确认抽数 |
| last_highest_draw_ordinal | integer | 平台单调累计；最近最高稀有度所在抽序号，初始 0 |
| exchange_tokens_earned_total | integer | 平台单调累计的已赚取兑换凭证 |
| exchange_tokens_spent_total | integer | 平台单调累计的已兑换消耗量 |
| counter_revision | integer | 平台 CAS 修订 |

派生值：draws_since_highest = total_draws - last_highest_draw_ordinal；exchange_tokens_available = earned_total - spent_total。若 draws_since_highest = hard_pity_count-1，则下一抽服务器池请求必须限定为最高稀有度的已公示保底池。命中最高稀有度时以 CAS 把 last_highest_draw_ordinal 前移到该抽的 total_draws，而不是“归零”可递减计数。十连按 10 次单抽顺序处理，不是一次聚合概率。

### 4.3 CredentialCounterState

| 字段 | 类型 | 说明 |
|---|---|---|
| credential_type | string | 对应商品与同类型卡池 |
| credential_granted_total | integer | 订单确认后平台单调增加 |
| credential_consumed_total | integer | 抽取授权成功时平台单调增加 |
| credential_refunded_total | integer | 仅平台确认“已消耗但无抽取结果”补偿时单调增加 |
| counter_revision | integer | 平台 CAS 修订 |

可用抽取凭证只按 granted_total + refunded_total - consumed_total 派生。三个累计量都不得下降；退款/补偿不得回减 consumed_total。任何私人表型存档和 UI 缓存都不得成为余额权威。

### 4.4 PaidEntitlementCursor

| 字段 | 类型 | 说明 |
|---|---|---|
| entitlement_id | string | ent_char_ 或 ent_martial_ |
| content_id | string | 对应角色或武学 |
| platform_slot_id | integer | 200–299 唯一映射 |
| platform_count | integer | 平台权威单调计数 |
| delivery_cursor | integer | 本系统已收到下游幂等确认的最大连续 entitlement ordinal |
| cursor_revision | integer | 槽 5 section 修订 |
| duplicate_policy | enum | TOKEN_ONLY 或 STACKABLE |
| last_reconciled_at | integer? | 可信时间 |

平台 count 不允许由游戏流程减少。PaidEntitlementCursor 仅由本文系统拥有并保存在槽 5；角色、武学、擂台或其他系统不得读写该游标，也不得维护第二份平台游标。

### 4.5 EntitlementDeliverySubReceipt

包含 subreceipt_id、entitlement_id、content_id、entitlement_ordinal、platform_revision、target_owner_system、state 和 applied_receipt_digest。subreceipt_id 由 entitlement_id + entitlement_ordinal 规范派生。角色/武学 owner 幂等应用同一子收据并保存正常内容所有权；本系统收到其已持久化确认后才推进连续 delivery_cursor。中断时重发同一 subreceipt_id，不创建新权益。

用于竞技来源向量时，本系统可派生只读 EntitlementCursorAttestationReceipt，仅含 cursor_revision 与规范摘要，不含 platform_count、订单或付费数值。竞技系统只消费该派生收据，不获得 PaidEntitlementCursor 的读取或写入权；游标唯一 owner 仍是本文系统。

### 4.6 PaidTransaction

| 字段 | 类型 | 说明 |
|---|---|---|
| transaction_id | string | 全局唯一，不由 UI 重试时更换 |
| order_id | string? | 平台订单 ID |
| request_key | string | 随机池业务幂等键；由 transaction_id/draw_index 派生，并写入端口 `context.idempotency_key` |
| banner_id、probability_version | string | 抽取时固定 |
| draw_count | integer | 1 或允许的多抽数 |
| state | enum | 见状态机 |
| platform_counter_before/after | list | credential、total_draws、last_highest ordinal、token earned/spent 的值与 CAS 修订摘要 |
| result_entries | list | 顺序、reward_id、rarity、duplicate |
| entitlement_deltas | list | 槽 ID 与增量 |
| exchange_tokens_earned_delta / spent_delta | integer | 本事务两个方向各自的非负累计量推进值，不是余额 |
| audit_record_id | string? | 平台审计记录 |
| failure_code | string? | 稳定错误码 |

### 4.7 AuditRecord

至少包含：匿名玩家标识、transaction_id、平台 `order_ref`、稳定抽取 `request_key`、每次端口调用的诊断 `request_id`、服务器时间、banner_id、概率版本、抽数、每抽顺序结果、平台单调计数前后及 CAS 修订、权益槽变化、子收据交付摘要、最终状态、补偿链和平台环境。客户端日志不能替代该记录。

## 7. 概率、保底与重复规则

### 7.1 单抽决策

应用层只决定本抽是否为 HARD_PITY 请求以及使用哪个已公示服务器池，实际 reward 由 GachaService 返回。普通抽使用基础池；硬保底抽使用仅含最高稀有度且概率已展示的保证池。

服务器确认结果必须返回完整审计元组：`status=CONFIRMED`、`pool_id`、`request_key`、`probability_version`、`result_id`、`trusted_unix_seconds`、`platform_code=SUCCESS` 和有序 `rewards`。`request_key` 必须等于本次端口调用的 `context.idempotency_key`，pool 与概率版本必须等于请求中的期望值。任何缺项、绑定不一致、结果不在配置白名单或奖励顺序/唯一性非法时进入 RESULT_UNKNOWN/MANUAL_REVIEW，不能自行换结果。

这里的 `request_key` 是跨重试保持不变的业务抽取身份；22 的 `context.request_id` 只标识一次传输调用。每次查询或重试必须创建新的 `context.request_id`，但沿用同一个 `request_key`，不得把两者混为一个字段。

### 7.2 多抽

- 先固定一次 transaction_id 和 draw_count。
- 按 index 1..draw_count 串行推进保底状态。
- 每一抽使用 transaction_id/index 派生的唯一 request_key。
- 中途结果未知时停止后续抽取并恢复该 index；不得跳过后继续。
- UI 动画可批量播放，但审计和领域结果保持逐抽顺序。

### 7.3 重复与兑换

- 首次获得使平台 entitlement count 从 0 增至 1。
- 重复获得仍写入受信结果，并按 rarity 通过 CAS 增加 exchange_tokens_earned_total；是否增加 entitlement count 由 duplicate_policy 固定。
- 每次有效付费抽取额外单调增加 exchange_tokens_earned_total，保证长期存在确定性兑换路径。
- 兑换不是随机行为；可用量由 earned_total-spent_total 派生，兑换通过 CAS 增加 exchange_tokens_spent_total，再幂等增加目标 entitlement 槽，绝不减少余额字段。
- PaidEntitlementCursor 发现 platform_count-delivery_cursor 的正差后按 ordinal 派生子收据。角色/武学 owner 幂等应用，确认后游标才前移；重复对账不得重复创建内容。

## 8. 付费事务、原子性与补偿

### 8.1 状态机

CREATED → CREDENTIAL_CAS_PENDING → CREDENTIAL_CONSUMED → DRAW_REQUESTED → RESULT_CONFIRMED → COUNTERS_ADVANCING → ENTITLEMENT_WRITING → AUDIT_CONFIRMED → COMMITTED。

异常状态：

- RESULT_UNKNOWN：请求可能已执行，必须按相同 request_key 查询。
- ENTITLEMENT_PENDING：结果已确认但权益尚未确认。
- AUDIT_PENDING：结果及权益已确认但受信审计未确认。
- COMPENSATION_PENDING：具备确定补偿依据。
- MANUAL_REVIEW：无法证明应发、应退或应重试。
- COMPENSATED：补偿完成并有审计链。
- CANCELLED：仅 credential_consumed_total 尚未增加，且平台确认订单/抽取均未发生时。

### 8.2 单调计数事务顺序

1. SaveCoordinator 串行查询原 transaction/request_key 及整组平台整数值与 CAS revision；重试先查询原请求，不生成新 transaction_id。
2. 计算 credentials_available = granted_total + refunded_total - consumed_total。足够时以 transaction_id 派生幂等键，CAS 正向增加 credential_consumed_total；冲突后重新查询，不盲目重复增量。
3. 每一抽以固定 request_key 作为 `context.idempotency_key` 调用 GachaService，并显式提交 `expected_probability_version`；结果未知时只调用 `query_pool_request(original_request_key, expected_pool_id, expected_probability_version)`。
4. 结果确认后，以有序 step receipt 和 CAS 推进 total_draws、必要时把 last_highest_draw_ordinal 前移到该抽序号、增加 exchange_tokens_earned_total，并增加目标 entitlement count。每个 step 结果未知都查询原 CAS request/idempotency key。
5. 平台累计量确认后，由本文唯一的 PaidEntitlementCursor 派生子收据给角色/武学 owner；子收据落盘与游标推进通过各自 section owner 和 SaveCoordinator 前向完成。
6. 审计确认后提交事务。任何阶段都不创建可递减余额镜像，也不通过反向写 counter 假装回滚。

订单授予凭证同样只 CAS 增加 credential_granted_total。补偿只在平台证明“consumed 已增加而原抽取不存在”时 CAS 增加 credential_refunded_total，不减少 consumed_total。

### 8.3 原子性门禁

真实付费卡池只有在 Y3 能证明以下任一能力时可开启：

1. 平台提供“扣抽取凭证—产生结果—写权益/计数”的单一原子事务；或
2. 每一步均支持稳定 request_key、原 CAS 请求查询和单调幂等写，使进程崩溃后能确定恢复到唯一结果，且任何中间态不会吞单或重复发放。

仅有客户端 Lua 收据、仅能重试但不能查询原请求、或随机池重试会产生新结果，均判定门禁失败。

### 8.4 补偿规则

- credential_consumed_total 未增加且无结果：安全取消。
- consumed_total 已增加、原 request_key 明确无结果：平台允许时单调增加 credential_refunded_total，并写补偿审计；不得回减 consumed_total。
- 结果已确认、权益未写：只重试原权益增量，禁止重新抽取。
- 权益已写、子收据未确认：运行 ReconcilePaidEntitlements 并重发同一 subreceipt_id，不再写平台权益。
- 结果状态未知：不得退款、补抽或手工猜测，进入 RESULT_UNKNOWN/MANUAL_REVIEW。
- 重复平台回调：按 order_id、request_key 返回原结果。
- 退款后的权益撤销只有平台具备受信逆向权益流程时才允许；普通游戏存档不得自行扣除已获角色/武学。

平台整数槽、槽 5 cursor、角色/武学槽 3 所有权和审计系统之间不承诺跨存储 ACID，也不承诺“失败后全部回滚”。PaidTransaction 的有序步骤、原请求查询、CAS 收据与固定子收据用于前向恢复。

## 11. 存档 DTO 与槽位

### 11.1 平台权威整数槽

| 范围 | 用途 |
|---:|---|
| 200–299 | 付费角色/武学 entitlement count；一个 entitlement_id 固定映射一个槽 |
| 300–319 | credential_granted/consumed/refunded_total、total_draws、last_highest_draw_ordinal、exchange_tokens_earned/spent_total 和必要限购累计计数 |

正式配置生成前必须证明槽数量足够、整数范围安全、所有值只单调前进，且平台 API 支持 CAS、幂等键和原 CAS 请求查询。槽映射发布后不可复用。300–319 不保存 draws_since_highest、可用抽取凭证、可用兑换 token 或任何可递减余额；它们只能由累计 totals 计算。

### 11.2 私人云档与 section owner

- 槽 5 paid_transactions section（本文唯一 owner）：transaction_id、平台 order_ref 摘要、稳定 request_key、有序步骤、状态、结果摘要、recovery queue、兑换收据和审计记录引用；单次调用 request_id 只进入有界诊断/审计，不作为恢复身份。
- 槽 5 paid_entitlement_cursor section（本文唯一 owner）：每个 entitlement 的 last_observed_platform_count、delivery_cursor、cursor_revision 和未确认 subreceipt_id。
- 槽 3 不保存本文拥有的 mirror/cursor。它只保存由 01 角色或 04 武学等各自 section owner 管理的普通内容所有权及已应用 child receipt ID；本文不得直接写这些 section。
- 私人档不得把自身数值反向覆盖平台权益或累计计数槽。其他系统只接收派生的 EntitlementDeliverySubReceipt，不接收平台 cursor 的读写权。

本文对槽 5 的所有权只到上述两个 section，不拥有整个槽 5。所有槽 5 与下游槽 3 写入均由 SaveCoordinator 按 SectionOwnerRegistry 合并；跨 section 只用固定子收据前向恢复，不假设跨槽原子回滚。

若槽 300–319 无法完整承载保底与兑换状态，不能静默移到可篡改的普通私人档后开启付费池；必须判定平台门禁失败或补充合规服务。

## 12. Y3 适配与 UI

### 12.1 Y3 适配风险验证

- 商城：商品、订单 ID、支付成功/取消/失败、重复回调、补单查询、退款通知。
- 随机池：服务器权威、request_key 幂等、原结果查询、概率版本、批量/顺序能力。
- 权益/累计槽：整数范围、CAS/compare-and-add、原请求查询、并发冲突、幂等键和身份绑定；负增量或无条件覆盖必须不可用。
- 审计：至少 90 天受信保存、查询与导出；包含概率版本、结果、权益和补偿链。
- 合规：实名、防沉迷、未成年人消费限制及紧急关停由平台真实能力证明。
- 以上证据必须来自实机/平台文档和故障注入记录，不能以客户端日志替代。

### 12.2 UI

- 卡池页首屏显著展示完整奖励入口、各奖励概率、保底规则、当前保底计数、重复转化和定向兑换。
- 概率页固定展示 probability_version 和生效时间。
- 购买按钮使用平台返回商品信息；Lua 不自行拼接权威价格。
- 抽取提交后进入不可重复点击状态；超时显示“结果确认中”，保留原 transaction_id。
- 动画只在结果确认后播放；跳过动画不影响结果或权益领取。
- 记录页展示受信匿名抽取历史、补偿状态和查询失败说明。
- 未成年人限制、实名失败、审计不可用、平台维护和紧急关闭均隐藏或禁用付费入口。
- TEST_GACHA 使用明显测试币标识，不得复用付费商品、权益槽或伪装真实购买。

## 13. 合规与上线门禁

PAID_GACHA 只有以下全部为 PASS 才能从默认关闭改为开启：

1. 完整奖励、概率、保底、重复转化和兑换规则可在抽取前显著查看。
2. 客户端展示与服务器随机池 probability_version 自动比对一致。
3. 订单、随机结果、权益和保底状态具备原子性或可证明的唯一恢复路径。
4. 至少 90 天受信抽取审计可查询和导出，且补偿链可追踪。
5. 平台实名、防沉迷、未成年人消费限制和适龄提示已验证。
6. 紧急关闭不会中断既有事务恢复；关闭后禁止新交易。
7. 概率、运营、法务和平台审核的发布检查表均完成。

任一项从 PASS 变为 UNKNOWN/FAILED 时立即停止新付费抽取，旧事务进入恢复队列。具体法律适用和公示形式仍须由发行与合规审核确认。

## 14. 边界与失败

- banner 在购买后、抽取前关闭：已取得的通用凭证保留；是否允许完成原池由配置和公示规则决定，不能临时改概率。
- 多抽第 k 抽未知：停止 k+1 以后请求；只查询 k 的原 request_key。
- probability_version 不一致：禁止抽取，不自动接受新版本。
- 平台 entitlement count 小于本文唯一 delivery_cursor 或 last_observed_platform_count：视为严重异常，禁止反向扣内容并进入人工复核。
- 抽取凭证不足统一返回 GACHA_CREDENTIAL_INSUFFICIENT；不得复用普通经济系统的 COST_INSUFFICIENT，以免 UI 采用错误的重试或购买恢复路径。
- 整数槽溢出或映射重复：生成/运行时均阻止。
- 权益已确认但 AuditRecord 未确认：不回滚权益，状态为 AUDIT_PENDING，并暂停新付费抽取。
- 服务器随机池返回未知 reward_id：不映射为其他奖励，进入人工复核。
- 回调晚于 UI/地图销毁：事务协调器继续处理，不能访问失效节点。
- 本地时间、UI 参数、客户端余额镜像和网络重放均不能改变概率、平台累计量或付费结果。

## 15. 生成与静态校验

- 每个 banner_id、probability_version、pool_id、product_id、entitlement_id 和槽映射唯一。
- 普通池 rarity_weights_ppm 与各层奖励权重精确合计 1,000,000。
- 角色最高稀有度基础概率为 20,000 ppm、hard pity=80；武学为 30,000 ppm、hard pity=60。
- pity_group 内 hard pity、最高稀有度和计数语义一致。
- 平台 paid counter 只能是单调 totals；不得生成 balance、draws_since_highest 或 token_available 的权威槽映射。
- PaidEntitlementCursor 只注册给本文系统；角色/武学 section 只注册其普通所有权与 child receipt，不得重复注册平台游标。
- 所有付费独占内容存在可达的确定性兑换 offer。
- 多抽逐抽模拟在所有 pity 初值下不越界。
- 槽 200–319 数量和最坏计数不超过 Y3 实测边界。
- 客户端展示清单与服务器池导出清单、权重和版本完全一致。
- deprecated 奖励不可仍留在活动服务器池；历史记录仍可解析。
- 配置不得包含未公示软保底或按玩家动态调整权重的字段。

| 类别 | 必测场景 |
|---|---|
| 概率配置 | 权重总和、展示/服务器差异、版本不一致 |

| 重复兑换 | 首次、重复、固定每抽 earned_total、CAS 增加 spent_total、定向兑换和限购 |
| 幂等/CAS | 重复订单回调、重复 request_key、原 CAS 查询、同 transaction 不同输入、并发 revision 冲突 |
| 故障注入 | credential CAS 前后崩溃、结果响应丢失、累计计数/权益写失败、审计失败；不得依赖跨槽回滚 |
| 对账 | platform_count 高于游标、同 child receipt 重发/重复应用、平台低于游标、并发回调、21 为唯一 cursor owner |

必须以两个真实测试账号和平台沙盒完成端到端故障测试；Fake 测试不能代替平台能力证明。

## 17. 验收标准

- 客户端无法指定付费随机结果，所有确认结果均可追溯到 Y3 服务器随机池 request_key 与 result_id。
- 角色 2%/80 抽、武学 3%/60 抽及跨同类型继承通过边界测试。
- 重复权益和每抽累计凭证能形成公开、确定的付费独占兑换路径。
- 任意重复回调、重试、崩溃和重进不会吞单、重抽或重复发权益。
- 付费凭证、抽数、保底序号与兑换凭证只由平台单调 totals 表达，CAS 冲突与原请求查询不会形成可递减余额镜像。
- 平台权益计数通过槽 5 唯一 PaidEntitlementCursor 和固定 child receipt 与角色/武学所有权幂等对账。
- 玩家在抽取前可查看完整概率、保底、兑换和当前计数。
- 至少 90 天审计、实名/防沉迷、未成年人限制和紧急关闭有平台证据。
- 未满足全部门禁时，真实付费卡池在发布配置和运行时都保持关闭，仅测试币卡池可用。
