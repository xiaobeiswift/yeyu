# 《雾州侠行》确定性战斗与 AI 工程规格

> 状态：实施候选稿；仅描述未来实现，不代表代码已经存在。
>
> 上位约束：[00-通用工程约定](./00-通用工程约定.md)。战斗输入来自 [01-角色与属性](./01-角色与属性.md)、[03-队伍与阵型](./03-队伍与阵型.md)、[04-武学系统](./04-武学系统.md)，效果执行遵循 [05-状态与效果](./05-状态与效果.md)。

## 1. 目标与非目标

### 1.1 目标

- 实现纯 Lua、无 Y3 依赖、可在 Lua 5.1 下独立运行的速度驱动半自动战斗内核。
- 普通攻击自动执行；剧情/PVE 战允许在角色行动决策点手动选择绝招或切换全自动；擂台强制全自动。
- 相同规范化双方快照、规则版本、种子和有序命令流产生完全相同的状态、随机消耗、事件流及事件哈希。全自动战斗不需要外部命令，因此仅快照和种子即可复现。
- 战斗内核只输出事件和结果，Y3 单位只负责模型、动画、特效、声音、血条和输入表现。
- 支持最多双方各四名正式战斗者、3×3 阵位、状态/护盾/控制、首领阶段、召唤请求、超时及可配置 AI。

### 1.2 非目标

- 不实现实时联机同步、帧同步、服务器战斗、玩家交易、观战联网或战斗中换装备/武学。
- V1 不支持战斗内使用背包道具、快捷栏药品或任何临时消耗品；物品系统只能在 `WORLD/NO_COMBAT` 上下文使用道具。
- 不从 Y3 单位属性、动画结束时间、UI 帧率、本地时钟或 `math.random` 读取权威结果。
- 首发不保存战斗中断点；异常退出返回开战前安全点，只有结算事务可写永久进度。
- 本系统不决定关卡奖励、任务推进、擂台积分或付费权益，只提供经校验的 `CombatResult`。

## 2. 依赖与跨系统接口

### 2.1 上游输入

| 系统 | 输入契约 |
|---|---|
| 队伍与阵型 | 攻方 `FormationCombatInput`，成员按逻辑阵位稳定排序 |
| 敌人/关卡 | 防方/增援快照、胜负条件、场景机制、规则版本和奖励引用 |
| 角色属性 | 已本地重算的 `CombatantStatBlock` 与来源哈希 |
| 武学 | `MartialLoadoutSnapshot`、`MoveRuntimeSpec[]`、被动钩子、AI 元数据 |
| 状态与效果 | 效果执行、状态集合、触发调度与原子状态差异 |
| 显式随机源 | 规范种子 `1..2147483646`；领域层唯一随机入口 |

战斗输入不包含实时背包、道具数量、快捷栏或物品效果。应用层不得为了“只读展示”把槽 4 内容冻结进战斗快照。

### 2.2 下游输出

| 消费方 | 输出 |
|---|---|
| 表现层 | 按 `sequence` 排序的 `CombatEvent[]` 与当前展示快照 |
| 关卡/奖励/任务 | `CombatResult`、关卡 ID、胜负原因、参与者与事件哈希 |
| 擂台 | 全自动结果、进攻胜负、规则/快照/命令哈希、违规诊断 |
| 测试/复盘 | 初始快照、种子、命令流、最终状态摘要、PRNG 消耗数和哈希 |
| UI/AI 调试 | 决策请求、候选动作、拒绝原因、AI 命中规则（正式日志可降采样） |

### 2.3 边界

- 战斗内核可调用效果领域服务，但不能调用存档、奖励、任务、排行榜、商城、服务器时间或 Y3 API。
- 应用层只在 `CombatFinished` 后启动结算；表现播放未结束不影响领域结果，但结算 UI 可等待关键事件播放。
- 公开擂台快照是不可信输入，必须由擂台适配流程重建角色/武学/装备派生属性后才形成战斗输入。
- 背包、快捷栏、Y3 物品触发器和 UI 不得绕过 `CombatCommand` 直接调用效果执行器。V1 任意战斗道具入口都在应用边界稳定拒绝，不读取或扣除背包，也不改变战斗状态。

### 4.5 `CombatCommand`

| 字段 | 说明 |
|---|---|
| `command_id` | 战斗内唯一幂等键 |
| `combat_id` | 目标战斗 |
| `expected_revision` | 乐观并发修订 |

`USE_ITEM`、`ITEM`、`QUICK_SLOT` 及其任何别名都不是 `CombatCommand` 枚举成员。通用输入网关遇到这些保留值时必须返回 `COMBAT_ITEM_USE_UNSUPPORTED`；其他未知值返回 `COMBAT_COMMAND_TYPE_UNSUPPORTED`。两类拒绝都发生在领域命令反序列化前，不创建效果、不消费 PRNG、不推进 `revision/sequence`，也不进入 `command_hash/event_hash`；相同 `command_id + payload_hash` 重试返回相同错误，不同载荷复用 ID 返回 `IDEMPOTENCY_KEY_REUSED`。

字段：`outcome`（`ATTACKER_WIN/DEFENDER_WIN/ATTACKER_FORFEIT/TIMEOUT/INVALID_RULE_EXECUTION`）、`winner_side`（规则错误可空）、`finish_reason`、`action_count`、`final_tick`、`survivor_rows[]`、`snapshot_hash`、`command_hash`、`event_hash`、`prng_draw_count`、`rules_version`、`diagnostics[]`。奖励系统只接受允许的正常结果；`INVALID_RULE_EXECUTION` 不发正常奖励。

## 6. 战斗状态机

### 6.1 主状态

`CREATED → INITIALIZING → RUNNING → DECISION_REQUIRED ↔ RUNNING → FINISHING → FINISHED`

任一不可恢复规则错误进入 `INVALID`，随后生成 `INVALID_RULE_EXECUTION` 结果。玩家放弃从 `RUNNING/DECISION_REQUIRED` 进入 `FINISHING`。终态不可再接收改变状态的命令。

### 6.2 初始化

1. 校验快照 Schema、`rules_version`、双方人数/阵位/ID/来源哈希。
2. 初始化 PRNG；`state=seed`，消耗数为 0，`sequence_cursor=1`；先手偏好由种子奇偶直接派生。
3. 按稳定 actor 顺序创建运行态，`hp=max_hp`、`qi=initial_qi`、`gauge=0`。
4. 安装初始被动/状态，按稳定顺序处理 `COMBAT_STARTED` 效果。
5. 排空效果队列并检查胜负；无终局则进入 `RUNNING`。

### 6.3 推进边界

`ADVANCE` 自动运行，直到以下任一边界：需要玩家绝招决策、战斗结束、规则错误、事件输出达到应用层单批上限。批上限只切分响应，不改变内核逻辑；下一次推进从相同状态继续。

## 7. 确定性随机与规范化

### 7.1 子种子隔离与 PRNG

一次 Encounter/run 只保存一个可信 `root_seed`。应用编排必须用版本化 `DeriveSeedV1(root_seed, namespace, context_id)` 派生互相隔离的子流：命名空间枚举只允许小写 ASCII `combat` 与 `reward`。`combat` 的 `context_id` 固定为 `run_id`，擂台可使用挑战收据 ID；`reward` 的 `context_id` 由奖励 owner 按 10 的规范生成，必须是已校验的派生 ID。派生算法冻结如下：

1. 校验 `root_seed` 在 `1..2147483646`，把它作为初始 `state`。
2. 按 UTF-8 字节遍历 `decimal(root_seed) + NUL + namespace + NUL + context_id`；十进制根种子不带前导零，`NUL` 是单字节 `0x00`。
3. 每个字节 `b` 执行 `state = (state × 48271 + b + 1) mod 2147483647`；遍历结束若为 0，则规范为 1。
4. `namespace=combat` 的结果写入 `CombatSnapshot.seed`；`namespace=reward` 的结果只交给关卡/奖励结算器。派生算法版本进入 run 的来源哈希，升级必须新建版本和黄金向量。

战斗内核只能看到 `combat` 子种子。它不得接收 `reward_seed`，也不得把战斗结束时的 `prng_state/prng_draw_count` 交给奖励抽取；奖励系统同样不得继续消费战斗 PRNG。奖励抽样次数、掉落表变化和补发重试因此不会改变任何 `CombatEvent`、`command_hash` 或 `event_hash`。付费随机池禁止使用这两个本地子流。

固定使用 Park–Miller 最小标准：模数 `2147483647`、乘数 `48271`、状态范围 `1..2147483646`。每次原始抽样把状态更新为 `(state × 48271) mod 2147483647`。Lua 5.1 双精度整数精确范围足以覆盖该乘积；实现仍需黄金向量验证。

均匀区间 `0..n-1` 使用拒绝采样：令原始零基值为 `state-1`，接受范围为小于 `floor(2147483646 / n) × n` 的值，超出则继续抽取，最终取模。禁止直接对任意区间使用有偏 `% n`。

### 7.2 随机消费规则

- 概率为 0 或 10000 不消费抽样；中间概率消费恰一次，`roll 0..9999 < chance_bp` 成功。
- 目标随机、伤害浮动、暴击、格挡分别消费独立的有序抽样；是否消费由前置结果决定并写事件诊断。
- AI 默认不随机；明确 `RANDOM_N/WEIGHTED` 时必须先稳定排序候选再抽样。
- 表现、日志采样和 UI 预览不得共享战斗 PRNG。
- 道具入口在命令反序列化前拒绝，因此永远不消费战斗或奖励子流。

### 7.3 规范化与哈希

- 所有 map 转为按键升序的行；集合按文档指定键排序；缺省值显式补齐。
- 哈希输入编码固定字段顺序、UTF-8、整数十进制和布尔字面量；不包含内存地址、Y3 Key或本地时间。
- 最终事件哈希包含所有改变战斗状态的事件与已成功反序列化领域命令产生的拒绝事件；V1 道具/未知类型在应用边界的拒绝不是 `CombatEvent`，不进入哈希。纯表现完成回调同样不进入哈希。
- 全自动契约为“快照+种子决定结果”；手动战为“快照+种子+有序命令流决定结果”。命令流本身计算 `command_hash` 并随结果保存摘要。

## 8. 时间轴、行动与 AI 规则

### 8.1 速度槽

对每个 `ALIVE` 且可获得行动机会的角色，计算：

`ticks_to_ready = ceil((1,000,000 - gauge) / max(1, speed))`

取最小值 `delta`，把所有相关角色的 `gauge` 更新为 `min(1,000,000, gauge + speed × delta)`，`current_tick += delta`。所有达到阈值者按以下键选择一人：

1. 是否为种子指定优先方；优先方在前。
2. 当前逻辑阵位 `position_index` 升序。
3. `actor_id` 字典序。

角色行动完成（含被眩晕跳过）后其 `gauge -= 1,000,000`，并令 `action_index += 1`。同刻其他已满槽角色下一次以 `delta=0` 行动。速度变化从下一次推进立即生效。

### 8.2 行动流程

1. 选择行动者并发布 `ActorReady`。
2. 执行 `BEFORE_ACTION` 触发；若角色在此过程中倒地则结束其机会。
3. 解析控制：眩晕等可产生 `ActionSkipped`，仍消耗一次行动机会。
4. 生成合法主动绝招候选。
5. 全自动/敌方调用 AI；手动绝招模式若存在候选则进入 `DECISION_REQUIRED`。玩家可选招式或 `PASS_ULTIMATE`。
6. 未使用绝招时自动选套路普通攻击；若被缴械且无替代动作则跳过。
7. 再次验证目标、聚气、冷却和状态；成功后扣成本、设冷却、执行效果。
8. 处理死亡、召唤、阶段与胜负；结算 `ACTION_FINISHED`、持续时间和冷却。
9. 再次检查胜负；若 `action_index=99` 且无胜负，按超时结束。

### 8.3 冷却

招式成功使用时设为配置 `action_cooldown`。在该角色以后每次行动机会完整结束时，其他处于冷却的招式减 1；刚使用的招式本次不立即递减。冷却为 0 才可选。`initial_cooldown` 在初始化时设置。

### 8.4 聚气

聚气范围 `0..max_qi`。招式成功锁定目标后先扣成本。获得聚气只来自招式/效果明确配置的 `MODIFY_QI`，例如普攻命中、受击或内功触发；统一执行 `actual_gain = floor(base_gain × qi_gain_bp / 10000)` 并钳制。系统不隐式每秒回复。

### 8.5 前后排与目标

- `MELEE + frontline_blocking=true` 的敌方单体目标：只要敌方前排 0–2 有合法存活目标，就不能选择中/后排。
- 远程/全局可跨排；嘲讽若适用，先把候选限制为合法嘲讽者。
- 自动目标候选统一按“规则评分降序、生命比例升序/降序（视规则）、阵位、actor ID”排序。
- 手动传入目标也必须满足相同规则；非法目标命令不消耗聚气、不推进战斗。

### 8.6 命中、伤害、暴击与格挡公式

非 `UNMISSABLE`：

`hit_bp = clamp(8000 + attacker.accuracy - target.evasion + spec.hit_bonus_bp, 2000, 9800)`

按概率规则判定；未命中结束该目标的伤害链，不判暴击/格挡/浮动。

命中后固定顺序：

1. `base = max(0, floor(attacker.attack × attack_ratio_bp / 10000) + flat_damage)`。
2. `effective_defense = floor(max(0, target.defense - penetration_flat) × (10000 - penetration_bp) / 10000)`。
3. 非真实伤害：`mitigated = floor(base × 10000 / (10000 + effective_defense × defense_scale))`；真实伤害为 `base`。
4. `after_bonus = floor(mitigated × max(0, 10000 + attacker.damage_bonus_bp + spec.damage_bonus_bp) / 10000)`。
5. `after_reduction = floor(after_bonus × max(0, 10000 - target.damage_reduction_bp) / 10000)`。
6. 在配置区间均匀抽整数倍率，`after_variance = floor(after_reduction × variance_bp / 10000)`；上下限相等时不抽样。
7. 若可暴击，`crit_bp=clamp(attacker.crit_chance_bp-target.crit_resist_bp+spec.crit_bonus_bp,0,7500)`；成功后乘 `clamp(attacker.crit_damage_bp+spec.crit_damage_bonus_bp,10000,30000)`。
8. 若可格挡，`block_bp=clamp(target.block_chance_bp,0,7500)`；成功后乘 `max(0,10000-target.block_reduction_bp)`。
9. 若 `base>0`，最终至少为 `minimum_damage`；随后由护盾按状态规则吸收，余量扣生命。

每一步向下取整并记录公式版本。中间值必须受整数安全检查。减伤超过上限已由角色属性钳制。

### 8.7 治疗

`base_heal = max(0, floor(source[source_stat_key] × stat_ratio_bp / 10000) + flat_healing)`，依次乘来源 `healing_bonus` 与目标 `healing_received`，每步向下取整。实际治疗不超过 `max_hp-current_hp`；溢出仅在配置显式时转护盾。

### 8.8 AI 决策

每份 `AIProfile` 含有序规则。规则字段：`rule_id`、优先级/表内顺序、动作选择（具体招式或标签）、自方/敌方生命阈值、聚气范围、状态条件、目标数量条件、行动计数、机制标记、保留聚气下限、目标评分配置。执行：

1. 生成当前合法动作集合，按 `move priority, move_id` 排序。
2. 从上到下检查 AI 规则，首个同时满足且能选出合法动作/目标的规则胜出。
3. 若规则指定标签，选招式按配置优先级、聚气成本、move ID 稳定排序。
4. 目标按目标规则评分和稳定键选择；无合法目标则继续下一规则。
5. 无规则命中时使用合法普通攻击；仍无动作则跳过。

AI 不读取对方隐藏配置、未来随机数、UI 状态或本地时间。调试事件记录命中规则和未命中原因；正式可只保留规则 ID。

## 9. 胜负、死亡与超时

- `current_hp` 降到 0 时进入 `DOWNED`，立即发布事件并处理倒地触发；同一效果链结束后检查阵营存活。
- 一方没有任何可计入胜负的 `ALIVE` 正式成员/召唤物时败北；不计入胜负的装饰/机制单位忽略。
- 双方在同一效果链全灭按进攻方失败：PVE 为 `DEFENDER_WIN`，擂台亦为防守方胜。
- 行动机会完整结算达到 99 且无胜负：`TIMEOUT`，PVE 失败、擂台进攻方失败。
- 玩家放弃：`ATTACKER_FORFEIT`；是否消耗关卡尝试/给安慰奖励由关卡结算规则决定。
- 规则错误、预算超限、非法快照只生成 `INVALID_RULE_EXECUTION`，不得按普通战败扣排行分或发胜负奖励；擂台由上层安全策略处理。

## 10. 应用用例

所有战斗输入先经过一个通用命令网关：校验 `command_id/combat_id/payload_hash` 后，只把 4.5 白名单类型反序列化为领域命令。V1 道具保留值在此按 4.5 稳定拒绝，禁止适配器把它改写成招式或直接调用效果服务。

### 10.1 `StartCombatSession`

| 项 | 契约 |
|---|---|
| 输入 | 关卡/阵容来源、`rules_version`、可信 `root_seed`、`seed_context_id`、控制策略、`start_receipt_id` |
| 前置 | 所有来源读取成功且修订稳定；关卡允许开始；无未结算同收据战斗 |
| 事务 | 按 `DeriveSeedV1(...,"combat",...)` 派生战斗子种子 → 构建双方快照 → 规范化/校验/哈希 → 创建会话 → 初始化事件；奖励子种子不进入会话，关卡入场成本由上层同收据处理 |
| 输出 | `CombatSessionDTO`、初始事件、快照哈希、修订 |
| 错误 | `COMBAT_SNAPSHOT_INVALID`、`PARTY_NOT_READY`、`COMBAT_RULES_VERSION_UNSUPPORTED`、`COMBAT_SEED_INVALID`、`COMBAT_SESSION_EXISTS` |
| 幂等 | 同启动收据返回原会话；载荷不同复用收据拒绝 |

### 10.2 `AdvanceCombat`

输入战斗 ID、预期修订、命令 ID、最大事件批大小。推进至决策/终局/批边界。输出事件批、新修订、决策或结果。错误包括 `COMBAT_REVISION_CONFLICT`、`COMBAT_ALREADY_FINISHED`、`COMBAT_INVALID_STATE`。同命令 ID 返回原批次边界和结果。

### 10.3 `ChooseCombatMove`

| 项 | 契约 |
|---|---|
| 输入 | 战斗/角色/招式/目标、决策 token、预期修订、命令 ID |
| 前置 | `DECISION_REQUIRED`；token/角色匹配；招式目标仍合法 |
| 事务 | 规范化命令 → 校验 → 执行动作 → 推进至下个边界 |
| 输出 | 命令接受事件、战斗事件批、下一决策或结果 |
| 错误 | `COMBAT_DECISION_STALE`、`MOVE_NOT_AVAILABLE`、`MOVE_TARGET_INVALID`、`QI_INSUFFICIENT` |
| 幂等 | 重复命令返回首次响应；非法命令不推进修订之外的诊断计数 |

### 10.4 `PassUltimateDecision`

输入决策 token 和命令 ID；令当前行动执行自动普通攻击。与选择招式相同幂等/修订规则。若普通攻击也非法则产生跳过事件。

### 10.5 `SetCombatAutoMode`

PVE 输入目标模式和命令 ID；从手动改全自动后立即由 AI 完成当前决策。全自动改手动只影响未来决策，不撤销已选动作。擂台返回 `COMBAT_MODE_LOCKED`。模式变化进入命令哈希，确保重放一致。

### 10.6 `ForfeitCombat`

输入战斗 ID、确认和命令 ID；PVE/擂台均判进攻方放弃。终局或规则错误后调用返回原结果。表现确认不属于领域事务。

### 10.7 `SettleCombatResult`

| 项 | 契约 |
|---|---|
| 输入 | 完整 `CombatResult`、会话证明、关卡/擂台结算上下文、结算收据 |
| 前置 | 战斗终态，快照/命令/事件哈希复核；结果类型允许结算；非只读 |
| 事务 | 本用例只编排下游关卡/奖励/任务/擂台事务，不修改战斗结果；全部使用派生子收据。随机奖励只能从 run 根种子的 `reward` 子流准备，禁止复用结果中的战斗 PRNG 状态 |
| 输出 | 结算状态、奖励/任务/排行结果、待补项 |
| 错误 | `COMBAT_RESULT_UNVERIFIED`、`COMBAT_SETTLEMENT_NOT_ALLOWED`、`SAVE_REVISION_CONFLICT`、`SAVE_READ_ONLY` |
| 幂等 | 同结算收据只结算一次；部分成功通过子收据恢复，不重跑战斗 |

## 11. 战斗事件契约

`CombatEvent` 是 00 §6 通用 `DomainEvent` 信封的专化，不是第二套裸事件结构。字段固定如下：

| 字段 | 规则 |
|---|---|
| `event_id` | `combat_id + ":" + decimal(sequence)`；十进制序号无前导零 |
| `event_type/schema_version` | 完成时事实名称；事件结构版本，与 `rules_version` 分离 |
| `aggregate_id` | 必须等于 `combat_id` |
| `revision` | 必须等于 `sequence`；从 1 开始严格递增，同一命令批也不得共享 revision |
| `occurred_at` | 必须省略；不得写服务器或本地时间 |
| `causation_id` | 根命令 ID、上游战斗事件 ID 或初始化收据 ID |
| `payload` | 事件专属、规范化字段 |
| `combat_id` | 战斗聚合 ID；字符集禁止 `:`，保证事件 ID 无歧义 |
| `sequence` | 从 1 开始严格递增、战斗内唯一；由聚合统一分配 |
| `action_index` | 当前行动索引，初始化事件为 0 |

因此 `event_id` 必须精确等于 `combat_id:sequence`，表现、任务和诊断消费者均以它去重；`event_id` 只解决事件投递去重，不可充当奖励 `source_occurrence_id` 或业务收据。效果系统只能请求战斗聚合追加事件，不能自行分配另一套 ID/序号。

| 类别 | 事件 |
|---|---|
| 生命周期 | `CombatCreated`、`CombatStarted`、`CombatFinishing`、`CombatFinished`、`CombatInvalidated` |
| 时间轴 | `TimelineAdvanced`、`ActorReady`、`ActionStarted`、`ActionSkipped`、`ActionFinished` |
| 命令 | `DecisionRequired`、`CombatCommandAccepted`、`CombatCommandRejected`、`CombatModeChanged` |
| 招式 | `MoveSelected`、`MoveUsed`、`MoveCooldownSet/Changed`、`MoveUseRejected` |
| 数值 | 状态文档定义的伤害、治疗、聚气、状态、护盾事件 |
| 单位 | `ActorDowned`、`ActorRevived`、`ActorSummoned`、`ActorRemoved`、`ActorPositionChanged` |
| AI | `AIDecisionMade`：规则、动作、目标、候选摘要；可配置诊断级别 |
| 机制 | `BossPhaseChanged`、`MechanicFlagChanged`、`WaveChanged` |
| 终局 | `CombatTimedOut`、`CombatForfeited`、`EffectBudgetExceeded`、`CombatFinished` |

表现层按序消费并用 `event_id` 去重；`(combat_id, sequence)` 必须能重建同一个 ID。`CombatFinished` 载荷包含结果与哈希，不包含永久奖励清单。

## 12. 存档、会话与复盘 DTO

### 12.1 云存档

- 槽 `1–5` 不保存进行中战斗状态。槽 `5` 只保存启动/结算业务收据和“待结算”记录。
- 开战前完成必要的入场成本事务并记录安全点；战斗异常退出后重进可选择重新开始该 Encounter，不能恢复到中途随机状态。
- 结算成功后保存关卡、奖励和任务结果；没有结算收据不得仅凭 UI 胜利画面发奖。

### 12.2 `CombatReplayDTO`

用于测试、诊断和可选本地复盘，不默认上传云档：快照规范化内容或引用哈希、`combat` 子种子、按序命令行、`rules_version`、最终结果、事件哈希、可选事件摘要。不得保存 `root_seed/reward_seed`；任何敏感平台标识先脱敏。

### 12.3 擂台

擂台结算可在槽 `5` 保存挑战收据与事件哈希摘要，在槽 `101` 更新积分；完整事件流不进入公开槽 `100`。公开快照规则见擂台文档，战斗内核只接收已验证本地重建结果。

## 13. Y3 适配与 UI

### 13.1 战斗表现控制器

- 根据 `CombatSnapshot` 创建临时 Y3 单位和双方镜像阵位；维护 `actor_id ↔ unit_handle` 只在适配层。
- 事件播放队列驱动动画、位移、弹道、特效、音效、镜头和跳字；同一序号只消费一次。
- 播放速度、跳过和追帧只改变等待时长。内核可提前生成结果，但 UI 在关键事件播完前不提前显示错误生命值。
- 资源/单位缺失时使用占位或直接同步最终位置，记录诊断，不重跑领域命令。

### 13.2 战斗 HUD

- 显示双方生命、聚气、状态、行动准备提示、当前行动者、手动/自动模式和 99 行动计数。
- 手动决策只显示领域返回的合法招式与目标；按钮提交中防重入，决策 token 过期后重载当前状态。
- V1 HUD 不创建道具按钮、药品快捷栏或背包入口；旧 UI/Y3 触发器若提交道具意图，只展示 `COMBAT_ITEM_USE_UNSUPPORTED`，不得本地播放使用成功或预扣物品。
- 可随时切全自动；切回手动从下一决策点生效。擂台隐藏/锁定切换。
- 支持 1×、2×、4×表现速度和跳过非首领演出；不改变内核推进。
- 状态覆盖：初始化、等待决策、播放、追帧、暂停菜单、规则错误、断线/应用恢复、终局待结算、结算失败待重试。

### 13.3 输入与生命周期

键鼠和 UI 均能选招式、选目标、放弃和切自动。V1 不绑定任何战斗道具快捷键；捕获到旧绑定时走同一稳定拒绝网关。关闭/切地图前若战斗未结算，应用层先写安全收据；Y3 单位清理失败不能导致再次结算。

## 14. 边界、失败与恢复

- 快照任何未知 ID、重复 actor/阵位、越界属性、`rules_version` 不支持或来源哈希不一致：不开战，返回完整原因。
- 快照或命令载荷出现背包物品、物品数量、快捷栏、`USE_ITEM` 或道具效果字段时稳定拒绝，不尝试裁剪后继续；拒绝不改变战斗、背包或任一随机流。
- 命令超时/响应丢失：客户端以 `command_id` 查询或重放；不能生成新 ID 猜测重试。
- 表现落后领域过多：暂停继续请求新事件批，先追帧；战斗结果已定也只结算一次。
- AI 配置无合法动作：使用普通攻击；普通攻击也非法则跳过。不得陷入无限决策。
- `current_tick` 或中间乘法将超安全整数范围：规则错误结束，不钳制为看似正常结果。
- 事件预算/状态预算超限：`INVALID_RULE_EXECUTION`，PVE 不发胜利奖励，擂台不按普通失败扣分并记录快照/规则诊断。
- 存档服务只读时可进行无奖励练习战；会产生进度/排行/奖励的战斗启动前必须拒绝或明确标为不可结算模式。
- 双方同时倒地、行动 99、玩家放弃、目标失效、召唤位置不足均有明确规则，不由 UI 判定。

## 15. 生成与静态校验

必须检查：所有战斗结构只使用 `rules_version`、伤害/治疗倍率安全上界、目标规则可选出目标或有回退、AI 规则引用与可达性、普通攻击存在、聚气/冷却范围、命令枚举不含道具、事件 Schema/`event_id` 公式、阵位与双方人数、首领/状态触发预算、擂台强制自动、所有表现 cue 映射。

生成报告应输出：

- 1/30/60 级标准角色对标准防御的伤害区间和随机消费路径。
- 每份 AI 配置在生命、聚气、状态关键组合下的首个命中规则。
- 所有招式的命中/暴击/格挡/效果概率最大抽样数。
- 所有首章 Encounter 的 99 行动可终结性模拟和无合法动作检查。
- 规范化快照、PRNG 向量、事件序列与哈希黄金文件版本。
- `DeriveSeedV1` 的 `combat/reward` 命名空间黄金向量，以及改变奖励抽样次数不改变战斗事件的隔离报告。

| 战斗道具 | `USE_ITEM`/别名、旧快捷键、伪造道具字段、重复 ID | 固定错误；战斗/背包/PRNG/哈希均不变 |
| AI | 规则优先、保命、保留聚气、无合法动作 | 相同状态始终同决策 |
| 终局 | 单方/双方全灭、99 行动、放弃、规则错误 | 结果和奖励许可正确 |
| 确定性 | 1000 次全自动、手动命令重放、输入乱序 | 状态/事件/哈希完全一致 |
| 存档/结算 | 异常退出、重复结算、部分奖励成功、只读 | 不重复发奖、不覆盖云档 |
| Y3 | 1×/4×/跳过、资源缺失、重复事件、单位清理 | 表现不改变结果 |
| 性能 | 双方 4 人、512 状态上限前合理压力 | 目标设备稳定，领域预算不误触发 |

## 17. 验收标准

- 纯 Lua 内核无 `y3.*`、系统时间、`math.random` 或不稳定集合遍历。
- 相同全自动快照、`combat` 子种子和 `rules_version` 运行 1000 次，最终状态、PRNG 消耗、事件序列与哈希完全一致；手动命令回放同样一致。
- 普通攻击自动、手动绝招/全自动切换、擂台强制自动均按契约工作。
- V1 所有战斗道具入口均以 `COMBAT_ITEM_USE_UNSUPPORTED` 稳定拒绝，不存在 `USE_ITEM` 领域命令，且拒绝前后战斗/背包/随机状态完全一致。
- 命中、伤害、治疗、聚气、冷却、状态、护盾、控制、前后排和超时黄金测试全部通过。
- 任何非法公开快照、未知规则、预算超限或整数风险被安全拒绝且不发正常奖励。
- 战斗结算重复提交和故障恢复不重复发奖励/任务/积分。
- 双方各四单位及首章首领机制在目标设备保持稳定表现；加速/跳过不改变结果。
