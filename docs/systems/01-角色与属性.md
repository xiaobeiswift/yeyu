# 《雾州侠行》角色与属性系统工程规格

> 状态：实施候选稿；仅描述未来实现，不代表代码已经存在。
>
> 上位约束：[00-通用工程约定](./00-通用工程约定.md)。若本文与通用约定冲突，以通用约定为准并补充决策记录。

## 1. 目标与非目标

### 1.1 目标

- 为主角、伙伴和敌人提供同一套可复算的基础属性、派生属性和战斗属性快照。
- 角色永久状态只保存“来源数据”，所有派生值按固定流水线计算，禁止把最终攻击、防御等缓存当作存档权威值。
- 支持等级成长、固定成长曲线、天赋、武器倾向、装备、武学、经脉和临时修正的组合。
- 领域层保持纯 Lua、整数化、确定性，可在 Lua 5.1 下脱离 Y3 完成测试。
- 为队伍、战斗、擂台公开快照和 UI 提供版本化、最小且稳定的只读 DTO。

### 1.2 非目标

- 本系统不负责伙伴招募、好感、阵位、装备穿脱、武学学习、经脉升级或奖励发放；只消费这些系统确认后的属性贡献。
- 本系统不保存战斗中的生命、聚气、冷却、状态效果或死亡状态。
- 首章不提供玩家自由加点和洗点；若后续启用，必须新增独立配置与迁移，不能复用成长字段。
- Y3 单位属性、物编数值和 UI 显示值不作为权威计算来源。

## 2. 依赖与跨系统接口

### 2.1 上游依赖

| 系统 | 输入契约 | 约束 |
|---|---|---|
| 配置注册表 | `CharacterDefinition`、`LevelCurve`、`AttributeFormulaSet`、`TalentDefinition` | 均以稳定字符串 ID 引用，启动时完成整表校验 |
| 装备系统 | canonical `StatContribution[]`，`source_type=EQUIPMENT` | 内部词条字段必须先适配为 4.3 的唯一 DTO；不给“最终面板” |
| 武学系统 | canonical `StatContribution[]`，`source_type=MARTIAL` | 只返回已装备且合法等级对应的被动贡献 |
| 经脉与长期成长 | canonical `StatContribution[]`，`source_type=PROGRESSION` | 必须带来源节点/境界 ID，便于重算和诊断 |
| 伙伴/权益系统 | 角色解锁事实 | 只决定角色是否拥有，不改变属性公式 |

### 2.2 下游接口

| 消费方 | 输出 | 说明 |
|---|---|---|
| 队伍与阵型 | `CharacterBuildView` | 用于编队合法性和阵容预览 |
| 确定性战斗 | `CombatantStatBlock` | 开战前冻结；战中只由效果系统修改运行时副本 |
| 异步擂台 | `CharacterBuildSnapshot` | 只包含来源 ID/等级/随机词条种子或结果，不含派生面板 |
| UI | `CharacterDetailDTO`、`StatBreakdownDTO` | 展示总值及来源拆分，禁止 UI 自行套公式 |
| 任务/对话 | 只读条件查询 | 可查询角色等级、主属性或标签，不得直接改角色状态 |

### 2.3 明确禁止的耦合

- 角色领域对象不得持有 Y3 单位句柄、物编 Key、UI 节点或平台玩家对象。
- 属性重算不得主动发放物品、触发任务、保存云档或播放表现。
- 跨系统贡献必须先由各系统校验，再以标准贡献 DTO 输入；角色系统不读取其他系统内部表。

### 2.4 canonical 属性与武器路线契约

- `StatContribution` 是所有永久构筑属性生产者的唯一跨系统 DTO。装备、武学、经脉/境界、阵型和关卡即使拥有内部 `stat_id/flat_value/rate_basis_points` 等配置字段，也必须在各自领域适配器内转换成 4.3 的完整字段后再交给角色流水线；系统私有贡献结构不得跨越该边界。
- 角色系统只校验 canonical DTO、来源修订和构筑上下文，不反向读取生产者配置。缺字段、未知枚举、重复 `stable_order_key`、越界值或未注册 `target_stat` 时整份构筑返回 `CHARACTER_CONTRIBUTION_INVALID`，不得猜默认操作或静默丢行。
- canonical 武器路线只有 `UNARMED/SWORD/BLADE/STAFF`。装备形态不是第五条路线：未装备武器和 `FIST_WEAPON` 都解析为 `UNARMED`，且 `FIST_WEAPON` 只能映射到 `UNARMED`；`SWORD_WEAPON/BLADE_WEAPON/STAFF_WEAPON` 分别映射同名路线。任何 `FIST` 路线值、其他隐式映射或一件武器映射多条路线均为生成错误。
- 武器路线解析只比较稳定枚举，不读取 Y3 物编 Key、模型或图标。快照保存 canonical 路线与装备来源 ID；装备形态仍由装备系统保存和展示。

## 4. 领域模型字段

### 4.1 `CharacterAggregate`

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `character_id` | string | `char_` 前缀；已注册 | 角色定义 ID，也是单玩家角色聚合 ID |
| `definition_version` | integer | `>=1` | 创建该角色时采用的定义兼容版本 |
| `level` | integer | `1..level_cap` | 当前等级 |
| `experience` | integer | `0..2^53-1` | 累计阅历，不因升级扣除 |
| `awakening_rank` | integer | 首章固定 `0` | 后续突破预留；未开放时非零即非法 |
| `unlocked_talent_ids` | ordered set<string> | 稳定排序、无重复 | 已确认解锁的天赋 |
| `custom_name` | string/null | UTF-8，0–18 个显示字符 | 仅主角可用；过滤和显示由应用层处理 |
| `created_receipt_id` | string | 非空、全局唯一 | 防止重复创建/发放角色 |
| `revision` | integer | `>=0`，每次成功变更加一 | 乐观并发修订 |

### 4.2 `PrimaryAttributes`

| 字段 | 范围 | 含义 |
|---|---:|---|
| `strength` | `0..9999` | 臂力；主要影响外功攻击和部分负重/条件 |
| `constitution` | `0..9999` | 根骨；主要影响生命、防御和治疗承受 |
| `agility` | `0..9999` | 身法；主要影响速度、命中与闪避评分 |
| `inner_power` | `0..9999` | 内息；主要影响聚气上限、聚气获取和内功威力 |

### 4.3 `StatContribution`

| 字段 | 类型 | 约束 |
|---|---|---|
| `source_type` | enum | `CHARACTER/LEVEL/TALENT/EQUIPMENT/MARTIAL/PROGRESSION/FORMATION/ENCOUNTER` |
| `source_id` | string | 稳定来源/贡献 ID；发布后不可复用语义 |
| `target_stat` | enum | 见 4.4；不得使用其他属性字段别名 |
| `operation` | enum | `ADD_FLAT/ADD_BP/MULTIPLY_BP/SET_MIN/SET_MAX` |
| `value` | integer | `-1,000,000,000..1,000,000,000` |
| `priority` | integer | `-1000..1000`；相同操作按升序处理 |
| `condition_tags` | ordered set<string> | 默认空；全部标签命中才生效，仅可读取战前 `BuildContext` |
| `stable_order_key` | string | 非空、构筑内唯一；由生产者确定性生成，发布后不可改变同一贡献的键 |

八个字段必须全部显式存在；空条件写 `condition_tags=[]`，不得省略。`stable_order_key` 建议规范为 `source_type:source_id:target_stat:operation:local_contribution_id`，它是排序键而不是可解析业务 ID。所有有效贡献先按 `(priority, stable_order_key)` 排序；同键即整份构筑非法，绝不以输入数组顺序破局。`condition_tags` 采用 AND 语义，OR 必须展开成多条具有不同稳定键的贡献。`ADD_BP` 表示把倍率基点相加；`MULTIPLY_BP` 表示逐项乘算，`10000` 为 100%。生产者内部字段到 canonical 操作的固定映射为：定值→`ADD_FLAT`、相加倍率基点→`ADD_BP`、显式独立乘区→`MULTIPLY_BP`；`SET_MIN/SET_MAX` 只能由白名单规则声明。

`source_id` 与 `stable_order_key` 使用 ADR-0005 的专用引用键语法，不套用 64 字节外部原子 ID 上限：组件最长 96 字节，`source_id` 总长最多 320 字节，`stable_order_key` 总长最多 512 字节。禁止空组件、连续冒号、尾冒号及非 ASCII 标点；超过上限必须在生产者边界拒绝，不能截断后参与排序或哈希。

### 4.4 `CombatantStatBlock`

| 字段 | 范围 | 说明 |
|---|---:|---|
| `max_hp` | `1..2,000,000,000` | 最大生命 |
| `attack` | `1..10,000,000` | 通用攻击评分 |
| `defense` | `0..10,000,000` | 防御评分 |
| `speed` | `1..100,000` | 行动速度评分 |
| `accuracy` | `0..10000` | 命中评分，非最终命中率 |
| `evasion` | `0..10000` | 闪避评分 |
| `crit_chance_bp` | `0..7500` | 暴击概率基点，战斗中再扣目标抗暴 |
| `crit_damage_bp` | `10000..30000` | 暴击伤害倍率，默认 `15000` |
| `crit_resist_bp` | `0..7500` | 抗暴基点 |
| `block_chance_bp` | `0..7500` | 格挡概率基点 |
| `block_reduction_bp` | `0..8000` | 格挡减伤，默认 `2500` |
| `damage_bonus_bp` | `-9000..50000` | 造成伤害统一修正 |
| `damage_reduction_bp` | `-50000..9000` | 承受伤害统一修正 |
| `healing_bonus_bp` | `-9000..50000` | 造成治疗修正 |
| `healing_received_bp` | `-9000..50000` | 受到治疗修正 |
| `max_qi` | `100..2000` | 聚气上限，默认公式通常落在 `1000` 左右 |
| `initial_qi` | `0..max_qi` | 开战聚气 |
| `qi_gain_bp` | `0..50000` | 聚气获得倍率，`10000` 为 100% |
| `effect_accuracy` | `0..10000` | 状态施加评分 |
| `effect_resistance` | `0..10000` | 状态抵抗评分 |

所有上限在流水线最后执行。达到上限要记录诊断项 `STAT_CLAMPED`，但只要配置合法不视为运行错误。

### 4.5 值对象

- `CharacterBuildView`：角色 ID、等级、已装备来源摘要、武器倾向、可用标签、修订号。
- `StatBreakdownDTO`：每个 `target_stat` 的基础值、逐项贡献、取整结果、钳制前后值和公式版本。
- `CharacterBuildSnapshot`：角色 ID、等级、天赋 ID、有版本的装备/武学/经脉来源 DTO、角色修订；不保存 `CombatantStatBlock`。
- `WeaponAptitude`：键严格为 `UNARMED/SWORD/BLADE/STAFF` 四项，范围 `0..10000`；首章只用于武学兼容、AI 标签和展示，不直接成为第五项主属性。拳套是 `FIST_WEAPON` 装备形态，但只查询 `UNARMED` 倾向，任何存档或配置都不得新增 `FIST` 倾向键。

| 字段 | 约束 |

| `hp_per_constitution` | 12 | 每点根骨生命 |
| `base_attack` | 10 | 不含武器攻击 |
| `attack_per_level` | 3 | 每级攻击 |
| `attack_per_strength` | 3 | 每点臂力攻击 |
| `attack_per_inner_power_milli` | 500 | 每点内息增加 0.5 攻击，统一最终向下取整 |
| `base_defense` | 5 | 基础防御 |
| `defense_per_level` | 2 | 每级防御 |
| `defense_per_constitution` | 2 | 每点根骨防御 |
| `base_speed` | 1000 | 基础速度 |
| `speed_per_agility` | 12 | 每点身法速度 |
| `base_accuracy` | 7000 | 基础命中评分 |
| `accuracy_per_agility` | 8 | 每点身法命中 |
| `base_evasion` | 0 | 基础闪避 |
| `evasion_per_agility` | 5 | 每点身法闪避 |
| `base_max_qi` | 1000 | 基础聚气上限 |
| `max_qi_per_inner_power` | 2 | 每点内息上限 |

### 5.4 `TalentDefinition`

字段包括：`id`、`schema_version`、`name_key`、`description_key`、`unlock_rule_id`、`contributions[]`、`combat_hook_ids[]`、`exclusive_group`、`tags[]`、`deprecated`。`combat_hook_ids` 只能引用状态与效果系统已注册的声明式钩子，不能嵌入脚本字符串。

## 6. 运行时状态与生命周期

### 6.1 永久状态

`CharacterAggregate` 只在以下事实发生后改变：角色首次创建、获得阅历导致等级变化、合法天赋解锁、主角改名、版本迁移。装备/武学/经脉变更保存在各自聚合中，只令角色构筑缓存失效。

### 6.2 派生缓存

- 缓存键：`character_revision + equipment_revision + martial_revision + meridian_revision + formation_context_hash + formula_version`。
- 缓存可随时丢弃，不进入云存档，不作为战斗或擂台校验依据。
- 生成战斗快照时必须重算一次；若重算结果与调试缓存不同，以重算值为准并记录 `CHARACTER_CACHE_MISMATCH`。

### 6.3 状态机

角色永久生命周期为：`UNOWNED → OWNED → AVAILABLE`。`UNAVAILABLE` 是由剧情/关卡给出的会话可用性视图，不改变拥有状态。角色 ID 一旦拥有不得回到 `UNOWNED`。战斗中的 `ALIVE/DOWNED` 属于战斗系统，不回写角色聚合。

## 7. 规则与公式

### 7.1 等级解析

给定累计阅历 `xp`，等级为满足 `cumulative_exp_by_level[level] <= xp` 的最大等级，并钳制在上限。升级不扣阅历。一次增加阅历可跨多级，只产生一个 `ExperienceGranted` 和一个包含起止等级的 `CharacterLevelChanged`。

### 7.2 主属性成长

每项主属性：

`成长值 = floor((level - 1) × growth_per_level_milli / 1000)`

`战前主属性 = clamp(基础值 + 成长值 + 所有 ADD_FLAT，再应用倍率与上下限, 0, 9999)`

倍率规则见 7.4。角色定义中的基础值和成长不受条件贡献影响。

### 7.3 首章派生基础公式

- `max_hp = base_hp + level × hp_per_level + constitution × hp_per_constitution`
- `attack = base_attack + level × attack_per_level + strength × attack_per_strength + floor(inner_power × attack_per_inner_power_milli / 1000)`
- `defense = base_defense + level × defense_per_level + constitution × defense_per_constitution`
- `speed = base_speed + agility × speed_per_agility`
- `accuracy = base_accuracy + agility × accuracy_per_agility`
- `evasion = base_evasion + agility × evasion_per_agility`
- `max_qi = base_max_qi + inner_power × max_qi_per_inner_power`
- `effect_accuracy = inner_power × effect_accuracy_per_inner_power`
- `effect_resistance = constitution × effect_resistance_per_constitution`

装备武器的基础攻击作为 `ADD_FLAT attack` 贡献进入，不写入公式常量。未列出的派生属性使用 4.4 默认值再接收贡献。

### 7.4 贡献流水线与取整

对每个属性固定执行：

1. 计算角色/等级公式基础值。
2. 按稳定顺序累加全部 `ADD_FLAT`。
3. 把全部 `ADD_BP` 求和，执行 `floor(value × max(0, 10000 + sum_bp) / 10000)`。
4. 对每个 `MULTIPLY_BP` 按稳定顺序执行 `floor(value × multiplier_bp / 10000)`；倍率必须 `0..50000`。
5. 应用最高优先级的 `SET_MIN` 与 `SET_MAX`；若最小值大于最大值，构筑非法。
6. 应用 4.4 的系统硬上限并输出诊断。

负值在最终硬钳制前允许存在，以便减益表达；每一步使用整数向下取整。贡献条件只能读取明确传入的 `BuildContext` 标签，例如 `PVE/ARENA/NIGHT`，不得自行取时间。

### 7.5 构筑合法性

- 角色必须已拥有，等级与定义上限一致，所有天赋/装备/武学/经脉引用存在并归属于该角色。
- 同一唯一来源不能重复贡献；重复时返回 `CHARACTER_DUPLICATE_SOURCE`，不得静默合并。
- 公开擂台快照中的最终属性一律忽略并报告；只从白名单来源重算。
- `deprecated` 内容可供已有存档读取，但不得新获得；其公式兼容版本必须保留。

## 8. 应用用例

### 8.1 `GetCharacterDetail`

| 项 | 契约 |
|---|---|
| 输入 | `player_id`、`character_id`、`view_context` |
| 前置 | 角色存档与相关装备/武学/经脉槽已成功读取；只读模式允许 |
| 事务 | 无写入；按修订组合重算或读取安全缓存 |
| 输出 | `CharacterDetailDTO`、`StatBreakdownDTO`、来源修订 |
| 错误 | `CHARACTER_NOT_OWNED`、`CHARACTER_CONFIG_MISSING`、`CHARACTER_BUILD_INVALID` |
| 幂等 | 天然幂等；相同修订和上下文返回相同结果 |

### 8.2 `GrantCharacterExperience`

| 项 | 契约 |
|---|---|
| 输入 | `character_id`、`amount`、`reason`、`receipt_id`、`expected_revision` |
| 前置 | 非只读；`amount` 为 `1..1,000,000,000`；角色已拥有；收据未处理 |
| 事务 | 校验收据 → 增加累计阅历 → 解析新等级 → 生成升级奖励意图 → 保存槽 3 和槽 5 收据；奖励由统一奖励事务同一提交边界完成 |
| 输出 | 旧/新阅历、旧/新等级、奖励结果、修订号 |
| 错误 | `CHARACTER_NOT_OWNED`、`CHARACTER_XP_OUT_OF_RANGE`、`SAVE_REVISION_CONFLICT`、`SAVE_READ_ONLY` |
| 幂等 | 同一 `receipt_id` 返回首次结果；不同内容复用同一收据返回 `IDEMPOTENCY_KEY_REUSED` |

### 8.3 `CreateOwnedCharacter`

| 项 | 契约 |
|---|---|
| 输入 | `character_id`、`source_type`、`source_reference`、`receipt_id` |
| 前置 | 来源已由任务、伙伴招募或权益对账系统验证；定义可创建 |
| 事务 | 若未拥有则创建一级角色、默认天赋和空构筑；若已拥有则由调用方的重复转化规则处理，本用例不自行发替代奖励 |
| 输出 | 创建结果或 `already_owned=true`、角色摘要、修订 |
| 错误 | `CHARACTER_SOURCE_UNVERIFIED`、`CHARACTER_DEPRECATED`、`SAVE_READ_ONLY` |
| 幂等 | 收据去重；重复调用不得重置角色或重复默认奖励 |

### 8.4 `RenameProtagonist`

输入主角 ID、新名称、幂等键和预期修订；前置为允许改名且名称通过长度/字符审核。事务只改名称并保存槽 3。错误包括 `CHARACTER_RENAME_NOT_ALLOWED`、`CHARACTER_NAME_INVALID`、`SAVE_REVISION_CONFLICT`。相同幂等键返回原结果。

### 8.5 `BuildCombatantSnapshot`

输入角色 ID、构筑上下文、各来源只读快照和 `rules_version`；前置为相关槽均已读取。事务无持久写入，先把所有生产者输出校验为 canonical `StatContribution[]`，再执行全量重算。输出 `CharacterBuildSnapshot`、`CombatantStatBlock`、来源哈希。任何未知 ID、越界等级、修订不一致、非法权益、非 canonical 贡献或武器路线映射非法，均返回 `CHARACTER_BUILD_INVALID` 及结构化原因数组。

## 9. 领域事件

| `event_type` | 载荷 |
|---|---|
| `CharacterOwned` | `character_id`、`source_type`、`source_reference`、`receipt_id` |
| `CharacterExperienceGranted` | `character_id`、`amount`、`old_experience`、`new_experience`、`reason` |
| `CharacterLevelChanged` | `character_id`、`old_level`、`new_level`、`unlocked_refs[]` |
| `CharacterTalentUnlocked` | `character_id`、`talent_id`、`source_reference` |
| `CharacterRenamed` | `character_id`、名称脱敏摘要，不在日志复制完整名字 |
| `CharacterBuildInvalidated` | `character_id`、`cause_type`、`cause_revision`；应用内事件，不要求单独持久化 |

事件遵循通用信封。等级事件消费者按 `event_id` 去重；任务系统只能把事件用于推进已经存在的目标，不得回调修改本次角色事务。

## 10. 存档 DTO、槽位与迁移

### 10.1 槽位归属

- 槽 `3` 保存角色永久状态。
- 槽 `5` 保存经验/创建等幂等收据索引；收据正文可按通用收据格式滚动保留。
- 槽 `100` 的公开擂台快照只复制最小 `CharacterBuildSnapshot`，不复制私有好感、剧情标记或最终派生属性。

### 10.2 `CharacterSaveDTO`（槽 3 子表）

为满足三层嵌套限制，采用扁平数组：

| 字段 | 类型 |
|---|---|
| `schema_version` | integer |
| `revision` | integer |
| `character_rows` | array；每行含 `character_id/definition_version/level/experience/awakening_rank/custom_name/created_receipt_id/revision` |
| `talent_rows` | array；每行含 `character_id/talent_id/unlocked_revision` |

禁止保存属性贡献数组、派生属性或 Y3 Key。读取后按 `character_id` 组装领域对象；写出前统一按 `character_id`、`talent_id` 排序。

### 10.3 迁移规则

- 缺失新字段只能使用版本声明的默认值，迁移后重新计算等级和属性。
- 旧存档若保存过派生面板，迁移时丢弃并记录一次 `CHARACTER_DERIVED_STATS_DROPPED`。
- 未知角色 ID 不自动删除：进入只读隔离并列出断链；只有显式兼容映射可迁移。
- 迁移重复执行必须产出字节级等价 DTO；写入使用旧修订比较与新修订回读。

## 11. Y3 适配与 UI

### 11.1 Y3 适配器

- `CharacterVisualAdapter` 根据 `model_asset_id` 查本地映射并创建/更新 Y3 单位；领域角色 ID 始终保留在适配器侧映射表。
- Y3 单位生命/攻击字段只用于血条和表现同步，不能回读为战斗结果。
- `CharacterSaveRepositoryY3` 负责槽 3 的序列化、修订检查和错误转换；不计算等级或属性。
- 属性变化后通过展示事件刷新单位血条上限；战斗快照已冻结时，永久成长不得中途污染当前战斗。

### 11.2 角色界面

- 角色页显示头像、等级/阅历、四主属性、派生面板、天赋和武器倾向。
- 每个派生属性支持打开“来源明细”，依次展示基础、定值、加算倍率、独立倍率和最终钳制。
- 状态覆盖：加载、空角色、正常、配置断链错误、只读、保存中、修订冲突重载。
- 升级获得时只展示已由事务确认的等级；动画不得提前改本地数字。
- 1920×1080 为基准，低宽度下来源明细改为分页；键鼠和 UI 都能选择角色、打开明细和关闭页面。

## 12. 边界、失败与恢复

- 阅历加法溢出、NaN/非整数输入、等级曲线不递增均视为硬错误，不写存档。
- 角色定义缺失时保留原 DTO，禁止用默认角色替代并覆盖云档。
- 贡献来源修订在计算过程中改变时返回 `CHARACTER_SOURCE_REVISION_CHANGED`，调用方重新读取后重试。
- 保存超时状态未知时，按收据查询/重新下载槽位，不直接再次加阅历。
- 角色达到等级上限后仍可累计阅历到配置的经验硬上限；不再产生升级奖励。
- 改公式版本不会静默改写旧擂台快照；快照必须声明规则版本，由擂台兼容策略决定重建或拒绝。
- 负倍率导致中间值小于零时按流水线继续，最终按属性下限钳制；诊断必须可见。

## 13. 生成与静态校验

生成器必须拒绝：重复/错误前缀 ID、缺失本地化、曲线非递增、上限不一致、成长或系数越界、天赋断链/互斥冲突、未知 `target_stat`、非法贡献操作、八字段不完整、`condition_tags` 非稳定集合、`stable_order_key` 缺失或重复、最小值大于最大值、武器路线第五枚举、`FIST_WEAPON` 非 `UNARMED` 映射、资源映射缺失、发布 ID 语义复用。

额外报告：

- 1、10、30、60、100 级的四主属性和派生面板快照。
- 各角色相对同级中位数超过配置阈值的离群项。
- 可能触及硬上限的贡献组合。
- 所有角色在无装备、首章标准装备和理论首章上限装备下的构筑合法性。

## 14. 测试矩阵

| 类别 | 必测用例 | 通过条件 |
|---|---|---|
| 等级 | 0 阅历、阈值前后、跨多级、满级、溢出 | 等级与奖励只产生一次，边界精确 |
| 公式 | 每项基础公式、负贡献、多倍率、上下限冲突 | 每步取整与黄金结果一致 |
| 顺序 | 打乱输入贡献数组 100 次 | 输出与来源哈希完全一致 |
| 贡献契约 | 装备/武学/成长内部字段适配、八字段缺失、稳定键重复、未知操作 | 只接受 canonical DTO；非法整构筑拒绝 |
| 武器路线 | 空手、拳套、剑/刀/棍、伪造 `FIST` 路线 | 只得到四路线；拳套固定为 `UNARMED` |
| 构筑 | 合法、未知 ID、重复来源、越界等级、弃用内容 | 合法通过；非法有稳定错误原因 |
| 缓存 | 任一来源修订变化、缓存损坏 | 必须重算且不污染权威结果 |
| 存档 | 往返、旧版迁移、重复迁移、修订冲突、读失败 | 无派生值落盘；失败不覆盖云档 |
| 幂等 | 重放经验/创建/改名命令 | 状态与事件不重复 |
| 擂台 | 伪造最终攻击、未知词条、旧公式版本 | 本地重算或明确拒绝 |
| Y3 | 单位创建、模型缺失、血条同步 | 适配失败不改变领域角色 |
| UI | 加载/空/错误/只读/重复点击 | 状态完整且无直接写领域数据 |

## 15. 验收标准

- 五名首章可用角色均能从配置生成合法一级与等级上限构筑。
- 同一角色来源 DTO、上下文和公式版本重复计算 1000 次，属性与哈希完全一致。
- 任意排列 canonical `StatContribution[]`，结果保持一致；所有生产者只有一种跨系统贡献 DTO，领域目录不引用 `y3.*`、系统时间或 `math.random`。
- 阅历跨级、满级、重复收据和保存冲突均通过无引擎测试且不重复奖励。
- 槽 3 往返与迁移不保存派生面板，数据不超过三层嵌套。
- 角色详情 UI 能准确展示每个属性来源，错误/只读时不会允许修改。
- 公开快照中伪造的派生属性无法进入战斗。

## 16. 实施任务拆分

1. 冻结 canonical `StatContribution`、四武器路线、属性键、整数范围、`rules_version` 和错误码。
2. 建立角色/曲线/公式/天赋 Schema 与生成校验器。
3. 实现主属性值对象、角色聚合、阅历等级解析和贡献稳定排序。
4. 实现属性流水线、来源明细、构筑校验和来源哈希。
5. 定义角色仓储端口、槽 3 DTO、槽 5 收据与幂等迁移。
6. 实现五个应用用例及领域事件派发/消费者去重。
7. 实现 Fake 仓储、公式黄金样本、属性组合与迁移测试。
8. 接入装备、武学、经脉/长期成长和阵型的 canonical 贡献适配器及武器形态映射。
9. 实现 Y3 角色视觉/云档适配和角色页 ViewModel。
10. 完成公开快照恶意输入、引擎烟测和验收数据报告。

## 17. 待决项

以下不阻塞领域骨架，但进入内容冻结前必须形成 ADR：

- 首章等级上限最终采用 50、60 还是其他值；当前公式样例按 60 校验。
- 主角是否允许改名、改名消耗与敏感词审核由平台还是本地承担。
- `awakening_rank` 是否在首章后启用，以及启用时对公式版本的影响。
- 武器倾向只做门槛/标签，还是加入小幅数值倍率；当前不直接增伤。
- 战斗外是否允许生命不满并持久化；当前明确不保存战斗生命，战后由结算规则处理。
- 数值平衡更新时，旧 PVE 存档是否立即采用新公式；擂台必须按赛季规则版本冻结。
