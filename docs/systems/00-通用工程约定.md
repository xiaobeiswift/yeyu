# 《雾州侠行》系统工程文档通用约定

> 状态：规划冻结候选稿
>
> 适用范围：`docs/systems` 下全部系统规格。本文只定义未来实现约束，不代表代码已经存在。

## 1. 文档目的

每份系统文档必须足以让开发者在不自行补完核心规则的情况下开始实现，并让策划、UI、测试能够围绕同一契约并行工作。系统实现前若发现文档存在冲突，先修订文档和决策记录，再修改实现。

每份系统文档至少包含：目标与非目标、依赖关系、领域模型、配置结构、运行时状态、规则与状态机、应用用例、事件契约、存档归属、Y3 适配、UI 行为、异常与边界、校验规则、测试矩阵、验收标准、实施拆分和待决项。

## 2. 分层与依赖规则

未来业务代码统一放在 `maps/EntryMap/script/wzx` 命名空间下。

```text
wzx/
├─ domain/          # 纯 Lua 规则、实体、值对象、状态机
├─ application/     # 用例编排、会话、事务边界、接口调用
├─ adapters/        # Y3 与 Fake 接口实现、DTO 转换
├─ presentation/    # UI 状态、输入映射、战斗事件表现
├─ config/          # Schema 与生成后的只读配置
├─ bootstrap/       # 依赖注入、启动、功能开关
└─ tests/           # 单元、契约、集成、黄金样本
```

硬性约束：

- `domain` 不得引用 `y3.*`、Y3 句柄、UI 节点、系统时间、平台玩家对象或网络回调。
- `application` 只能依赖领域模块和 `ports` 中的稳定接口。
- `adapters` 负责 Y3 数据与领域 DTO 的双向转换，不把 Y3 句柄写入领域状态或存档。
- `presentation` 只能通过应用用例发命令，通过领域/应用事件读状态，不得直接改背包、任务、战斗或权益。
- `bootstrap` 是唯一允许选择 Y3/Fake 实现并装配依赖的位置。
- 跨系统调用优先使用应用用例；领域事件只表达已经发生的事实，不作为隐式远程命令。

## 3. 稳定 ID 与配置规则

所有内容使用稳定字符串 ID。建议前缀：

| 类型 | 前缀 | 示例 |
|---|---|---|
| 角色 | `char_` | `char_player` |
| 武学 | `martial_` | `martial_sword_mist_01` |
| 招式 | `move_` | `move_sword_mist_finisher` |
| 效果 | `effect_` | `effect_bleed_minor` |
| 物品 | `item_` | `item_herb_green` |
| 装备 | `equip_` | `equip_sword_tier1_01` |
| 敌人 | `enemy_` | `enemy_bandit_blade` |
| 战斗配置 | `encounter_` | `encounter_ridge_boss` |
| 任务 | `quest_` | `quest_main_ch01_01` |
| 任务目标 | `objective_` | `objective_talk_gatekeeper` |
| 对话 | `dialogue_` | `dialogue_inn_intro` |
| 地区/地点 | `area_` / `location_` | `area_mist_inn` |
| 商店 | `shop_` | `shop_inn_general` |
| 掉落表 | `loot_` | `loot_bandit_common` |
| 卡池 | `banner_` | `banner_char_standard` |
| 轻功通行档 | `traversal_profile_` | `traversal_profile_cloudstep_01` |
| 探索通行网格 | `traversal_grid_` | `traversal_grid_reed_lake` |
| 探索通行格 | `traversal_cell_` | `traversal_cell_reed_lake_12_08_l0` |
| 特殊通行连接 | `traversal_link_` | `traversal_link_ravine_east` |
| 轻功通行规则 | `traversal_rule_` | `traversal_rule_jump_gap_basic` |
| 轻功位移表现 | `traversal_presentation_` | `traversal_presentation_mist_arc` |
| 轻功选点覆盖层 | `traversal_overlay_` | `traversal_overlay_default` |
| 水面通行区 | `water_zone_` | `water_zone_reed_lake_north` |

ID 发布后不可复用。内容下线时标记 `deprecated`，不能把旧 ID 指向语义不同的新内容。Y3 数字物编 Key 只允许出现在 `adapters/y3/mappings`，配置和存档不得直接持有数字 Key。

生成配置视为只读产物，禁止手改。所有配置必须通过重复 ID、必填字段、枚举、范围、概率、引用断链、循环依赖、任务可达性和版本兼容校验。

跨系统统一枚举：武器路线只使用 `UNARMED/SWORD/BLADE/STAFF`。拳套属于装备表现/类型 `FIST_WEAPON`，映射到路线 `UNARMED`，不得把 `FIST` 当成第五条路线直接比较。

轻功探索能力统一使用 `JUMP_BASIC/JUMP_LONG/JUMP_HIGH/WATER_WALK`。能力集合必须按固定顺序输出并完成依赖闭包：LONG/HIGH 均隐含 BASIC，WATER_WALK 独立。跳跃同时满足水平格数、单段 Link cost、垂直高度和地图连接要求；水上入口、内部移动和出口只累计扣除本次会话的 `water_range_cells`，WATER_WALK 的 `max_route_cost` 固定为 0，标签不能绕过预算与水域连通性校验。V1 不引入轻功体力、耐力、随机失败、任意自由物理跳或游泳。

探索轻功使用独立的 `TraversalGrid/TraversalCell` 离散网格。它只服务于地图落点、渡水路径和可达范围展示，与战斗系统的 3×3 `Formation` 阵位没有坐标换算或数据复用关系。普通格和连接可由地图数据烘焙，跨悬崖、单向、高低差或剧情门等特殊边由稳定 `TraversalLink` 覆盖；玩家看到的格子范围只是领域层可达集的投影视图，确认目标时必须再次按当前世界修订校验。

所有战斗、公开快照、Manifest 和诊断统一使用字段名 `rules_version`；`schema_version` 只表示数据结构版本，`content_version` 只表示内容集合版本，三者不得互换。

## 4. 数值、时间与随机性

- 权威规则使用明确的取整方向；涉及伤害、概率、排名和货币时，文档必须给出整数边界。
- 金额、积分、计数和关键战斗数值优先使用整数；不得依赖平台浮点显示值反推权威状态。
- 领域层不得使用 `math.random`。所有随机行为接收显式 PRNG 与种子。
- 会影响结果的集合必须显式排序；不得依赖 `pairs` 遍历顺序。
- 原始可信 UTC 时间只通过 `ClockService.now()` 获取。通用日/周/活动周期由 17 `TrustedPeriodPort` 计算，竞技赛季/竞技日由 20 规则计算，卡池开放窗由 21 规则计算；其他系统不得自行从本地时间或裸时间戳拼周期 ID。
- UI 动画时间、表现速度和本地时间不得影响战斗、奖励、任务或权益结果。

所有属性来源统一输出 `StatContribution`：`source_type`、`source_id`、`target_stat`、`operation`、`value`、`priority`、`condition_tags`、`stable_order_key`。装备、武学、经脉和天赋可以拥有自己的配置视图，但进入角色属性流水线前必须转换为这一规范类型；禁止各系统各自实现乘区和优先级。

## 5. 命令、结果与错误

应用用例接收结构化 Command，返回 `Result`：

```text
Result = {
  ok: boolean,
  value?: DTO,
  error?: {
    code: string,
    message_key: string,
    retryable: boolean,
    details?: table
  }
}
```

错误码采用 `SYSTEM_REASON`，例如 `INVENTORY_FULL`、`QUEST_PREREQUISITE_MISSING`、`SAVE_REVISION_CONFLICT`。面向玩家的文字由 `message_key` 本地化，领域层不返回拼接后的中文错误句。

会产生奖励、消耗货币、更新积分或发放权益的命令必须包含幂等键。重复提交同一幂等键必须返回原结果，不得再次改变状态。

## 6. 领域事件契约

所有跨系统事件使用统一信封：

```text
DomainEvent = {
  event_id: string,
  event_type: string,
  schema_version: integer,
  aggregate_id: string,
  revision: integer,
  occurred_at?: integer,
  causation_id?: string,
  payload: table
}
```

确定性战斗事件不写服务器时间；其顺序由 `sequence` 和战斗种子决定。持久化事件必须有唯一 `event_id`，消费者按事件 ID 去重。事件 Schema 升级时保留上一发布版本的读取路径。

事件命名使用完成时事实，例如 `QuestAccepted`、`ItemGranted`、`FormationChanged`、`CombatFinished`，不使用 `DoQuestReward` 这类命令式名称。

## 7. 存档与修订

规划槽位：

| 槽 | 归属 |
|---:|---|
| `1` | 玩家档案、版本、功能开关快照 |
| `2` | 世界、任务、对话选择、采集和宝箱状态 |
| `3` | 角色、伙伴、武学、经脉、阵型 |
| `4` | 背包、装备、非付费货币权威余额、制作状态 |
| `5` | 引导、可信周期观察、各系统周期状态、恢复索引与幂等收据；按 section 分权 |
| `100` | 公开擂台快照 |
| `101` | 擂台排名整数 |
| `200–299` | 付费角色/武学权益平台单调计数 |
| `300–319` | 抽取凭证、累计抽数、最高稀有度序号、兑换 earned/spent 等平台单调 totals；不保存可递减余额 |

每个表型槽必须包含 `schema_version` 和 `revision`。数据最多三层嵌套；系统文档中的逻辑模型若超过三层，必须定义扁平化保存 DTO。

读取失败进入只读恢复流程，禁止以默认新档覆盖未知云档。迁移必须幂等；写入前校验旧修订，写入后校验新修订。关键奖励使用业务收据去重，不能仅依赖“某字段是否已有值”。

只有存档系统的 `SaveCoordinator` 可以直接调用 `SaveStore`。共享槽使用一个 `owner_coordinator` 和多个 `payload_section_owners`；子系统通过 `SlotNTransactionPort` 提交变更，不能读改写整槽覆盖其他系统。

Y3 云档不假定支持跨槽 ACID。跨槽业务统一采用可恢复 Saga：

1. 槽 `5` 写入 `PREPARED` 意图和各目标槽预期修订。
2. 各权威槽按固定顺序应用带同一 `transaction_id` 的子收据并回读验证。
3. 失败或结果未知时进入 `RECOVERY_REQUIRED`，只允许用同一事务 ID 前向补完或按明确补偿规则处理。
4. 全部权威槽确认后，把全局收据标记 `COMMITTED`；事件通过 outbox 重放。

系统文档中的“原子”只可表示同一内存聚合或同一槽协调写；涉及多个云槽时必须写成“幂等、可恢复 Saga”，不得承诺失败后云端整体回滚。详见 [ADR-0002 跨槽可恢复事务](../architecture/ADR-0002-跨槽可恢复事务.md)。

ID 语义固定如下：`command_id` 是同一用户/系统命令的重试身份；`source_occurrence_id` 是奖励来源事实的唯一身份；`transaction_id/receipt_id` 是已编排业务事务及其结果身份；`event_id` 只用于事件投递去重。不同语义不得复用同一裸 ID，均需系统命名空间。详见 [ADR-0003 身份与事件字典](../architecture/ADR-0003-身份与事件字典.md)。

## 8. 权威性与安全边界

- 单机 PVE 的同步 Lua 是战斗和奖励规则权威，表现客户端无权直接写结果。
- 公开擂台快照属于不可信输入：只接收白名单 ID 和范围内等级/词条，派生属性全部本地重算。
- 付费结果只能来自 Y3 平台商城和服务器随机池；客户端 Lua 不生成付费抽取结果。
- 真实付费卡池默认关闭。原子性、补偿、实名/防沉迷、概率公示和至少 90 天审计任一项未验证，均不得开启。
- 日常与赛季不可使用本地系统时间作为领奖依据。
- 槽 `200–319` 的平台整数权益由平台服务权威；槽 `3/5` 只能保存领域拥有状态、不可变事务摘要或恢复游标，不能保存第二份可独立增减的权益计数。
- 公开快照必须携带槽 `3`、槽 `4`、权益游标、`rules_version` 和 `content_version` 的来源向量；任一来源修订变化均使快照失效并重新发布。

## 9. UI 与交互约定

- 设计基准为 1920×1080，使用锚点和安全区适配。
- 每个应用用例必须声明忙碌、成功、失败、可重试和只读状态。
- 所有提交型按钮在命令未完成时防重复点击；超时后不得假定失败或成功，需查询状态或安全重试。
- UI 只保存临时展示状态；会影响进度的选择必须通过应用用例进入领域状态并保存。
- 键鼠操作必须有等价 UI 路径；关键教学可跳过并能从帮助页重看。

## 10. 可观测性

日志统一包含：`session_id`、`player_aid` 的脱敏值、`use_case`、`correlation_id`、`result_code`、`revision`。不得记录完整付费身份、未脱敏平台标识或敏感凭证。

关键链路必须有结构化日志：存档读取/迁移/写入、奖励事务、战斗事件哈希、擂台快照校验、商城回调、随机池请求和权益对账。

## 11. 通用完成定义

一个系统只有同时满足以下条件才算工程完成：

- 配置 Schema、默认值、枚举、范围和引用规则已冻结。
- 领域规则和状态机有无引擎测试。
- 应用用例定义了成功、失败、重试和幂等行为。
- Y3 适配器只做转换与调用，没有重复实现领域规则。
- 存档 DTO、迁移、失败恢复和三层嵌套限制已验证。
- UI 覆盖加载、空、正常、错误、只读和重复点击状态。
- 结构化日志和关键诊断信息可用。
- 验收用例通过，P0/P1 缺陷为零。
