# ADR-0002：Y3 云档跨槽可恢复事务

> 状态：已采纳（规划阶段）

## 背景

Y3 云存档按槽保存，当前不能假定多个槽支持数据库式原子提交。任务交付、装备生成、门派晋升和奖励可能同时涉及槽 2、3、4、5。

## 决策

跨槽操作使用前向恢复 Saga，不承诺 ACID 回滚。

### TransactionRecord

字段：`transaction_id`、`command_id`、`kind`、`state`、`expected_revisions`、`ordered_steps`、`completed_step_ids`、`result_hashes`、`created_at`、`last_error`。

状态：`PREPARING → PREPARED → APPLYING → COMMITTED`；异常进入 `RECOVERY_REQUIRED`，明确补偿完成后才可为 `COMPENSATED`。`FAILED_BEFORE_APPLY` 只用于没有权威步骤成功的情况。

### 提交协议

1. 验证全部前置、来源修订、容量和余额，生成不可变 change set。
2. 在槽 5 保存 PREPARED 意图。
3. 按固定顺序写 owner 槽；每槽保存 transaction_id、step_id 和结果哈希后回读。
4. 结果未知时停止后续普通命令，进入恢复；不得换新 command_id 重试。
5. 加载阶段按收据查询每个步骤，已应用步骤不重复，缺失步骤继续执行。
6. 全部确认后槽 5 标记 COMMITTED，并从 outbox 发布完成事件。

同一槽内由 Slot Coordinator 合并 section change，可作为一个槽步骤。私人槽完成后再发布槽 100/101 等派生数据；派生发布失败不回滚私人进度。

### 检查点

槽 2–5 的关键写入携带 `checkpoint_id`。槽 1 Manifest 最后写入新的 committed checkpoint 与各槽修订向量。加载器将高于 Manifest 的槽修订视为待对账写入，不能直接当成完整检查点。

## 后果

- UI 需要“正在确认/需要恢复”状态。
- 业务设计优先前向补完；已经消费并发放的普通奖励不做任意逆向回滚。
- 所有跨槽故障点必须有 Fake 注入和重进测试。
